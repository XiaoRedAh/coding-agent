⓪ 项目本质 · 什么是 Harness 工程

Harness（驾驭框架 / 脚手架）的定义

  • 围绕 LLM 的运行时基础设施：让 LLM 从「只会说话」变成「能可靠地做事」
  • 字面义：马具/挽具——把 LLM 这匹"野马"套上挽具，让它能拉车干活
  • Anthropic 的核心公式：Augmented LLM = LLM + 工具 + 检索 + 记忆
  • 本项目不是"调 API 写 prompt"，而是手搓了一整套 harness
关键认知：coding agent 的大部分工程不在 prompt，而在 harness（循环、工具、上下文、稳定执行）

⓪ 业界视角 · ACI / Poka-yoke / Workflows vs Agents

ACI（Agent-Computer Interface）

  • 像设计 HCI（人机接口）一样设计 ACI——工具描述是给模型看的 UI，好坏直接决定模型用不用得对
# ✗ 坏描述（模型不知何时该用、和谁重复）
name: grep
description: "Search files"

# ✓ 好描述（何时用 / 代替谁 / 返回什么）
name: grep_search
description: "在文件内容中搜索正则。
  用这个代替 cat|grep 管道——直接返回
  文件名+行号+匹配行，比读整个文件省
  上下文。找不到返回'无匹配'而非报错。"
三条要诀：何时用（场景）、代替谁（防和 shell 竞争）、返回什么（设定预期）——"找不到不算错"这种边界情况写进去，模型就不会误判失败

Poka-yoke（防错设计）

  • 修改参数设计使错误更难发生，而非事后纠错
  • 案例：SWE-bench Agent 用相对路径易错 → 强制绝对路径后无误
  • 本项目对应：edit_file 唯一性匹配、safe_path 归一化、危险命令白名单

Workflows vs Agents

  • Workflow：LLM 沿预定义代码路径编排（可预测）
  • Agent：LLM 动态主导流程（灵活但成本高）
  • 本项目两者都有：核心循环=Agent，SOP 工作流=Workflow
  • 原则：从最简单开始，不够再上 agentic

② 知识铺垫 · 一次 LLM 调用的完整解剖

三个输入：你是谁 / 聊到哪了 / 能干什么

# 真实 API（Anthropic 侧）
client.messages.create(
  system="你是编程助手...",
  messages=[{role, content}, ...],
  tools=[{name, description, input_schema}])

# 输出不是纯文本，是块列表：
resp.content = [text 块 | tool_use 块]
  • system = 员工手册：身份/规则/规范——跨轮几乎不变（→ 可缓存，Prompt Caching 章细讲）
  • messages = 聊天记录：三个输入里唯一会增长的（→ 长了必须压缩，上下文管理章）
  • tools = 工具柜清单：模型每轮都看得见，自己决定伸不伸手（→ ACI 工具设计）

为什么要 tools 槽位（而不是写进 prompt）

  • 2022 年的做法：把工具说明写进 prompt，要求模型输出 JSON 文本，再用正则解析——约定脆弱，模型格式经常崩，崩了整个循环就卡死
  • 独立槽位后：输入侧——服务端把定义转译成模型训练过的内部格式；输出侧——模型产出结构化 tool_use 块，无需文本解析
  • 注意：工具定义照样消耗 token（模型必须"看得见"才能选）——省的不是 token，是解析的可靠性
一句话：tools 槽位把"模型会用工具"从外挂约定升级为 API 原生能力——这是现代 Agent 与 2022 年"prompt 里调工具"的分水岭，也是本项目循环层的地基

  "name":"get_sum","description":"加两个数",

② 知识铺垫 · 并发三模型（进程/线程/协程）

进程（Process）

  • 独立内存空间，隔离性最强
  • 通信靠 IPC（管道/共享内存）
  • 创建/切换开销大
  • 适用：CPU 密集、强隔离（如 MCP 子进程）

线程（Thread）

  • 共享进程内存，通信直接
  • 创建/切换开销小
  • GIL：CPU 密集受限，IO 密集不受影响
  • 适用：IO 密集（等 LLM/shell/网络）
本项目选线程——Agent 的并发是"等 LLM/shell"的 IO 等待，不是计算

协程（Coroutine）

  • 单线程内切换，开销最小
  • 需 async/await + 事件循环
  • 改造现有同步代码成本高
  • 适用：海量 IO 连接（如 web 服务）

② 知识铺垫 · threading.Thread + daemon

创建线程 + daemon 语义

t = Thread(target=run_subagent, daemon=True)
t.start()   # 立即返回，后台跑

# daemon=True 的规则：
# 主线程退出时不等待它，直接强杀
  • daemon=True：后台守护线程，进程退出即结束
  • 这正是"自杀死进程丢结果"的根源——daemon 线程的结果可能没来得及回收

join 超时 + is_alive

# 超时护栏：等 LLM 最多 N 秒
t.join(timeout=300)
if t.is_alive():
    # 超时了，但线程仍在跑（僵尸）
    mark_timeout()
  • join(timeout)：阻塞等最多 timeout 秒，不终止线程
  • is_alive()：判断是否还在跑——实现"超时检测"而非"超时终止"
  • 超时 ≠ 终止：join 超时后线程仍在后台跑（需额外处理）

② 知识铺垫 · queue / Lock / Event 原理

queue.Queue

# 内部 = deque + Condition
q.put(item)       # 入队
q.get(timeout=5)  # 出队，可超时
  • 线程安全的生产-消费队列
  • get 里 while not empty（非 if）防竞态
  • get(timeout) 实现"带超时的等待"

threading.Lock

with lock:
    # 临界区：同一时刻只有一个线程
    counter += 1
  • 互斥：保护共享状态（如 in_flight 计数）
  • 底层是二值信号量，不可重入
  • 粒度越细，并发越高（但易错）

threading.Event

event.wait(timeout)  # 阻塞等待
event.set()          # 唤醒所有等待者
event.clear()        # 复位
  • 布尔标志 + Condition：跨线程信号灯
  • set() 唤醒 wait() 的线程，零忙等
  • 用于"任务完成"通知（子 Agent 完成 → 唤醒主循环）

② 知识铺垫 · 订阅发布模式（EventBus）

发布-订阅（Pub-Sub）核心思想

  • 解耦：发布者不知道谁在听，订阅者不知道谁在发
  • 核心三要素：topic（主题）、publish（发布）、subscribe/consume（订阅/消费）
  • 与队列的区别：队列是"点对点"，pub-sub 是"一对多广播"
类比：函数调用 = 领导挨个打电话（谁接、什么顺序，代码里写死）；EventBus = 发邮件到组（谁订阅了谁收到，关系运行期可改）——所以「测试失败要回环到实现」这种流程变化，只改订阅关系，不动引擎代码，这正是工作流选它的原因

本项目 EventBus 实现

# topic → 订阅者集合
subscribers = defaultdict(set)
# 每个角色 → 消息 inbox
inbox = defaultdict(deque)

publish(topic, event):
  for role in subscribers[topic]:
      inbox[role].append(event)

consume(role):
  return inbox[role].pop()  # 取一条
  • 工作流角色订阅 topic，事件发布后路由到角色 inbox
  • deque 做每角色队列（先进先出）

② 知识铺垫 · 用四个原语手搓 mini 任务队列（综合运用）

MiniAgentTaskQueue（项目骨架的极简版）

class MiniTaskQueue:
    def __init__(self):
        self.results = Queue()     # ① 队列：传数据
        self.in_flight = 0
        self.lock = Lock()          # ② 锁：护计数
        self.event = Event()        # ③ 事件：做唤醒

    def increment(self):          # 派发前调用
        with self.lock:
            self.in_flight += 1

    def submit(self, task_id, result):  # 完成时调用
        self.results.put({"id": task_id, "r": result})
        with self.lock:
            self.in_flight -= 1
        self.event.set()           # 唤醒等待者

    def wait_and_drain(self, timeout=120):
        if self.event.wait(timeout):   # 阻塞等唤醒
            drained = []
            while not self.results.empty():
                drained.append(self.results.get())
            self.event.clear()     # 复位，等下一批
            return drained
        return None              # 超时

四个原语为什么缺一不可

  • 去掉 Queue：结果没地方放——多个任务同时完成会互相覆盖
  • 去掉 Lock：in_flight 计数竞态——两个线程同时 +1/-1，计数漂移，等待判断失效
  • 去掉 Event：主循环只能忙轮询（sleep 1s 查一遍）——白烧 CPU 且延迟高
  • 去掉 Thread（调用方）：没有"后台"可言，长任务阻塞主循环

典型用法

q.increment(); Thread(target=agent_a).start()
q.increment(); Thread(target=agent_b).start()
while q.in_flight > 0:
    results = q.wait_and_drain(120)
    if results: inject(notify(results))

④ ReAct 论文 · 核心思想（Thought→Action→Observation）

论文信息 + 核心思想

  • 论文：Yao et al. 2022《ReAct: Synergizing Reasoning and Acting in Language Models》，ICLR 2023，arXiv:2210.03629
  • 核心主张：让 LLM 交错生成「推理轨迹」和「具体动作」，而不是把推理和行动分开
  • 关键洞察：推理帮助更好地行动，行动获取外部信息，外部信息再帮助更准确地推理——三者互相增强

三要素

  • Thought（推理轨迹）：生成/追踪/更新行动计划，处理异常
  • Action（动作）：与外部资源交互（知识库/Wiki API/环境）
  • Observation（观察）：动作获得的外部信息，反馈到下一步推理

④ 前置概念 · CoT 思维链（Chain-of-Thought）

CoT 是什么

  • 论文：Wei et al. 2022《Chain-of-Thought Prompting Elicits Reasoning in Large Language Models》
  • 核心：通过 prompt 引导 LLM 生成中间推理步骤——一步步思考，而非直接给答案
  • 方法：few-shot 示例里给出「问题 → 推理步骤 → 答案」，让模型模仿这种格式

为什么有效（我的理解）

  • 强制模型把"跳跃的直觉"展开成"可逐步验证的步骤"，每步都有依据可查
  • 相当于让模型"打草稿"——草稿暴露了推理路径，错误才能被发现和纠正
  • 在算术、常识、符号推理等任务上显著提升（尤其大模型）

经典例子

Q: Roger 有 5 个网球，又买了
   2 罐，每罐 3 个。一共几个？

A（标准）：11

A（CoT）:
   一开始有 5 个网球
   2 罐 × 3 个 = 6 个
   5 + 6 = 11 个
   → 答案是 11 个
CoT 与 ReAct 的关系：CoT = 只推理不行动（闭门造车，会幻觉）；ReAct = CoT + 行动（用外部观察纠正推理）。理解了 CoT，才能理解 ReAct 为什么"多了一个行动"就解决了幻觉——用外部事实打断错误推理的传播

④ 核心循环 · 等待闭环 · 三态决策算法

问题定义

  • 主 Agent 派发后台子 Agent后，模型可能过早 end_turn 结束对话，导致后台结果丢失
  • 解决：在调 LLM 之前，先检查「有没有在飞的后台任务」，有就等而不是调 LLM

三态决策

if in_flight == 0:      # 态1
    call_llm()           # 正常推理
elif queue.drain():      # 态2 有结果
    pass                # 处理完结果继续
else:                   # 态3 等待超时
    skip_llm()           # 跳过 LLM 继续等

推导关键点

  • 为什么收到部分结果仍 skip LLM：只要还有任务在飞，就继续等，否则模型可能拿「不完整结果」过早下结论
  • 为什么用 Event 唤醒而非轮询：主循环在 wait_and_drain 上阻塞，子 Agent 完成时 set() 唤醒，零忙等
  • 超时语义：agent_wait_timeout=120s 超时后 skip LLM 继续等，最多等到轮次耗尽
def wait_and_drain(timeout):
    if event.wait(timeout): # 被唤醒
        return drain()   # 收结果
    return False         # 超时
数据基础：AgentTaskQueue = 通知队列 + 在飞计数 + 阻塞 Event（详见 08/10 模块）

④ 多 Agent · AgentTaskQueue 三态等待

数据结构 = 三合一

class AgentTaskQueue:
  results = Queue()     # 通知队列
  in_flight = 0        # 在飞计数（Lock 保护）
  event = Event()       # 阻塞事件

submit()    → 投递结果 + set()
increment() → in_flight += 1
drain()     → 取空队列
wait_and_drain(timeout) → 等待+收
  • 「队列 + 计数 + 事件」三种原语各司其职：队列传数据、计数判在飞、事件做唤醒

三态等待的推导

  • 为什么用 Event 而非 Queue.get(timeout)：需要「等待 + 顺便查 in_flight」的复合语义——纯 Queue 无法知道"是否还有任务在飞"
  • drain 的竞态防御：单消费者场景，主循环独占消费，无并发竞争
  • in_flight 计数：每派一个后台子 Agent 就 +1，完成 -1，用于判断"是否还有在飞"
increment(); Thread(run_subagent).start()
# 子 Agent 完成后：
submit(result); event.set()  # 唤醒等待者
完整时序见 10 模块「并发与消息传递」，此处聚焦数据基础角色

④ 实战复盘 · 贪吃蛇任务 33 分钟不收敛

发现的问题（现象）

  • 贪吃蛇任务跑 33 分钟，4 轮 Engineer/Tester 都没收敛，最后进程被 Killed
  • Tester 输出的 test_report.json 里 verdict/blocker_count 等核心字段为空，raw_output 只是半截文本
  • artifacts 只剩最后一轮覆盖的文件，前几轮失败细节丢失
排查手段：看日志层（每角色 turn 数/耗时）+ 交付物证据（artifacts）——发现"空壳产物"通过了兜底补字段，掩盖了真实失败

根因分析（4 个）

  • ① 结构化输出校验过宽：缺失字段自动补空值，把"空壳产物"修饰成合法 → 质量门禁失效
  • ② artifact 固定路径写入：每轮写同一路径，覆盖多轮上下文 → 复盘困难
  • ③ 回路预算不匹配：简单任务也走重 SOP → 性价比低
  • ④ Tester 策略偏 shell 回路：低价值重复动作 → 收敛效率低

④ 实战复盘 · 解决方案（P0/P1/P2 分层）

P0 立即执行（对症下药）

  • ① 结构化输出硬校验：verdict 等字段非空/类型校验，不通过触发"格式修复重试"
  • ② 产物按轮次归档：路径加 fix_round + 时间戳 → 正是 PPT 里「产物版本化」的来源
  • ③ 回路异常短路：连续两轮关键信息为空，提前升级人工接管

P1/P2 长期 + 经验沉淀

  • P1：任务复杂度分流 Router（简单任务走单 Agent，复杂才走 SOP）+ 动态预算收缩
  • P2：失败画像聚类（格式失败 / 测试失败 / 环境失败）
沉淀的经验：失败不是单点 bug，而是「质量门禁 + 可观测性 + 任务路由」三者叠加——结构化协议要硬校验、产物要版本化、任务要按复杂度路由

⑤ 记忆系统 · 调研 · 读写时机的三难题

何时写？

  • 每轮都写 → 记忆沦为噪音垃圾场
  • 从不写 → 跨会话失忆
  • CC 方案：每轮结束后台 fork extractMemories（不阻塞主循环，去重后再落盘）
  • 本项目：模型显式决定写什么（system prompt 指导 + 写入工具）

写什么？

  • 只记不可推导：偏好 / 决策 / 背景——代码里能读到的不记
  • 记事实 → 过期腐烂：记忆漂移（代码改了，记忆没改）
  • CC 的 autoDream：后台整理去重，对抗陈旧条目堆积

何时读？

  • 启动时注入索引（MEMORY.md 常驻 system）
  • 正文按需 read_file（两级召回）
  • 挑战：相关性判断全靠 description 语义——模型"想不起来要查"就没救（召回失败的隐性成本）
记忆的本质矛盾：写多了是噪音，写少了是失忆；读早了浪费 token，读晚了错过时机——所有记忆系统设计都在这组矛盾里找平衡点，没有银弹

⑤ 记忆系统 · 一次读写的完整闭环

读链路（每个会话启动时）

① 扫描 memory/ 目录（*.md 文件）
② 每个文件解析 frontmatter：
   name + description（一行简介）
③ 汇总生成 MEMORY.md 索引
   （≤200 行 / ≤25KB，超限截断+WARNING）
④ 注入 system prompt 动态区
⑤ 模型看索引 → read_file 全文（按需）
  • 索引是动态生成的，不是手工维护的文件——删掉一条记忆文件，下次启动索引自动更新
  • 第⑤步 = 两级召回的第二级：全文只在"模型觉得相关"时才进上下文

写链路（模型显式决定）

模型判断"这值得记"
（system prompt 指导：只记不可推导）
  → 调用写入工具
  → memory/ 下创建/更新一个 .md：
     ---
     name: user-prefers-pytest
     description: 用户偏好 pytest 测试
     ---
     正文：具体偏好细节...
  → 下次启动回到读链路①
  • 写入即文件：无数据库、无向量库——文件可直接 cat/git 管理，可观测性最好
  • 已知边界：写入靠模型自觉 + prompt 指导，没有后台自动抽取（CC 用 fork extractMemories）
读写闭环的关键：frontmatter 是索引和正文的契约——读链路只取 name+description 生成索引，正文整块不动，两级召回才能成立

⑤ 技能系统 · 参数替换 + 规范校验

参数替换算法

load(name, args):
  ① replace("$ARGUMENTS", args)  # 整体
  ② for i, a in enumerate(args.split()):
       replace("$ARG_%d" % (i+1), a)
  ③ replace("${SKILL_DIR}", dir) # 无条件
  • 先 $ARGUMENTS 后 $ARG_N：避免替换进去的内容被二次污染
  • split() 任意空白：连续空格/换行不产生空元素
  • ${SKILL_DIR} 无条件：即使无参也要定位自己的资源
  • 缺参不报错：技能是文档非函数，缺参兜底由正文教模型

规范校验 + 扫描去重

_NAME_PATTERN = r"^[a-z0-9]+(-[a-z0-9]+)*$"
# 小写字母数字连字符，不能连续/首尾连字符

if name not in self.skills:  # 重名先到先得
    self.skills[name] = {...}
  • name 强制小写连字符：是斜杠命令合法字符集，防 / 解析混乱
  • 可选字段宽容：license 等不校验，避免"装不上"假阳性
  • rglob + sorted：递归扫技能仓库，排序保证重名确定性

⑤ MCP · JSON-RPC 2.0 底层协议

为什么选 JSON-RPC 而非 REST/gRPC

候选不选的原因
REST面向资源(CRUD)，MCP 是「调用工具」非「操作资源」
gRPC需 protobuf 编译，门槛高，不利于社区采用
GraphQL过度复杂，MCP 不需要灵活查询
JSON-RPC传输无关 + 极简(3页) + JSON 原生 + 支持通知
关键优势 · 传输无关：同一套消息可走 stdio/HTTP/WebSocket——协议只关心「消息内容」，不关心「怎么传输」。这是 MCP 能跨多种传输的根本原因

三种消息类型 + 标准错误码

Request:      {id, method, params}   # 有响应
Response:     {id, result|error}     # id 匹配请求
Notification: {method, params}        # 无 id 无响应
错误码含义
-32700Parse error（JSON 解析失败）
-32600Invalid Request（格式无效）
-32601Method not found（方法不存在）
-32602Invalid params（参数错误）
-32603Internal error（内部错误）
id 是匹配的关键：请求带 id，响应带相同 id，客户端据此配对——这正是本项目 _send_request 里 response.id == request_id 的协议根源

⑤ MCP · 三大能力本质 + vs Function Calling

三大能力的本质

能力本质触发方副作用
Tools动作（函数）模型自主可能有
Resources数据（只读）应用按需无
Prompts流程（模板）用户选择无
我的理解：MCP 把「动作 / 数据 / 流程」三种不同性质的抽象统一成一个协议——Tools 是"让模型动手"，Resources 是"给模型资料"，Prompts 是"给用户模板"。多数 Server 只用 Tools，但协议设计时预留了三类

MCP vs Function Calling（关联概念）

  • Function Calling：LLM API 特性——让模型输出结构化工具调用意图
  • MCP：Agent 与外部服务的通信协议——标准化获取和执行工具
  • 层次不同：Function Calling 在「LLM 层」，MCP 在「协议层」，两者配合
LLM 层：Function Calling
  → 模型输出 tool_use（"调用 get_sum"）
协议层：MCP
  → 把 tool call 转发到 Server
执行层：MCP Server → 真实 API
类比：Function Calling 是「嘴巴」（说出想做什么），MCP 是「手」（实际去做）——一个表达意图，一个落地执行，缺一不可

⑤ MCP · 实战复盘 · 7 个真实 Bug（逐个排查）

Bug现象根因修复
① 超时失效tools/call 卡死，永不超时readline() 阻塞读，本身无超时参数读下沉线程 + queue.get(timeout)

④ 命名冲突工具名解析歧义server 名含 - 转成 _ 后与分隔符 __ 混淆非 [a-z0-9] 字符折叠为单个 _

⑤ 小节复盘 · 散落在工具/上下文/权限里的坑

工具系统的坑（发现 → 排查 → 解决）

  • 弯引号匹配失败：模型输出弯引号（"hello"），源码里是直引号（"hello"）→ edit_file 精确匹配失败，报 not found，模型反复重试
  • 解决：_normalize_quotes 标准化后再匹配（对齐 CC 14 步流水线的一步），成功时注明 "matched via quote normalization"
  • grep 退出码误判：grep 无匹配返回 1——被当"命令失败"，模型以为 grep 坏了，换别的工具绕路
  • 解决：_EXIT1_OK_COMMANDS 白名单——grep/diff/test 的退出码 1 返回正常输出"无匹配"

上下文与权限的坑

  • 索引截断无提示：MEMORY.md 超 200 行被截断 → 模型以为索引就是全部，该查的记忆没查
  • 解决：截断必须附 WARNING——宁可多解释，不让模型猜错
  • 压缩级联失败：压缩失败 → 上下文继续涨 → 触发再压缩 → 再失败（雪崩）
  • 解决：断路器连续 3 次熔断跳过——跳过是止损，报错是加速崩溃
  • 路径逃逸：../../etc 相对路径绕过工作区白名单
  • 解决：resolve() 归一化后再判定 is_relative_to(workdir)
这些坑的共同点：不是 crash，而是模型对环境产生错误认知——工具没坏但报失败、索引不全但模型不知情。Poka-yoke 在 agent 语境的真正含义：让"环境反馈"永远真实

⑥ 横切保障 · 四模块设计动机（问题 → 方案）

提示词工程 · 为什么不是"写一段话"

  • 问题：system prompt 混着稳定身份（几乎不变）与每轮变化的 cwd/记忆/技能 → 每轮整段变化
  • 方案：三级覆盖（project>user>builtin）+ 动静分离切分 + cache_control 标静态区
  • 衍生问题：模板含花括号 → str.format 会炸 → .replace 替换

权限安全 · 防的是什么

  • 问题：模型能执行任意 shell / 写任意文件——一次误操作就是灾难（rm -rf / 杀宿主进程）
  • 方案：deny>ask>allow 管线 + bypass-immune 危险检测 + fail-closed 默认拒绝

上下文管理 · 窗口不是无限大

  • 问题：长任务几十轮后上下文爆炸 → API 报错 / 成本失控 / 旧信息挤出新信息
  • 方案：五级渐进压缩（廉价到昂贵逐级）+ 锚点增量估算 + 断路器防级联

稳定执行 · LLM API 不可靠是常态

  • 问题：429 限流 / 529 过载 / 空响应 / 截断——任何一个都能让循环卡死或崩掉

⑥ 提示词工程 · 调研 · Prompt Caching 原理

原理：为什么能缓存

  • LLM 推理是自回归：每步生成都要对「整个前缀」做 attention，算出 K/V 矩阵
  • 前缀逐字节相同 → K/V 矩阵完全相同 → 服务端缓存下来，后续请求直接复用
  • Anthropic 价格：写 1.25×、读 0.1×（cache 命中省 90%）；5 分钟 TTL
关键约束：前缀必须逐字节一致，改一个字符整块失效——这就是"动静分离"存在的设计动机

算一笔账（为什么值得）

# 假设 system+工具 10k token，对话 50 轮
无缓存: 10k × 50 轮 = 500k 全价输入
有缓存: 首轮 10k × 1.25（写）
       + 49 轮 × 10k × 0.1（读）
       ≈ 12.5k + 490k等效×0.1
# system 部分 ~85% 折扣，且
# TTFT（首 token 延迟）显著下降
  • CC 场景 system+工具+CLAUDE.md 常达数万 token × 每轮 → 不缓存成本不可承受

⑥ 权限安全 · 调研 · Prompt Injection 挑战

攻击面（coding agent 特有的）

  • 直接注入：用户输入恶意指令——相对好防（本来就有确认管线）

  • CC：7 层纵深防御 + sandbox 隔离 + AI 危险分类器（语义级判断，非纯正则）

  • 权限最小化 + deny>ask>allow 弹窗确认
  • 权限疲劳：弹窗太频繁 → 用户无脑 always allow → 防线名存实亡（可用性 vs 安全的经典权衡）

⑥ 提示词工程 · 踩过的坑与沉淀的经验

三个真实问题（发现 → 排查 → 解决）

  • 事故 F · 双指令冲突：工作流角色模板（prose 流程描述）与内置 agent 提示词（JSON 输出指令）同时生效——模型一会听模板的、一会听内置的，输出格式反复横跳
  • 解决：中性 system_prompt_override 整体替换——角色模式下模板全权接管，不再拼接
  • 事故 H · 花括号劫持：角色模板里的 JSON 示例含大量 {...}，被 str.format 当占位符解析，直接 KeyError 崩溃
  • 解决：放弃 format，约定显式占位符 + replace 只替换 {key}——模板语法和内容转义分离
  • Coordinator 不插值 bug：系统提示词里的 {WORKDIR} 写在普通字符串里（非 f-string）——运行时模型拿到的是占位符原文而非路径
  • 解决：f-string 修复；更深的教训——提示词的插值错误没有报错，只有静默的错误输出

沉淀的四条经验

  • 双指令必冲突：两段"都算数"的指令，模型表现 = 随机切换——覆盖语义 > 拼接语义（三级覆盖同款原则）
  • 模板与内容必须解耦：占位符显式约定、replace 精确替换——模板里出现 JSON/代码是常态，format 天生不兼容
  • 插值要像代码一样被验证：静默错误最险——test_workflow_stability 专门断言输出含 <summary> 标签（提示词产物也有单测）
  • 每条规则可追溯：写新规则前先问"这条对应什么坏行为"——答不上来就不写
核心认知：提示词就是代码——会有语法错误（插值）、合并冲突（双指令）、静默失败（占位符原文）——所以要用工程手段对待：约定、替换语义、单测覆盖，而不是"写完就跑"

⑥ 上下文管理 · 设计动机：为什么逐级、为什么这些阈值

为什么逐级，而非一步 LLM 摘要到底？

  • 各级代价差异巨大：L1 纯裁剪零成本、L2 字符串替换近零、L5 要一次完整 LLM 调用——逐级 = 每次只付「必要的最小代价」
  • 损失不可逆：L5 摘要丢掉的细节找不回来——能用廉价手段撑住，就绝不动昂贵手段
  • 类比：磁盘满了先清回收站，不够再删下载目录，最后才考虑格式化——没人上来就格式化

为什么阈值是 50 / 60 / 85（不是 90 / 95）

  • 压缩不是瞬时的：从触发到生效之间模型还在跑、上下文还在涨——阈值必须留缓冲，否则"压缩进行中撞墙"
  • 低水位动廉价手段（50%→L1、60%→L2）：零/低成本提前腾地方
  • 昂贵手段留逃生距离：L5 在 85% 就触发——离上限还有 15%，一次摘要调用的往返时间足够
三个数字背后是同一个思想：越昂贵的操作，越早触发、留越多余量——与六道防线「廉价检查在前、昂贵中断在后」同构，这是贯穿全项目的资源管理哲学

⑥ 上下文管理 · token 估算的数学

为什么需要估算 + 两种方法

  • 为什么估算：判断"上下文利用率到阈值了吗（50%/60%/85%）"是每轮都做的高频操作，每次都调 tokenizer 太贵，需要轻量估算
  • 方法一 · 本地估算：字符数 ÷ 经验比例（英文约 4 字符/token，中文约 1-2 字/token）——快但误差大
  • 方法二 · API 回传：usage.input_tokens 精确，但只在 LLM 调用之后才有
为什么本地估算误差大（30%+）：token 不是字符——中文 1 字 ≈ 1~2 token、英文单词长度变化、代码/数字/符号比例又不同，用固定比例必然失真。尤其中文，一个"字符/token 比"根本稳定不下来

锚点 + 增量：误差稀释的数学

estimate = anchor + delta
            ↑          ↑
        API 精确(误差0) 本地估算(误差 e=30%)

总误差 = e × (1 - r)
  # r = anchor 占总量的比例
  # r=0.85 → 30% × 15% = 4.5%
  • API 每轮刷新锚点，只估算"锚点之后新增"的一小段
  • 直觉：错误只作用在"没被锚点覆盖的增量"上，锚点占比越高，误差被稀释得越狠
  • CJK 修正：中文按更高比例估算，进一步压低增量误差
一句话理解：与其全程猜（30% 误差），不如"猜最近一小段、前面用真实值"——把大误差问题缩小成小误差问题

⑥ 上下文管理 · 锚点估算 + snip 算法

snip 前后对照（真实效果）

# 压缩前：多轮历史，含大工具结果
[assistant] 我先读一下核心文件...
[user/tool_result · read_file loop.py]
  "loop.py 完整源码（8,420 字符）..."
[user/tool_result · read_file main.py]  ← 最新读取
  "main.py 完整源码（1,100 字符）..."

# L2 snip 后（保留最近 3 条 + 最新读取）
[user/tool_result · read_file loop.py]
  "[Content snipped - re-read if needed]"
[user/tool_result · read_file main.py]  ← 原样保留
  "main.py 完整源码（1,100 字符）..."
  • 占位符自带逃生门："re-read if needed" 告诉模型随时可重取——压缩不改变"世界状态的认知"
  • 同一文件多次读取只保最新：旧版本已被覆盖，留在上下文里是纯浪费
  • write/edit 结果永不被 snip——写入不可重取，丢了模型就"失忆"改错

L2 snip 六步算法

① utilization < 0.6 → 直接返回
② 收集所有 tool_result 反查工具名
③ len <= 3（保留最近）→ 返回
④ candidates = 去掉最近 3 条
⑤ 建"每文件最新读取"索引（从后往前）
⑥ 逐条 snip：
   read_file 且是最新读取 → 跳过
   len > 100 → 替换为占位符
  • 可重取才可 snipe：read/grep/list 可重取，write/edit 不可丢
  • len>100 才 snip：占位符本身有成本，收益不明显不动

⑥ 上下文管理 · 断路器 + 截断公式

断路器 · 连续 3 次熔断

should_skip(): return fail >= 3
record_success(): fail = 0   # 清零
record_failure(): fail += 1
  • 连续 vs 累计：累计 3 次会因偶发失误永久熔断；连续 3 次表达"系统恢复了重新计数"
  • 熔断语义：跳过压缩而非报错——防"失败→涨→再压缩→再失败"级联
  • 压缩后恢复：_collect_recent_files 从后往前去重，找回最近文件 + 技能

截断公式推导

keep_each = (budget - 80) // 2
# 头尾各半 + 中缝提示(80字符)
# keep_each + 80 + keep_each ≤ budget
  • // 2 整除：切片索引须整数，向下取整保证不越界
  • 头尾各半而非全留头：返回码/结论常在尾部
  • 80 是"中缝提示"保守估长，宁可略保守不超预算
关键原则贯穿：压缩不得改变模型对世界状态的认知（snip 保最新读取、截断附 WARNING）

⑥ 上下文管理 · 一次压缩事件的完整时间线（端到端走查）

从触发到恢复（真实时序）

turn N：工具结果回传
  → maybe_compact()            # hooks 每轮调用
  → 估算 utilization = 0.87      # 锚点+增量
    0.87 > 0.85 → 触发压缩
  → L1 budget_tool_results      # 动态缩结果
    → 0.81 仍高，继续
  → L2 snip_stale_results       # 换占位符

  → L3 microcompact             # 空闲触发，跳过
  → L5 auto_compact             # 最贵的一级

    messages = [<summary>块]     # 92k → 6k
  → 恢复：_collect_recent_files # 找回最近文件+技能
  → tracker.reset_after_compact # 锚点重置
  → 下一轮照常继续              # 模型几乎无感

时间线上的四个关键设计

  • 逐级尝试、够了就停：L1 降到 0.7 就不会走到 L5——多数压缩在前两级无感解决
  • 断路器并行待命：L5 连续失败 3 次 → 熔断跳过——防"压缩失败→上下文涨→再压缩"的雪崩
  • 恢复是压缩的一半：摘要丢细节后，_collect_recent_files 把最近文件内容补回来——否则模型"失忆后找不着文件"，从头再读一遍（成本反弹）
  • 锚点重置：摘要后 token 从新基线算起——旧锚点作废，否则估算永远虚高
检验压缩系统是否合格的标准：压缩后模型的行为是否平滑——不重复读文件、不忘初衷、能接着干（L5 摘要 9 节结构就是为此设计的）

<analysis>   # 阶段1：按时间走查

产物形态 + 压缩后恢复

  • 替换整个 messages：摘要成为新历史的第一条（几十轮 → 一块 <summary>）
  • 为什么要 9 节：每节都是一个"防遗忘"——初衷（1）、工作对象（3）、踩过的坑（4）、当前断点（8 最详细，续作靠它）

L5 的设计哲学：丢掉过程，保住"继续干活所需的最小状态"——初衷、对象、错误、断点，一个都不能少；这也是为什么它是最后手段（一旦摘要偏了，信息就永久丢失）

⑥ 稳定执行 · 指数退避 + 可观测

指数退避公式推导

delay = base × 2^(n-1)
  # 1s→2s→4s→8s... 封顶 32s
jitter = delay × 0.25 × random()
  # 随机抖动，错峰重试
  • 为何指数：给服务端越来越长的恢复窗口，请求频率越来越低
  • 为何 jitter：防"惊群效应"——大量客户端同时退避会同时重试造成二次限流
  • 为何封顶 32s：用户等不了 2^10=1024s，超时交还模型换策略
模拟：429 重试序列 1.12s→2.3s→4.8s→耗尽注入 error；400 零重试直接交还

全链路可观测

  • JSONL trace：结构化事件落盘，可复盘

  • 错误分类 → 用户友好消息（get_error_message）
  • 复盘方法论：莫名退出怎么查（atexit + trace 对照）

⑥ 并发与消息传递 · 全手搓

只用标准库三件套

原语用途

无 asyncio / 无消息中间件 / 无第三方并发库

模型：多线程 + 锁 + 信号灯的协作式并发，非事件驱动、非 async/await

为什么手搓（三个判断）

  • IO 密集（等 LLM/shell）→ 线程够用，无需 asyncio
  • 单进程 → 进程内 Queue 够用，无需中间件
  • 低并发（<10）→ 无需复杂调度

核心原语原理

  • Queue：内部 deque + Condition，get 里 while not empty 防竞态
  • Event：布尔标志 + Condition，用于"等待 + 查 in_flight"复合语义
  • daemon=True：进程退出不等它直接强杀（这是"自杀死进程丢结果"的根源）

⑥ 并发 · 完整链路 + 坑与隐患

后台子 Agent 完整链路

① increment()          # in_flight += 1
② Thread(run_subagent).start()
③ 子 Agent 完成:
   submit(result)       # 投递结果
   event.set()          # 唤醒等待者
④ 主循环 wait_and_drain:
   event.wait(120s)     # 被唤醒
   drain()              # 收结果
  • 「计数判在飞 + 队列传数据 + 事件做唤醒」三者分工清晰

6 个已知边界（坑）

  • daemon 结果丢失：进程退出不等后台线程，强杀丢结果
  • 超时 ≠ 终止：join(timeout) 超时后线程仍在跑（僵尸）
  • empty() 竞态：单消费者场景安全，多消费者会误判
  • EventBus 非线程安全：单线程串行消费所以安全
  • stderr 管道死锁：不消费会写满 64KB 阻塞（MCP 已修）
  • 阻塞读无超时：readline 无法加超时，需下沉线程 + 队列

⑦ 全书收束 · 一次用户输入的完整生命周期

主循环（带模块坐标）

while turns < max_turns:              # ④ 核心循环
    notifs = drain()                   # ⑥ 并发：收割后台通知
    resp = adapter.chat(system,        # ⑥ 稳定执行：退避重试
              messages, tools)         #   + JSON 截断修复
    for tb in resp.tool_blocks:      # ④ tool_use 块
        permit = check(tb)             # ⑥ 权限：deny>ask>allow
        r = dispatch(tb)               # ⑤ 工具：注册表→执行
        messages.append(               #   ToolResult + 截断
            tool_result(r))
    maybe_compact(messages)            # ⑥ 上下文：五级压缩
    if resp.end_turn and not pending: # 等待闭环
        return resp.text

一行一模块（这段伪代码 = 全书目录）

  • system 由提示词章装配（动静分离+缓存）；messages 由上下文章维护（压缩）；tools 由工具/技能/MCP 章提供
  • adapter.chat：Anthropic 直传 / OpenAI 转换，流式回调实时渲染，429 退避重试
  • 每个 tool_use 依次过权限 → 工具 → 截断三关——⑤ 章"五站旅程"
  • 全程横切：trace 落盘（可观测）、LLM 错误走注入式恢复（稳定执行）
  • end_turn 不是终点：有后台任务/在飞子 Agent 就继续等（等待闭环）
