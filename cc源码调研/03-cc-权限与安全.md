## 一、AI Agent 权限控制概论

### 1.1 什么是 AI Agent 的权限控制？

传统 CLI 工具的权限模型非常简单——用户敲什么命令就执行什么命令，责任完全在用户。但 AI Agent 彻底改变了这个范式：**模型自主决定执行什么操作**。当用户说"帮我重构这个项目"，模型可能自主决定删除文件、执行 shell 命令、修改系统配置——这些操作的风险程度天差地别。

**AI Agent 的权限控制**，是指在 Agent 自主执行工具调用（Tool Use）之前，由一套系统化的机制来判定"是否允许该操作执行"、"是否需要人类确认"、"是否应直接拒绝"。它本质上是 Agent 与用户环境之间的**安全护栏（Guardrail）**。

### 1.2 为什么需要权限控制？——动机与必要性

| 挑战维度 | 传统 CLI | AI Agent |
|--------|--------|---------|
| 操作发起者 | 人类直接输入 | 模型自主决策 |
| 操作可预测性 | 完全可预测 | **不可预测**——用户无法提前知道模型会调用哪些工具 |
| 风险谱系 | 用户自行承担 | 从读取文件（无害）到 `rm -rf /`（灾难性），所有操作通过同一接口 |
| 效率要求 | 不存在 | **每次弹确认会让用户抓狂**，但完全自动化又有安全风险 |
| 信任边界 | 明确 | **模糊**——模型可能被 prompt injection 误导执行危险操作 |

核心矛盾总结：

> **效率与安全的矛盾**：每次都弹确认对话框会严重降低生产力，但完全自动化又面临不可控的安全风险。权限控制的核心使命就是在这两者之间找到精确的平衡点。

### 1.3 设计权限控制时需要考虑的方面

在为 AI Agent 设计权限控制系统时，需要系统性地考虑以下维度：

```
┌─────────────────────────────────────────────────────┐
│                 权限控制设计考量                        │
├──────────────┬──────────────────────────────────────┤
│ 1. 粒度设计   │ 工具级 vs 操作级 vs 内容级              │
│ 2. 信任模型   │ 默认拒绝 vs 默认允许 vs 渐进式信任       │
│ 3. 规则体系   │ 静态规则 vs 动态规则 vs AI 辅助判断       │
│ 4. 用户体验   │ 确认频率 vs 安全性的平衡                  │
│ 5. 持久化     │ 会话级 vs 项目级 vs 全局级 规则管理        │
│ 6. 企业管控   │ 管理员策略覆盖 vs 用户自定义              │
│ 7. 降级策略   │ 自动化失败时如何优雅降级                   │
│ 8. 审计追踪   │ 每次决策的完整记录与来源追溯               │
│ 9. 攻击防御   │ Prompt Injection / TOCTOU / 路径穿越      │
│10. 运行环境   │ 交互式 vs Headless vs 子 Agent             │
└──────────────┴──────────────────────────────────────┘
```

## 二、Claude Code 权限系统设计亮点与创新点

Claude Code 的权限系统是目前公开可见的 AI Agent 中最完善的权限控制实现之一。以下是其核心设计亮点：

### 亮点 1：纵深防御（Defense in Depth）— 7 层安全架构

Claude Code 不是依赖单一权限检查，而是构建了 7 层独立的安全防线：

```
Layer 1: 工作区信任确认（Trust Dialog）
Layer 2: 权限模式（Permission Mode）
Layer 3: 权限规则匹配（allow/deny/ask）
Layer 4: Bash 多层安全（AST 解析 + 23 项静态检查）
Layer 5: 工具级安全（validateInput / checkPermissions）
Layer 6: 沙箱与隔离（Sandbox + Git Worktree）
Layer 7: 用户确认（交互式对话框 + ML分类器 + Hook）
```

> 核心哲学：**每一层都假设其他层可能失效**。即使 AST 语义分析被绕过，路径约束和用户确认仍然可以拦截。

### 亮点 2：渐进式信任 + 快速通道

不是对所有操作使用统一的安全检查强度，而是将检查成本与风险级别对齐：
- **低风险操作**（读文件）→ 规则快速放行
- **中风险操作**（编辑项目内文件）→ 模式级判断
- **高风险操作**（执行 shell 命令）→ AI Classifier + 人工确认

### 亮点 3：AI Classifier 辅助安全判断

用一个**独立的 AI 模型**来判断主模型请求的操作是否安全（"AI 监督 AI"架构），并配合三层快速通道避免不必要的 API 调用。

### 亮点 4：`passthrough` 语义的引入

工具的 `checkPermissions` 可以返回 `passthrough`，表示"我没有意见，交给通用权限系统决定"。这让工具权限逻辑与全局权限逻辑实现了优雅的解耦。

### 亮点 5：Bypass-Immune 安全检查

即使用户选择了最宽松的 `bypassPermissions` 模式，对 `.git/`、`.claude/` 等敏感路径的安全检查**仍然生效**。用户显式配置的 `ask` 规则同样不会被 bypass 跳过。

### 亮点 6：连续拒绝熔断器（Denial Tracking）

当自动决策连续失败时，不会无限重试，而是根据运行环境选择合适的降级策略：有人时降级到人工干预，无人时果断中止。

### 亮点 7：竞速决策机制（Race Decision）

用户确认对话框、Hook 脚本和 AI 分类器**同时启动、竞速决策**——但一旦用户亲自操作对话框，自动化结果一律丢弃，**人类意图永远优先**。

### 亮点 8：tree-sitter AST 解析 + Shadow 测试策略

用真正的 Bash 语法解析器替代手工正则解析，采用 FAIL-CLOSED 原则（不理解的结构一律不信任），并通过 Shadow 模式在生产环境中渐进式验证。

## 三、深度解读：分模块体系化讲解

### 3.1 权限模式（Permission Mode）分类归纳

Claude Code 定义了 **7 种权限模式**，代表用户对 AI 操作的不同信任程度。可以按照"面向用户 vs 内部"以及"信任级别"两个维度进行分类：

#### 3.1.1 外部模式（用户可用）

| 模式 | 信任级别 | 行为 | 适用场景 |
|------|---------|------|---------|
| `default` | ★☆☆☆☆ 最低 | 每个非只读操作都需要用户确认 | 日常交互式使用 |
| `plan` | ★★☆☆☆ 只读 | 只能读取和搜索，写入操作需要确认 | 代码审查、架构分析 |
| `acceptEdits` | ★★★☆☆ 中等 | 工作目录内的文件编辑自动允许，其他操作仍需确认 | 信任度高的项目 |
| `bypassPermissions` | ★★★★☆ 高 | 跳过大部分权限检查（但 safety check 仍然生效） | CI/CD 管道、完全信任环境 |
| `dontAsk` | 特殊 | 不弹出确认对话框，需要确认的操作自动拒绝 | CI/CD 无人值守环境 |

#### 3.1.2 内部模式（不对外暴露）

| 模式 | 信任级别 | 行为 | 适用场景 |
|------|---------|------|---------|
| `auto` | AI 判断 | 用 AI Classifier 自动判断操作安全性 | 仅限 Anthropic 内部 |
| `bubble` | 冒泡 | 子 Agent 权限冒泡回主 Agent | 多 Agent 协调 |

#### 3.1.3 模式定义代码

```typescript
// types/permissions.ts:16-22
export const EXTERNAL_PERMISSION_MODES = [
  'acceptEdits',
  'bypassPermissions',
  'default',
  'dontAsk',
  'plan',
] as const

// types/permissions.ts:28-29
// 内部模式在外部模式基础上扩展 auto 和 bubble
export type InternalPermissionMode = ExternalPermissionMode | 'auto' | 'bubble'
export type PermissionMode = InternalPermissionMode
```

`auto` 模式通过编译期门控（Feature Gate）控制——在外部构建中，相关代码会被 DCE（Dead Code Elimination）完全移除：

```typescript
// types/permissions.ts:33-36
export const INTERNAL_PERMISSION_MODES = [
  ...EXTERNAL_PERMISSION_MODES,
  ...(feature('TRANSCRIPT_CLASSIFIER') ? (['auto'] as const) : ([] as const)),
] as const satisfies readonly PermissionMode[]
```

#### 3.1.4 模式切换机制

用户可以通过 `Shift+Tab` 在模式之间循环切换。切换顺序**不是简单的线性**，而是根据用户类型和可用性动态决定：

```
外部用户典型路径: default → acceptEdits → plan → [bypassPermissions →] default
内部用户简化路径: default → bypassPermissions → auto → default
```

#### 3.1.5 模式谱系图

```
严格 ◄──────────────────────────────────────────► 宽松

  default      plan       acceptEdits    bypassPermissions
  逐次确认     只读为主     自动编辑        完全跳过
  每次都问     写入被deny   项目内文件编辑   除deny/safetyCheck外
                          自动通过        全部自动放行

                    auto (内部)
                    AI分类器自动审批

  dontAsk (特殊)                   bubble (内部)
  不问直接拒绝                      子Agent权限冒泡
```

### 3.2 权限规则系统

权限模式是"粗粒度"的全局控制，而**规则系统提供了针对具体工具和操作的细粒度控制**。

#### 3.2.1 规则数据结构

每条权限规则由三个部分组成：

```typescript
// types/permissions.ts:75-79
export type PermissionRule = {
  source: PermissionRuleSource   // 规则来自哪里
  ruleBehavior: PermissionBehavior // allow | deny | ask
  ruleValue: PermissionRuleValue   // 匹配哪个工具/操作
}

// types/permissions.ts:67-70
export type PermissionRuleValue = {
  toolName: string       // 工具名称，如 "Bash", "FileEdit", "mcp__server1"
  ruleContent?: string   // 可选的内容匹配，如 "npm install", "python:*"
}
```

#### 3.2.2 三种规则行为

| 行为 | 含义 | bypass模式下是否生效 |
|------|------|-------------------|
| `allow` | 匹配的操作自动批准 | 是（直接放行） |
| `deny` | 匹配的操作直接拒绝，用户无法覆盖 | **是（deny 优先于 bypass）** |
| `ask` | 匹配的操作强制弹出确认对话框 | **是（即使 bypass 也要确认）** |

> **关键设计**：`ask` 规则的存在是一个重要的安全设计——即使你对大多数操作使用 bypass 模式，也可以对特定高危操作（如 `npm publish`、`git push --force`）设置 ask 规则作为安全阀。

#### 3.2.3 八种规则来源与优先级

```typescript
// permissions.ts:109-114
const PERMISSION_RULE_SOURCES = [
  ...SETTING_SOURCES,  // userSettings, projectSettings, localSettings,
                       // flagSettings, policySettings（后覆盖前）
  'cliArg',            // 命令行参数 --allowedTools
  'command',           // 斜杠命令设置
  'session',           // 当前会话中用户的临时授权
] as const
```

优先级从低到高：

```
userSettings → projectSettings → localSettings → flagSettings → policySettings → cliArg → command → session
     ↑ 最低                                                                              最高 ↑
```

**企业管控**：`policySettings`（企业策略）优先级高于用户个人设置，管理员可以通过 MDM 下发强制规则，用户无法覆盖。通过 `allowManagedPermissionRulesOnly` 选项可以限制用户只能使用管理策略定义的规则。

#### 3.2.4 规则存储格式

规则存储在 `settings.json` 文件中，格式是 `ToolName(ruleContent)`：

```json
{
  "permissions": {
    "allow": [
      "Bash(npm install:*)",    // 前缀匹配
      "Bash(git status)",       // 精确匹配
      "FileEdit",               // 整工具级别
      "mcp__server1"            // MCP 服务器级匹配
    ],
    "deny": [
      "Bash(rm -rf:*)",         // 前缀匹配
      "Bash(curl:*)"
    ],
    "ask": [
      "Bash(npm publish:*)"     // 发布时必须确认
    ]
  }
}
```

#### 3.2.5 Shell 命令的三种匹配模式

Bash 工具的权限规则支持三种匹配方式：

```typescript
// utils/permissions/shellRuleMatching.ts:25-37
export type ShellPermissionRule =
  | { type: 'exact'; command: string }     // 精确匹配: "git status"
  | { type: 'prefix'; prefix: string }     // 前缀匹配: "npm:*"（传统语法）
  | { type: 'wildcard'; pattern: string }  // 通配符匹配: "git *"
```

| 规则示例 | 匹配类型 | 匹配范围 |
|---------|---------|---------|
| `Bash(npm test)` | 精确 | 仅匹配 `npm test` |
| `Bash(npm:*)` | 前缀 | 匹配 `npm`、`npm install`、`npm run build` 等 |
| `Bash(git *)` | 通配符 | 匹配 `git commit`、`git push` 等，**也匹配裸 `git`** |

精巧细节：当模式以 ` *`（空格+通配符）结尾且只有一个通配符时，尾部空格和参数变为可选——`git *` 同时匹配 `git add` 和裸 `git`：

```typescript
// utils/permissions/shellRuleMatching.ts:90-154
if (regexPattern.endsWith(' .*') && unescapedStarCount === 1) {
  regexPattern = regexPattern.slice(0, -3) + '( .*)?'
}
```

### 3.3 决策管线（Permission Pipeline）

这是权限系统的**核心**——每次模型请求使用工具时，都会经过 `hasPermissionsToUseTool()` 函数的完整判定管线。

#### 3.3.1 决策结果类型

管线返回三种可能的决策，加上工具内部的 `passthrough`：

```typescript
// types/permissions.ts:241-246
export type PermissionDecision =
  | PermissionAllowDecision  // behavior: 'allow' — 允许执行
  | PermissionAskDecision    // behavior: 'ask'   — 需要用户确认
  | PermissionDenyDecision   // behavior: 'deny'  — 直接拒绝

// 工具内部还可以返回 passthrough
export type PermissionResult =
  | PermissionDecision
  | { behavior: 'passthrough'; message: string; ... }
```

> **`passthrough` 的设计意义**：表示"我没有意见，交给后续阶段决定"。如果后续的 allow 规则匹配了，passthrough 会被覆盖为 allow；但 `ask` 则不会被覆盖。这个细微的区别在特定场景下会产生不同的行为。

#### 3.3.2 四阶段管线（宏观视角）

```
阶段一：validateInput        → Zod Schema 验证输入合法性
         ↓
阶段二：规则匹配               → deny > ask > allow 优先级铁律
         ↓
阶段三：checkPermissions      → 工具特定的上下文评估
         ↓
阶段四：交互式提示              → Hook → 分类器 → 用户 多决策者竞争
```

#### 3.3.3 内层决策管线（7 步详解）

`hasPermissionsToUseToolInner()` 是权限检查的核心，按照严格的优先级顺序执行：

```
┌──────────────────────────────────────────────────────────┐
│                    阶段 1：规则检查                         │
│  (deny > ask > 工具内部 > safety)                          │
│                                                           │
│  1a. 整工具被 deny？     ──是──→ ❌ 拒绝（规则来源）        │
│       │否                                                  │
│  1b. 整工具被 ask？      ──是且无沙箱豁免──→ ⏸ 需确认       │
│       │否或可沙箱豁免                                       │
│  1c. 调用 tool.checkPermissions()                          │
│       │                                                    │
│  1d. 工具返回 deny？     ──是──→ ❌ 拒绝（工具实现）        │
│       │否                                                  │
│  1e. 需要用户交互？      ──是且ask──→ ⏸ 需确认（bypass免疫） │
│       │否                                                  │
│  1f. 内容级 ask 规则？   ──是──→ ⏸ 需确认（bypass免疫）     │
│       │否                                                  │
│  1g. Safety Check 触发？ ──是──→ ⏸ 需确认（bypass免疫）     │
│       │否                                                  │
├──────────────────────────────────────────────────────────┤
│                    阶段 2：模式检查                         │
│                                                           │
│  2a. bypassPermissions？ ──是──→ ✅ 允许（模式豁免）        │
│       │否                                                  │
│  2b. 整工具被 allow？    ──是──→ ✅ 允许（规则来源）        │
│       │否                                                  │
├──────────────────────────────────────────────────────────┤
│                    阶段 3：默认 → ask                       │
│                                                           │
│  passthrough → ask      ──────→ ⏸ 需确认                  │
└──────────────────────────────────────────────────────────┘
```

对应的核心代码（简化版）：

```typescript
// permissions.ts:1158-1319
async function hasPermissionsToUseToolInner(
  tool, input, context,
): Promise<PermissionDecision> {
  let appState = context.getAppState()

  // === 阶段 1：规则检查 ===
  
  // 1a. 整工具被 deny 规则封禁
  const denyRule = getDenyRuleForTool(appState.toolPermissionContext, tool)
  if (denyRule) return { behavior: 'deny', /* ... */ }

  // 1b. 整工具被 ask 规则标记
  const askRule = getAskRuleForTool(appState.toolPermissionContext, tool)
  if (askRule) {
    // 特殊处理：沙箱模式下的 Bash 可以跳过
    const canSandboxAutoAllow = tool.name === BASH_TOOL_NAME
      && SandboxManager.isSandboxingEnabled()
      && SandboxManager.isAutoAllowBashIfSandboxedEnabled()
      && shouldUseSandbox(input)
    if (!canSandboxAutoAllow) return { behavior: 'ask', /* ... */ }
  }

  // 1c. 委托工具实现检查
  let toolPermissionResult: PermissionResult = { behavior: 'passthrough' }
  try {
    const parsedInput = tool.inputSchema.parse(input)
    toolPermissionResult = await tool.checkPermissions(parsedInput, context)
  } catch (e) { /* ... */ }

  // 1d. 工具实现返回 deny
  if (toolPermissionResult?.behavior === 'deny') return toolPermissionResult

  // 1e. 工具需要用户交互（即使 bypass 模式也不跳过）
  if (tool.requiresUserInteraction?.() && toolPermissionResult?.behavior === 'ask') {
    return toolPermissionResult
  }

  // 1f. 内容级 ask 规则，bypass 模式也不跳过
  if (toolPermissionResult?.behavior === 'ask'
    && toolPermissionResult.decisionReason?.type === 'rule'
    && toolPermissionResult.decisionReason.rule.ruleBehavior === 'ask') {
    return toolPermissionResult
  }

  // 1g. Safety check — 写入 .git/、.claude/ 等危险路径
  if (toolPermissionResult?.behavior === 'ask'
    && toolPermissionResult.decisionReason?.type === 'safetyCheck') {
    return toolPermissionResult
  }

  // === 阶段 2：模式检查 ===
  appState = context.getAppState() // 重新获取最新状态！

  // 2a. bypassPermissions 模式
  const shouldBypassPermissions =
    appState.toolPermissionContext.mode === 'bypassPermissions'
    || (appState.toolPermissionContext.mode === 'plan'
      && appState.toolPermissionContext.isBypassPermissionsModeAvailable)
  if (shouldBypassPermissions) return { behavior: 'allow', /* ... */ }

  // 2b. 整工具被 allow 规则覆盖
  const alwaysAllowedRule = toolAlwaysAllowedRule(appState.toolPermissionContext, tool)
  if (alwaysAllowedRule) return { behavior: 'allow', /* ... */ }

  // === 阶段 3：默认 → ask ===
  return toolPermissionResult.behavior === 'passthrough'
    ? { ...toolPermissionResult, behavior: 'ask' }
    : toolPermissionResult
}
```

**关键设计决策**：步骤 1f 和 1g 在步骤 2a（bypass 检查）**之前**。这意味着：
- 用户显式配置的 ask 规则，即使在 bypass 模式下也会触发确认
- Safety check（保护 `.git/`、`.claude/` 等），在 bypass 模式下也不会被跳过

> 这是"防御纵深"的设计——bypass 模式跳过的是通用的"未配置规则时的默认 ask"，而不是用户刻意设置的安全屏障。

#### 3.3.4 外层包装：模式级变换

`hasPermissionsToUseTool()` 是外层包装，对内层返回的 ask 决策进行模式级变换：

### 3.5 文件系统路径验证

#### 3.5.1 `isPathAllowed()` 的五步验证

```typescript
// utils/permissions/pathValidation.ts:141-263（简化版）
export function isPathAllowed(resolvedPath, context, operationType): PathCheckResult {
  // 1. Deny 规则优先（最高优先级）
  const denyRule = matchingRuleForInput(resolvedPath, context, 'deny')
  if (denyRule) return { allowed: false, decisionReason: { type: 'rule', rule: denyRule } }

  // 2. 内部可编辑路径（plan 文件、scratchpad、agent memory）
  if (operationType !== 'read') {
    const internalEditResult = checkEditableInternalPath(resolvedPath, {})
    if (internalEditResult.behavior === 'allow') return { allowed: true }
  }

  // 2.5. 写操作安全检查（Windows 路径、Claude 配置文件、危险文件）
  if (operationType !== 'read') {
    const safetyCheck = checkPathSafetyForAutoEdit(resolvedPath, ...)
    if (!safetyCheck.safe) return { allowed: false }
  }

  // 3. 工作目录检查
  if (pathInAllowedWorkingPath(resolvedPath, context, ...)) {
    if (operationType === 'read' || context.mode === 'acceptEdits') {
      return { allowed: true }
    }
  }

  // 4. Allow 规则
  const allowRule = matchingRuleForInput(resolvedPath, context, 'allow')
  if (allowRule) return { allowed: true }

  // 5. 默认拒绝
  return { allowed: false }
}
```

#### 3.5.2 防止 TOCTOU 攻击

`validatePath()` 在路径验证前做多项安全检查，防止 shell 展开与验证之间的 TOCTOU（Time-of-Check to Time-of-Use）漏洞：

```typescript
export function validatePath(path, cwd, toolPermissionContext, operationType) {
  const cleanPath = expandTilde(path.replace(/^['"]|['"]$/g, ''))

  // SECURITY: 阻止 UNC 路径（可能泄漏凭证）
  if (containsVulnerableUncPath(cleanPath))
    return { allowed: false, reason: 'UNC network paths require manual approval' }

  // SECURITY: 拒绝 ~user、~+、~- 等 tilde 变体
  if (cleanPath.startsWith('~'))
    return { allowed: false, reason: 'Tilde expansion variants require manual approval' }

  // SECURITY: 拒绝包含 shell 展开语法的路径
  // $VAR, ${VAR}, $(cmd), %VAR% 在验证时是字面量，但 shell 执行时会展开
  if (cleanPath.includes('$') || cleanPath.includes('%') || cleanPath.startsWith('='))
    return { allowed: false, reason: 'Shell expansion syntax requires manual approval' }

  // SECURITY: 写操作不允许 glob 模式
  if (GLOB_PATTERN_REGEX.test(cleanPath) && (operationType === 'write' || 'create'))
    return { allowed: false, reason: 'Glob patterns are not allowed in write operations' }
}
```

### 3.6 Bash 命令多层安全验证

BashTool 是攻击面最大的工具，因此有独立的多层安全验证体系。

#### 3.6.1 tree-sitter AST 安全解析

**核心设计原则：FAIL-CLOSED**——不理解的结构一律不信任：

```typescript
// ast.ts 核心设计注释：
// "The key design property is FAIL-CLOSED: we never interpret structure we
//  don't understand. If tree-sitter produces a node we haven't explicitly
//  allowlisted, we refuse to extract argv and the caller must ask the user."
```

解析结果三选一：

| 结果 | 含义 | 后续处理 |
|------|------|---------|
| `simple` | 成功提取了干净的 argv[]，所有引号已解析 | 继续正常的权限规则匹配 |
| `too-complex` | 发现了无法静态分析的结构 | 检查 deny 规则后要求用户确认 |
| `parse-unavailable` | tree-sitter WASM 未加载 | 回退到 legacy 解析路径 |

白名单非常保守——只有 4 种结构节点会被递归遍历：

```typescript
const STRUCTURAL_TYPES = new Set([
  'program',              // 根节点
  'list',                 // a && b || c
  'pipeline',             // a | b
  'redirected_statement', // 带重定向的命令
])
```

以下结构都会被标记为 `too-complex`，需要用户确认：
- 命令替换 `$(cmd)` 或 `` `cmd` ``
- 变量展开 `${var}`
- 控制流 `if/for/while/case`
- 函数定义
- 进程替换 `<(cmd)` / `>(cmd)`

#### 3.6.2 23 项静态安全验证器

每一项针对特定的攻击向量，**各自独立、任一触发即拒绝**：

| ID | 检查项 | 防护目标 | 攻击示例 |
|----|--------|---------|---------|
| 1 | 不完整命令 | 防止注入续行 | 以 tab/flag/操作符开头的命令 |
| 2 | jq 系统函数 | 防止 jq 命令注入 | `jq 'system("rm -rf /")'` |
| 6 | 危险变量 | 防止环境变量注入 | `LD_PRELOAD=/evil.so cmd` |
| 7 | 换行符 | 防止多行注入 | 嵌入换行符隐藏第二条命令 |
| 8 | 命令替换 | 防止命令替换 | `echo $(rm -rf /)` |
| 10 | 输出重定向 | 防止输出劫持 | `cmd > ~/.bashrc` |
| 13 | /proc/environ | 防止环境泄露 | 读取 API keys |

#### 3.6.3 环境变量安全处理

```
安全变量白名单（权限匹配前被剥离）：
  NODE_ENV, RUST_LOG, TERM, NO_COLOR, TZ, LANG 等
  → 只影响程序行为，不影响代码执行

危险变量黑名单（绝不会被剥离）：
  PATH, LD_PRELOAD, NODE_OPTIONS, PYTHONPATH, BASH_ENV 等
  → 能影响代码执行或库加载
```

设计原则：**如果一个变量能影响代码执行或库加载，就不能剥离。宁可误报（安全的命令需要确认）也不能漏报（危险的命令被自动允许）。**

// createResolveOnce：确保只有第一个决定生效
function createResolveOnce<T>() {
  let resolved = false
  let resolve: (value: T) => void
  const promise = new Promise<T>(r => { resolve = r })
  return {
    promise,
    resolve: (value: T) => {
      if (resolved) return  // 后续决定被丢弃
      resolved = true
      resolve(value)
    }
  }
}

### 模式 1：纵深防御（Defense in Depth）

```
推荐做法:
  不要依赖单一权限检查，构建多层串联的管线
  每层有自己的职责：deny规则 → 工具内部检查 → safety check → 模式检查 → allow规则
  某些层在高信任模式下仍然生效（bypass-immune）

代码骨架:
  async function checkPermission(tool, input, context) {
    // Layer 1: 硬性拒绝规则（不可绕过）
    if (matchesDenyRule(tool, input)) return DENY
    
    // Layer 2: 工具自身的安全检查（不可绕过）
    const toolResult = await tool.checkSafety(input)
    if (toolResult === DENY) return DENY
    if (toolResult === ASK_BYPASS_IMMUNE) return ASK  // 即使 bypass 也要确认
    
    // Layer 3: 信任模式检查
    if (mode === 'bypass') return ALLOW
    
    // Layer 4: 允许规则
    if (matchesAllowRule(tool, input)) return ALLOW
    
    // Layer 5: 默认 → 请求确认
    return ASK
  }
```

### 模式 2：渐进式信任 + 快速通道

```
推荐做法:
  将判断成本与风险级别对齐
  低风险操作用规则快速放行
  高风险操作才动用昂贵的推理资源（如 AI Classifier）

实现建议:
  1. 维护一个安全工具白名单（只读工具直接放行）
  2. 在调用 AI 判断前，先用便宜的规则匹配过滤
  3. 为 AI 判断设置超时，超时后降级到人工确认
```

### 模式 3：连续拒绝熔断

```
推荐做法:
  当自动决策连续失败时，不应该无限重试
  有人在时：降级到人工干预
  无人在时：果断中止

实现建议:
  const LIMITS = { maxConsecutive: 3, maxTotal: 20 }
  
  if (consecutiveDenials >= LIMITS.maxConsecutive) {
    if (isInteractive) fallbackToUserPrompt()
    else abortAgent()
  }
```

### 模式 4：不可变权限上下文

```
推荐做法:
  每次权限更新产生新的上下文对象，而非修改现有对象
  确保并发环境下多个工具同时检查权限时的一致性

实现:
  // ❌ 不要这样做
  context.rules.push(newRule)
  
  // ✅ 应该这样做
  const newContext = { ...context, rules: [...context.rules, newRule] }
```

### 模式 5：多来源规则合并与企业管控

```
推荐做法:
  支持多层配置来源（全局 → 项目 → 本地 → 会话）
  企业策略优先级最高，用户无法覆盖
  deny 始终优先于 allow，无论来源如何

配置层级:
  企业策略 (MDM下发) > 用户全局 > 项目级 > 本地 > 会话级
```

### 模式 6：权限解释器

```
推荐做法:
  在确认对话框中提供 AI 生成的风险解释
  包含：操作说明、执行理由、潜在风险、风险等级

效果:
  用户不是面对一个裸命令凭直觉判断
  而是获得充分的上下文信息来做决策
```

### 模式 7：Hook 扩展点

```
推荐做法:
  提供可编程的权限决策扩展点
  让企业用户可以接入内部审批系统、Slack通知等

Hook 能力:
  - 做出 allow/deny 决策
  - 修改工具输入
  - 动态注入权限规则
  - 中断整个操作链（interrupt）
```

## 六、总结速记表

### A. 权限模式速记

| 模式 | 一句话 | 安全级别 | 场景 |
|------|--------|---------|------|
| `default` | 不确定就问我 | ★★★★★ | 日常使用 |
| `plan` | 只许看不许改 | ★★★★☆ | 代码审查 |
| `acceptEdits` | 改文件可以，其他问我 | ★★★☆☆ | 信任项目 |
| `dontAsk` | 不确定就拒绝 | ★★★★★ | CI/CD |
| `bypassPermissions` | 都放过（除了铁律） | ★☆☆☆☆ | 完全信任 |
| `auto` | 让 AI 替我判断 | ★★★☆☆ | 内部 |
| `bubble` | 交给上级决定 | - | 子Agent |

### B. 决策管线速记

```
deny规则 → ask规则 → 工具checkPermissions → safety check → bypass模式 → allow规则 → 默认ask
 ❌拒绝    ⏸确认        ❌/⏸/✅/穿透      ⏸确认(免疫)    ✅允许       ✅允许       ⏸确认
```

### C. 规则优先级铁律

```
deny > ask > allow    (行为优先级)
session > command > cliArg > policy > flag > local > project > user    (来源优先级)
```

### D. Bypass-Immune 检查清单

即使在 `bypassPermissions` 模式下也**不会被跳过**的检查：

| 检查类型 | 示例 |
|---------|------|
| deny 规则 | `Bash(rm -rf:*)` |
| 用户显式 ask 规则 | `Bash(npm publish:*)` |
| Safety Check | 写入 `.git/`、`.claude/`、`.bashrc` |
| requiresUserInteraction | 需要用户交互的工具 |

### E. Bash 安全检查层次

```
Layer 1: tree-sitter AST 解析 (FAIL-CLOSED)
Layer 2: checkSemantics 语义检查 (eval, zmodload 等)
Layer 3: 精确/前缀/通配符规则匹配
Layer 4: 23项静态安全验证器
Layer 5: 路径约束验证
Layer 6: 环境变量安全处理
```

### F. 关键设计原则总结表

| 原则 | 含义 | Claude Code 中的体现 |
|------|------|---------------------|
| 纵深防御 | 每一层都假设其他层可能失效 | 7 层安全架构，任一层可独立拦截 |
| 默认安全 | 未知的操作一律安全处理 | default 模式需确认，FAIL-CLOSED |
| deny 优先 | 拒绝的力量大于允许 | deny 在 allow 之前检查，不可覆盖 |
| 最小权限 | 只授予必要的权限 | 工作目录范围限制，沙箱隔离 |
| 可追踪 | 每次决策记录来源 | toolUseID + DecisionSource + 遥测 |
| 渐进式信任 | 检查成本与风险对齐 | 快速通道 → 规则 → AI → 人工 |
| 优雅降级 | 自动化失败时有退路 | 熔断器 + fallback to prompting |
| 人类优先 | 人的意图永远高于机器 | userInteracted 标志 + 200ms 宽限 |

---

> **总结**：Claude Code 的权限系统代表了当前 AI Agent 权限控制的最高工程水准。它的核心哲学——**"每一层都假设其他层可能失效"**——是构建安全关键系统的根本方法论。对于任何正在构建 Agent 系统的团队，Claude Code 的多层防御、渐进信任、熔断降级等设计模式都是极具参考价值的实践范例。
