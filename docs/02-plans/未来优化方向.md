# 未来优化方向

> 已讨论但暂不实施的事项。实施前先更新状态（移入正式计划或删除）。

## 多 Agent 演进（2026-09-02 讨论通过，暂缓）

> 详细调研与设计讨论见 `docs/01-research/多Agent架构调研与模式辨析-2026-09-02.md`。

按优先级，均待 trace 数据（agent_spawn 触发率）验证后决策：

1. **团队模式（Swarm 形态）**：星型委托 → 网状拓扑（成员互发消息）+
   成员持久化（可 respawn）+ 协作协议（关闭请求/计划审批）。
   参考 CC Agent Teams（JSONL 消息总线）与 CodeBuddy 团队模式。
   触发条件：星型委托被充分使用且出现"子任务间需互相沟通"的真实需求
2. **Fork 式缓存共享**：并行子 agent 共享 prompt cache 前缀降成本
   （CC 核心innovations，token 成本 -60%）。需先验证 DeepSeek 兼容模式
   是否支持
3. **工作量梯度引导**：委托指导加量化缩放（简单 1 个 / 中等 2-4 个 /
   复杂 10+，Anthropic 原则）
4. **子 agent 产出走文件引用**：普通模式委托让子 agent 写产物文件、
   只回传引用，防"传话游戏"信息损失（workflow 产物机制已这么做）
5. **REPL 空闲唤醒**：后台任务全部完成而主循环已退出时自动触发一轮
   处理结果（不改模式边界的等待缺口解法）

## 双层记忆制（2026-09-02 讨论通过，暂缓）

**问题**：当前 `MEMORY_DIR = WORKDIR/.xiaoagent/memory`，记忆完全按项目目录隔离。
用户在项目 A 说"我喜欢简洁回复"，换到项目 B 启动 agent 即"失忆"——
用户偏好、协作反馈这类跨项目有效的信息被错误地绑定在单个目录里。

**方案**：双层记忆注入与写入分流。

| 层 | 位置 | 存什么 |
|---|---|---|
| 全局层 | `~/.xiaoagent/memory/` | user 类型（身份/角色）、feedback 类型（协作偏好、纠正） |
| 项目层 | `{workdir}/.xiaoagent/memory/` | project 类型（决策、进度）、reference 类型（外部系统指针） |

- 注入：两份 `MEMORY.md` 索引都进 system prompt（分区标注 Global / Project）
- 写入分流：接在第一层写入引导上——`prompts/fragments/memory.md` 的
  When to Write 章节写明"user/feedback 写全局目录、project/reference 写项目目录"，
  LLM 端零额外机制（写入仍走 write_file/edit_file 工具）
- 参照：Claude Code 的 CLAUDE.md 用户级/项目级双文件结构

**前置依赖**：先用 `/stats` 的 `memory_write` 事件观察第一层写入引导的实际效果，
确认 LLM 确实在写记忆后再做分层（否则分层后写入率仍是 0，无意义）。

**涉及文件**（实施时）：`runtime/state.py`（全局 MEMORY_DIR）、
`services/memory.py`（双目录管理）、`services/permissions.py`（全局目录写入白名单）、
`prompts/fragments/memory.md`（写入分流规则）。
