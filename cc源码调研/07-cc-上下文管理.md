## 1. AI Agent 中上下文管理的含义、动机与必要性

### 1.1 什么是上下文管理

大语言模型（LLM）的一切推理能力都建立在一个前提之上——**上下文窗口（Context Window）**。上下文窗口是模型在一次推理中能够"看到"的全部信息总量，通常以 token 为单位衡量（Claude 当前最大约 200K token）。

在 AI Agent 系统中，上下文管理指的是：**系统性地决定在有限的上下文窗口中放入哪些信息、何时移除过时信息、以及如何在信息被移除后仍然保持 Agent 的工作连贯性。**

用一个直观的类比来理解：

> **上下文窗口就像一块有限大小的白板。** Agent 的所有工作记忆——对话历史、工具调用结果、中间推理——都必须写在这块白板上。白板空间用完时，你必须擦掉旧内容才能写新内容。关键问题是：**擦掉什么、保留什么、用什么方式擦？**

### 1.2 为什么上下文管理至关重要

**（1）LLM 的无状态本质**

LLM 本身是无状态的——每次 API 调用，模型都是从零开始。它没有跨请求的持久记忆，只能看到当前请求中携带的内容。因此，Agent 系统必须在每次 API 调用前，将模型需要的所有信息组装成一个完整的请求。

**（2）信息膨胀的必然性**

一次真实的编码会话，可能涉及几十次文件读取、数百次工具调用，产生的原始文本量轻松超过百万 token——远远超出上下文窗口的容量。以 Claude Code 为例，每一轮对话都需要将完整的消息历史（系统提示、用户消息、助手回复、工具调用与结果）打包发送给模型。随着对话推进，这个历史不可避免地膨胀，最终撞上模型上下文窗口的天花板。

**（3）取舍不当的严重后果**

如果上下文管理做得不好，会导致：
- 模型忘记刚才编辑了哪个文件
- 重复读取已经看过的内容
- 产生与之前决策矛盾的输出
- API 请求因超出窗口限制而直接报错（Prompt-Too-Long）

### 1.3 行业现状与 Claude Code 的差异化

许多 Agent 框架在上下文管理上选择了"暴力截断"——直接丢弃最早的消息。这种做法简单粗暴，容易导致关键信息丢失。

Claude Code 的做法**远比这精细**。它设计了一套**五级渐进式压缩策略**，从低成本到高成本依次递进，辅以断路器保护、精确的 Token 估算、以及压缩后的上下文恢复机制，构成了一个完整的"工作记忆管理系统"。

## 3. Token 估算机制

### 3.1 设计动机

上下文管理的一切决策都建立在一个基础问题上：**当前的 Token 用量是多少？** 只有精确知道当前用量，才能判断是否需要触发压缩、触发哪个级别的压缩。

但这里存在一个矛盾：
- **精确计算需要调用 API**（服务端有精确的 tokenizer），这会引入网络延迟
- **压缩决策需要实时做出**，不能等待 API 返回

Claude Code 通过一种**"锚点 + 增量估算"**的策略巧妙地解决了这个矛盾。

### 3.2 设计思路：锚点策略

核心思路可以用一个类比来理解：

> 假设你今早称了体重是 75 公斤，此后吃了一顿午饭。你不需要再次上秤——估计 75.5 公斤就足够好了。

`tokenCountWithEstimation()` 的"体重秤"是 API 返回的 `usage` 数据（服务端精确计算的 Token 数），"午饭"是此后新增的少量消息。

### 3.3 具体工作流程

`tokenCountWithEstimation()`（位于 `src/utils/tokens.ts`）是上下文大小估算的核心函数。其设计原则是**从不额外调用 API**。

```typescript
export function tokenCountWithEstimation(messages: readonly Message[]): number {
  // 步骤 1: 从消息末尾向前查找，找到最近一条有 API usage 数据的消息
  let i = messages.length - 1
  while (i >= 0) {
    const usage = getTokenUsage(messages[i])
    if (usage) {
      // 步骤 2: 向前跳过同一 API 响应的分裂记录（相同 message.id）
      //   并行工具调用可能将一个响应拆成多条消息
      const responseId = getAssistantMessageId(messages[i])
      if (responseId) {
        let j = i - 1
        while (j >= 0) {
          if (getAssistantMessageId(messages[j]) === responseId) {
            i = j // 锚定到同一响应的最早记录
          } else if (getAssistantMessageId(messages[j]) !== undefined) {
            break // 遇到不同的 API 响应，停止
          }
          j--
        }
      }
      // 步骤 3: 用 server 报告的 token 数作为锚点，加上后续消息的粗略估算
      return getTokenCountFromUsage(usage) +
             roughTokenCountEstimationForMessages(messages.slice(i + 1))
    }
    i--
  }
  // 步骤 4: 如果没有任何 usage 数据（如会话刚开始），完全靠字符串长度估算
  return roughTokenCountEstimationForMessages(messages)
}
```

算法的四个步骤：

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 从末尾向前查找 usage | 找到最近一次 API 返回的精确 Token 计数 |
| 2 | 处理分裂消息 | 并行工具调用可能把一个响应拆成多条消息，需要合并 |
| 3 | 锚点 + 增量 | 精确值 + 新消息的粗略估算（字符数 × 4/3） |
| 4 | 纯估算兜底 | 会话开始时没有 usage 数据，完全用字符长度估算 |

### 3.4 精度分析

**这种方法比完全靠客户端估算精确得多：**
- 纯客户端估算的误差可能高达 30%+
- 锚点策略的误差通常 < 5%

因为每次 API 响应都自带 `usage` 数据（包含 `input_tokens`、`output_tokens`、`cache_tokens`），这是服务端精确计算的结果。`tokenCountWithEstimation()` 把这个精确值作为锚点，只对锚点之后的新消息（通常只有几条工具结果）做粗略估算。

### 3.5 示例模拟

假设当前消息历史有 50 条消息：

```
消息 1-45: 历史消息
消息 46 (Assistant): API 返回 usage = { input_tokens: 150,000, output_tokens: 2,000 }
消息 47 (User): "请继续修改这个���件"
消息 48 (Tool Result): Read 工具返回了 200 行代码
消息 49 (User): "看起来不错"
消息 50 (Tool Result): Bash 工具返回了测试结果
```

估算过程：
1. 从消息 50 向前扫描，找到消息 46 有 usage 数据
2. 锚点值 = `input_tokens + output_tokens` = 152,000
3. 消息 47-50 的粗略估算 = 这些消息的字符总数 × 4/3 ≈ 3,000
4. **最终估算 ≈ 155,000 tokens**

这个值足以准确判断是否需要触发压缩。

## 4. 有效窗口与多级阈值体系

### 4.1 有效窗口公式

Claude Code 用一个精确的公式来刻画**真正可用于对话的空间**：

```
有效窗口 = 模型窗口 - 预留输出令牌
```

在 `getEffectiveContextWindowSize` 函数中：

```
预留空间 = min(模型最大输出令牌, 20,000)
有效窗口 = 模型窗口 - 预留空间
```

**为什么预留最多 20,000 令牌？**

因为 AutoCompact（最高级压缩）需要调用 LLM 生成摘要，摘要本身也消耗输出令牌。根据实际数据，p99.99 的压缩摘要输出为 17,387 tokens。如果不预留空间，压缩操作本身就可能因为输出空间不足而失败——这是一个经典的"压缩悖论"。

### 4.2 具体数字计算

假设模型上下文窗口为 200,000 令牌，最大输出令牌为 16,384：

```
预留空间 = min(16,384, 20,000) = 16,384 令牌
有效窗口 = 200,000 - 16,384 = 183,616 令牌
```

### 4.3 多级阈值体系

基于有效窗口，Claude Code 定义了多个关键阈值，形成一个**逐级收紧的安全网**：

```
  0%                    85%        90%        95%       100%
  ├─────────────────────┼──────────┼──────────┼─────────┤
  │     安全区域          │  警告区域  │  危险区域  │ 阻塞区域 │
  │     正常工作          │  WARNING  │ AUTOCOMP │ BLOCK   │
  │     无需干预          │  提醒用户  │ 自动压缩  │ 拒绝请求 │
  └─────────────────────┴──────────┴──────────┴─────────┘
```

| 常量 | 值 | 含义 | 设计意图 |
|------|------|------|---------|
| `AUTOCOMPACT_BUFFER_TOKENS` | 13,000 | 自动压缩触发缓冲区 | 在用尽空间前预留安全余量 |
| `WARNING_THRESHOLD_BUFFER_TOKENS` | 20,000 | 警告阈值缓冲区 | 早期预警，给用户留出反应时间 |
| `ERROR_THRESHOLD_BUFFER_TOKENS` | 20,000 | 错误阈值缓冲区 | 标记危险区域，触发更积极策略 |
| `MANUAL_COMPACT_BUFFER_TOKENS` | 3,000 | 手动压缩缓冲区 | 用户手动触发时的最小安全余量 |

### 4.4 多级警告状态

`calculateTokenWarningState` 函数计算当前令牌使用状态，返回多个布尔标志：

| 标志 | 触发条件 | UI 行为 |
|------|---------|--------|
| `isAboveWarningThreshold` | 令牌用量 >= 阈值 - 20,000 | 显示黄色警告 |
| `isAboveErrorThreshold` | 令牌用量 >= 阈值 - 20,000 | 显示红色警告 |
| `isAboveAutoCompactThreshold` | 令牌用量 >= 自动压缩阈值 | 触发自动压缩 |
| `isAtBlockingLimit` | 令牌用量 >= 有效窗口 - 3,000 | 阻止新请求 |

### 4.5 阈值计算示例

以 200K 上下文窗口 + 16K 最大输出的模型为例：

```
有效窗口          = 200,000 - 16,000 = 184,000
自动压缩阈值      = 184,000 - 13,000 = 171,000  (≈ 85.5%)
警告阈值          = 184,000 - 20,000 = 164,000  (≈ 82%)
阻塞限制          = 184,000 - 3,000  = 181,000  (≈ 90.5%)
```

## 5. 五级渐进式压缩策略

### 5.0 设计哲学

Claude Code 的上下文压缩采用**五级渐进式策略**，从低成本到高成本依次递进，每一级都在前一级不足以释放空间时才被激活。

这个设计哲学可以用一个类比来理解：

> **压缩策略就像衣物收纳。** 你不会一上来就把所有衣服扔掉（暴力截断），而是先把大件衣物压缩放好（Tool Result 裁剪），再收起不再穿的（Snip），再压缩换季衣物（MicroCompact），然后真空封存大件（Collapse），最后才做全面整理丢弃（AutoCompact）。

```
  Level 1          Level 2         Level 3          Level 4          Level 5
┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────────┐   ┌──────────┐
│Tool Result│──▶│  Snip    │──▶│  Micro   │──▶│   Context    │──▶│  Auto    │
│  裁剪     │   │  裁剪    │   │ Compact  │   │   Collapse   │   │ Compact  │
│          │   │          │   │  微压缩   │   │   折叠       │   │ 自动压缩  │
├──────────┤   ├──────────┤   ├──────────┤   ├──────────────┤   ├──────────┤
│ 无 LLM   │   │ 无 LLM   │   │ 无 LLM   │   │ 部分 LLM    │   │ 完整 LLM │
│ 成本 ≈ 0 │   │ 成本 ≈ 0 │   │ 成本极低  │   │ 成本中等     │   │ 成本高   │
│ 持久化    │   │ 标记清除  │   │ 时间触发  │   │ 投影式重构   │   │ 对话摘要  │
└──────────┘   └──────────┘   └──────────┘   └──────────────┘   └──────────┘
```

**为什么按此顺序执行？**

每一级都比前一级"更重"——消耗更多计算资源，或丢失更多上下文细节：

1. **Tool Result Budget 最先**：纯本地操作，不调用 API。大结果写入磁盘，上下文只保留预览。零延迟、零成本。
2. **Snip 释放最多**：直接从消息列表中移除冗余部分，释放大量 Token，可能使后续压缩不必要。
3. **Microcompact 成本极低**：清理旧工具结果，不调用 API，适合频繁执行。
4. **Context Collapse 在 Autocompact 之前**：折叠可能使 Token 使用量降到 Autocompact 阈值以下，从而阻止不必要的全量压缩——保留了更细粒度的上下文。
5. **Autocompact 作为最后手段**：需要 fork 一个子 Agent 调用 API 生成摘要，成本最高，且不可逆。

### 5.1 Level 1: Tool Result 预算裁剪

#### 设计动机

单次工具调用可能返回**巨大的结果**。例如，用 `FileReadTool` 读取一个万行文件，或用 `BashTool` 执行 `find` 命令获取数千个文件路径。如果把这些原始结果全部塞入上下文，几次工具调用就能耗尽窗口。

#### 设计思路

**核心思想：持久化而非截断。**

截断意味着数据永久丢失——如果模型后来需要查看完整输出（比如在第 500 行发现了 bug），它无法恢复。持久化则保留了完整数据，模型可以随时使用 Read 工具读取磁盘文件来获取完整内容。

#### 具体工作流程

`applyToolResultBudget()` 位于 `src/utils/toolResultStorage.ts`：

```
步骤 1: 检查工具结果大小
   ├─ 每个工具声明 maxResultSizeChars（默认 50,000 字符）
   ├─ 可通过 Feature Flag 按工具名覆盖阈值
   │
步骤 2: 如果超过阈值
   ├─ 将完整结果持久化到磁盘
   │   路径: {projectDir}/{sessionId}/tool-results/{tool_use_id}.{txt|json}
   │
   ├─ 上下文中替换为紧凑引用消息：
   │   ┌─────────────────────────────────────────────────────┐
   │   │ <persisted-output>                                   │
   │   │ Output too large (2.3 MB). Full output saved to:     │
   │   │ /tmp/.claude/session-xxx/tool-results/toolu_abc.txt  │
   │   │                                                      │
   │   │ Preview (first 2.0 KB):                              │
   │   │ [前 2000 字节的内容预览]                                │
   │   │ ...                                                   │
   │   │ </persisted-output>                                   │
   │   └─────────────────────────────────────────────────────┘
   │
步骤 3: 追踪替换状态（ContentReplacementState）
   └─ 确保会话恢复（resume）时做出完全相同的替换决策
```

#### 输入与输出

| 维度 | 说明 |
|------|------|
| **输入** | 原始消息列表，包含可能超大的工具结果 |
| **输出** | 处理后的消息列表，大结果被替换为磁盘引用 + 2KB 预览 |
| **成本** | 零 API 调用，仅磁盘 I/O |
| **信息损失** | 无（完整数据仍在磁盘上） |

#### 示例模拟

```
场景：用户让 Agent 执行 `cat large_file.py`，文件有 10,000 行代码

原始工具结果大小 = 约 300,000 字符 > 50,000 字符阈值

处理后：
  - 磁盘文件: /tmp/.claude/session-abc/tool-results/toolu_123.txt (300KB)
  - 上下文中: <persisted-output> 引用 + 前 2KB 预览
  - Token 节省: 约 100,000 tokens → 约 800 tokens（节省 99%+）
```

#### 这么设计的好处

1. **零成本**：纯本地操作，无 API 调用
2. **无损**：完整数据保留在磁盘，模型可随时取回
3. **2KB 预览**：给模型足够信息判断是否需要查看完整结果
4. **缓存稳定**：通过 `ContentReplacementState` 追踪，确保会话恢复时缓存一致

### 5.2 Level 2: History Snip（历史裁剪）

#### 设计动机

在长对话中，很多早期的工具结果已经不再有用了。例如，用户之前让 Agent 读取了 10 个文件来理解代码结构，分析完成后这些文件内容就不再需要了。但它们仍然占据着大量 Token 空间。

#### 设计思路

Snip 是最轻量的**用户可控**压缩手段。它不调用任何 LLM，而是直接清除旧的工具结果内容。

**关键设计智慧：为什么不直接删除消息，而是替换为标记文本？**

因为删除消息会破坏消息链的连续性——后续消息可能引用了前面的工具调用 ID（API 要求每个 `tool_use` 都有对应的 `tool_result`）。标记文本既释放了空间，又保持了消息结构完整。

#### 具体工作流程

`snipCompactIfNeeded()` 是 Feature-gated 功能（`HISTORY_SNIP`）：

```
步骤 1: 用户通过 Snip 工具标记不再需要的消息

步骤 2: 系统将工具调用结果替换为标记文本
   原始: { type: 'tool_result', content: '...10000行代码...' }
   替换: { type: 'tool_result', content: '[Old tool result content cleared]' }

步骤 3: 记录释放的令牌数（snipTokensFreed）

步骤 4: 将释放量传递给后续的 autocompact 阈值检查
   （修正 Token 计数，避免 autocompact 过早触发）
```

#### 输入与输出

| 维度 | 说明 |
|------|------|
| **输入** | 消息列表 + 被标记为 snip 的消息索引 |
| **输出** | 工具结果被替换为 `[Old tool result content cleared]` |
| **副产品** | `snipTokensFreed`：释放的 Token 数量 |
| **成本** | 零 LLM 调用，仅字符串替换 |

#### 示例模拟

```
场景：用户刚用 Read 工具读取了 10 个文件，每个文件 500 行代码

压缩前：
  消息 5: tool_result for Read(file1.py) = "...500行代码..."  (~2,000 tokens)
  消息 7: tool_result for Read(file2.py) = "...500行代码..."  (~2,000 tokens)
  ... (共 10 个文件)
  总计约 20,000 tokens

用户输入 /compact 或使用 Snip 工具后：
  消息 5: tool_result = "[Old tool result content cleared]"    (~10 tokens)
  消息 7: tool_result = "[Old tool result content cleared]"    (~10 tokens)
  ...
  总计约 100 tokens

snipTokensFreed ≈ 19,900 tokens
```

### 5.3 Level 3: MicroCompact（微压缩）

#### 设计动机

MicroCompact 解决的是一个与**缓存策略**深度耦合的问题。

Claude 的 API 支持**提示缓存（Prompt Caching）**——如果连续请求的前缀相同，缓存命中的部分可以大幅降低成本和延迟。但随着时间推移，缓存会过期（默认 5 分钟 TTL）。当缓存过期时，无论如何都需要重新发送完整内容。此时保留旧的工具结果只是徒增负载。

此外，在活跃对话中，工具结果也在不断累积。即使缓存没有过期，过多的旧工具结果也在消耗宝贵的上下文空间。

#### 设计思路：两条互斥路径

MicroCompact 有**两条完全不同的路径**，根据缓存状态选择。这是这个模块最精巧的设计：

```
                    ┌─ 缓存已过期？──┐
                    │                │
                   是               否
                    │                │
                    ▼                ▼
            路径 A: 基于时间    路径 B: 缓存编辑
            直接修改消息内容    通过 cache_edits API
            （缓存反正要重建）  （保持缓存热度）
```

#### 路径 A：基于时间的 MicroCompact（缓存已冷）

**触发条件：** 距上次 assistant 消息的时间间隔超过配置阈值（缓存已过期）。

**工作流程：**

```
步骤 1: 检查功能开关是否启用、消息来源是否为主线程

步骤 2: 计算距最后一次助手消息的时间间隔

步骤 3: 如果间隔超过配置的阈值（如 5 分钟），触发微压缩

步骤 4: 遍历所有消息，识别可压缩的工具类型：
   Read, Bash, Grep, Glob, WebSearch, WebFetch, Edit, Write

步骤 5: 保留最近 N 个可压缩工具结果（keepRecent，最小值 1）

步骤 6: 将其余工具结果内容全部替换为清除标记：
   return { ...block, content: '[Old tool result content cleared]' }
```

**为什么可以直接修改消息内容？** 因为缓存已经冷了，修改消息内容不会造成额外的缓存失效——缓存本来就需要重建。

#### 路径 B：缓存编辑 MicroCompact（缓存仍热）

**触发条件：** 缓存还没过期（用户一直在活跃对话），但可压缩的工具数量超过阈值。

**核心挑战：** 如果直接修改消息内容，会导致缓存键（cache key）变化，使 100K+ token 的缓存前缀全部失效，需要重新上传和计费。

**解决方案：完全不修改本地消息，使用 API 级的缓存编辑机制：**

```
步骤 1: 在工具结果块上添加 cache_reference 字段（= tool_use_id）
   让服务端能够定位缓存中的具体位置

步骤 2: 构造 cache_edits 块
   告诉服务端"删除这些 cache_reference 指向的内容"

步骤 3: 服务端在缓存中就地删除
   不需要客户端重新上传前缀

步骤 4: 已发出的 cache_edits 通过 pinCacheEdits() 保存
   在后续请求中按原始位置重新发送（维持缓存一致性）
```

```typescript
// 消息本身不变，编辑在 API 层发生
// cache_edits 块通过 consumePendingCacheEdits() 传递给 API 层
return { messages } // 原样返回！
```

#### 两条路径对比

| 维度 | 基于时间的 MC | 缓存编辑 MC |
|------|-------------|------------|
| **触发条件** | 时间间隔超过阈值（缓存冷） | 工具数量超过阈值（缓存热） |
| **操作方式** | 直接修改消息内容 | `cache_edits` API 块 |
| **对缓存的影响** | 缓存本来就要重建，无额外影响 | 保持缓存热度，避免重新上传 |
| **API 调用** | 零 | 零（编辑在下次正常请求中捎带） |
| **适用场景** | 用户回来后的首次请求 | 活跃对话中的持续清理 |
| **优先级** | 更高（互斥时优先执行） | 较低 |

#### 示例模拟

**场景 A（基于时间）：**
```
用户上午 10:00 进行了一系列文件读取操作
用户离开去开会
用户下午 2:00 回来继续对话

时间间隔 = 4 小时 >> 5 分钟缓存过期阈值

触发基于时间的 MicroCompact：
  - 保留最近 1 个工具结果
  - 清除其余所有旧工具结果
  - 缓存反正已过期，直接修改消息无额外成本
```

**场景 B（缓存编辑）：**
```
用户持续活跃对话，已执行了 50 次工具调用
每次请求间隔 < 5 分钟，缓存一直是热的

触发缓存编辑 MicroCompact：
  - 不修改本地消息（保持缓存键不变）
  - 通过 cache_edits 告诉服务端删除旧工具结果
  - 150K 的缓存前缀继续有效，节省大量重传成本
```

### 5.4 Level 4: Context Collapse（上下文折叠）

#### 设计动机

Context Collapse 代表了一种**不同的思维方式**——不是"空间不够了才压缩"，而是"在空间压力出现之前就主动重构"。这类似于操作系统的内存预取策略，在内存耗尽之前就开始整理碎片。

#### 设计思路：投影式只读视图

**关键特性：它不修改原始消息。** 它创建消息的折叠视图，将不重要的早期消息替换为摘要。

可以用数据库的 View 来类比：底层表（消息数组）的数据不变，但查询时（发送 API 请求时）看到的是一个过滤/转换后的视图。

```typescript
// src/query.ts — Context Collapse 是读时投影，不写原始消息
if (feature('CONTEXT_COLLAPSE') && contextCollapse) {
  const collapseResult = await contextCollapse.applyCollapsesIfNeeded(
    messagesForQuery, toolUseContext, querySource
  )
  messagesForQuery = collapseResult.messages
}
```

#### 具体工作流程

```
步骤 1: 在上下文使用率达到 ~90% 时，开始提交（commit）折叠操作

步骤 2: 选择性重构消息组
   - 分析哪些早期消息可以被摘要替代
   - 为这些消息生成摘要（可能需要 LLM 调用）
   - 摘要存储在独立的 collapse store 中

步骤 3: projectView() 在每次循环入口将折叠视图叠加到原始消息之上

步骤 4: 在 95% 利用率时阻止新的 spawn（fork 操作）

步骤 5: Collapse 模式会抑制 AutoCompact 的触发
   原因：两者在 93% 的临界点会产生竞争
```

#### Collapse vs AutoCompact 关键区别

| 特性 | Collapse | AutoCompact |
|------|----------|-------------|
| **触发时机** | 90% 利用率（主动） | 超过阈值（被动） |
| **压缩粒度** | 选择性重构消息组 | 全对话摘要 |
| **信息保留** | 更多原始细节 | 仅保留摘要 |
| **可逆性** | ✅ 可以回退（不修改原始消息） | ❌ 不可逆（原始消息被替换） |
| **与 Fork 的关系** | 阻止新 spawn（95%） | 不影响 spawn |

#### 这么设计的好处

1. **可逆性**：不修改原始消息，可以安全回退
2. **优先级高于 AutoCompact**：折叠可能使 Token 使用量降到 AutoCompact 阈值以下，避免不必要的全量压缩
3. **更细粒度**：选择性重构而非全量摘要，保留更多上下文细节

### 5.5 Level 5: AutoCompact（自动全量压缩）

#### 设计动机

AutoCompact 是最后的兜底手段——当以上四级都无法有效释放空间时，调用 LLM 对完整对话进行摘要。

这是最"昂贵"的操作：它需要一次额外的 API 调用来生成摘要，而且是**不可逆的**——原始消息被摘要替换后无法恢复。

#### 触发条件

`shouldAutoCompact()` 必须同时满足 **5 个条件**：

```typescript
// 1. 递归守卫：防止压缩 Agent 自己触发压缩（死循环）
querySource !== 'session_memory' && querySource !== 'compact'

// 2. 三重开关检查：任一禁用则不触发
isAutoCompactEnabled()
  // 检查 DISABLE_COMPACT 环境变量
  // 检查 DISABLE_AUTO_COMPACT 环境变量
  // 检查 userConfig.autoCompactEnabled 设置

// 3. 非 Reactive-only 模式

// 4. 非 Context-collapse 模式
// 当 CONTEXT_COLLAPSE 启用且活跃时，autocompact 被抑制

// 5. Token 阈值（含 snipTokensFreed 修正）
tokenCountWithEstimation(messages) - snipTokensFreed >=
  getAutoCompactThreshold(model)
```

#### 具体工作流程

```
                    AutoCompact 触发
                         │
                         ▼
               1. 执行 PreCompact 钩子
                  （用户可注入自定义压缩指令）
                         │
                         ▼
               2. 构建压缩提示
                  选择模板：BASE / PARTIAL / PARTIAL_UP_TO
                         │
                         ▼
               3. 流式生成摘要
                  通过 forked agent 或主线程调用 API
                  （子 Agent 最多运行 1 轮，无工具调用）
                         │
                         ▼
               4. prompt-too-long?
                 ┌──是──┤
                 │      └──否──┐
                 ▼              ▼
          截断最老的 API    5. 重建上下文
          轮次组并重试       CompactBoundaryMessage
          （最多 3 次）     + 摘要 + 附件 + 钩子结果
                              │
                              ▼
                    6. 执行 PostCompact 钩子
                              │
                              ▼
                     输出：CompactionResult
```

#### 压缩产物结构（CompactionResult）

```typescript
interface CompactionResult {
  boundaryMarker: CompactBoundaryMessage  // 压缩边界标记
  summaryMessages: Message[]              // 摘要消息
  attachments: Message[]                  // 重新注入的附件
  hookResults: Message[]                  // 钩子结果
  messagesToKeep?: Message[]              // 部分压缩时保留的消息
  preCompactTokenCount: number            // 压缩前 Token 数
  postCompactTokenCount: number           // 压缩后 Token 数
}
```

#### CompactBoundaryMessage（压缩边界标记）

每次压缩完成后，系统在消息流中插入一个 `CompactBoundaryMessage`，作为压缩前后的分界线：

```
压缩前的消息（已被摘要替代）
─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─  ← CompactBoundaryMessage
摘要消息
附件（恢复的文件等）
钩子结果
新的对话消息...
```

边界标记携带元数据：
- **触发类型**：手动 / 自动
- **压缩前令牌数**
- **压缩涉及的消息数量**
- **`logicalParentUuid`**：将边界标记与压缩前的最后一条消息关联，构建消息链的逻辑连续性

**边界标记的作用：** 使后续的压缩操作能够准确识别"哪些消息已被压缩过"，避免重复压缩已摘要的内容。

#### Prompt-Too-Long 重试机制

当对话已经极长时，发送完整消息让子 Agent 摘要的请求本身也可能触发 Prompt-Too-Long 错误。`truncateHeadForPTLRetry()` 通过按 API 轮次分组、从头部丢弃最旧的轮次来缩小压缩请求，最多重试 3 次。

#### 示例模拟

```
场景：长时间编码会话，Token 用量达到 172,000（超过 171,000 阈值）

1. 检查 5 个触发条件 → 全部满足

2. 执行 PreCompact 钩子
   用户之前配置了："特别保留与数据库 schema 相关的讨论"

3. 选择 BASE_COMPACT_PROMPT 模板（首次压缩，全量摘要）

4. Fork 子 Agent，发送当前所有消息 + 压缩提示
   子 Agent 生成摘要（详见第 6 节）

5. 重建上下文：
   - CompactBoundaryMessage（记录：从 172K tokens 压缩）
   - 摘要消息（约 3,000-5,000 tokens）
   - 恢复最近 5 个文件（约 25,000 tokens）
   - 恢复已加载的技能（约 10,000 tokens）

6. 压缩后 Token 数 ≈ 40,000（释放了 130,000+ tokens）
```

## 6. 压缩提示工程：双阶段输出结构

### 6.1 设计动机

压缩的质量直接取决于提示的设计。如果提示不够精确，摘要要么丢失关键信息，要么塞满了不必要的细节。

可以把压缩提示想象成给一位速记员的指令：你需要明确告诉她"记什么、不记什么、用什么格式记"。

### 6.2 三种压缩提示模板

Claude Code 定义了三种压缩提示模板，对应三种不同的压缩场景：

| 模板 | 场景 | 压缩范围 | 适用时机 |
|------|------|---------|---------|
| `BASE_COMPACT_PROMPT` | 全量对话摘要 | 从对话开始到当前的所有消息 | 常规自动压缩（首次） |
| `PARTIAL_COMPACT_PROMPT` (from) | 仅摘要最近的消息 | 从指定消息开始到当前 | 对话前半段已被压缩过 |
| `PARTIAL_COMPACT_UP_TO_PROMPT` (up_to) | 摘要指定消息之前的上下文 | 从对话开始到指定消息 | 保留最近完整消息 |

### 6.3 防工具调用前导指令

每个提示都包含一个关键的防工具调用前导指令：

```
CRITICAL: Respond with TEXT ONLY. Do NOT call any tools.
- Tool calls will be REJECTED and will waste your only turn — you will fail the task.
```

**为什么需要这个指令？** 因为压缩运行在受限的 forked agent 环境中（最多 1 轮），一个被拒绝的工具调用会直接导致空输出。在较新的自适应思考模型上，模型有时会无视较弱的限制而尝试工具调用。

**为什么压缩必须在受限环境中执行？** 因为压缩是对话历史的"重写"操作——如果在重写过程中又产生了新的对话历史，就会导致递归问题。限制为单轮、无工具调用，确保压缩是一个纯粹的"读取-摘要-输出"过程。

### 6.4 双阶段输出结构

这是 Claude Code 压缩提示工程中最精巧的设计。压缩提示要求模型输出两个 XML 块：

```
┌─────────────────────────────────────────────────┐
│                LLM 原始输出                       │
│                                                  │

│  │ - 识别用户意图、关键决策                       │  │
│  │ - 标注文件名、代码片段                         │  │
│  │ - 记录错误及修复、用户反馈                     │  │
│  │ </analysis>                                  │  │
│  │                 │                            │  │
│  │            ┌────▼────┐                       │  │

│  ┌────────────────────────────────────────────┐  │

```

#### `<summary>` 的 9 个标准化章节

| # | 部分 | 内容 |
|---|------|------|
| 1 | Primary Request | 用户的所有显式请求和意图 |
| 2 | Key Technical Concepts | 讨论的技术概念、框架 |
| 3 | Files and Code | 检查/修改/创建的文件及关键代码片段 |
| 4 | Errors and Fixes | 遇到的错误及修复方式，特别是用户反馈 |
| 5 | Problem Solving | 已解决的问题和进行中的排查 |
| 6 | All User Messages | 所有非工具结果的用户消息（原文） |
| 7 | Pending Tasks | 待完成的任务 |
| 8 | Current Work | 压缩前正在进行的工作（最详细） |
| 9 | Optional Next Step | 下一步计划（包含原始对话的直接引用） |

#### 后处理逻辑

`formatCompactSummary` 函数负责后处理：

```
步骤 1: 丢弃 <analysis> 块（思维草稿本）
步骤 2: 提取 <summary> 块的内容作为正式摘要
步骤 3: 将摘要包装为消息格式
```

### 6.5 为什么双阶段设计如此重要

这里存在一个矛盾：

- 如果**直接要求**模型输出摘要（无 analysis 阶段），模型往往会遗漏重要信息——因为它没有"思考"的空间
- 如果**保留 analysis** 在上下文中，又浪费了宝贵的令牌

双阶段设计完美地解决了这个矛盾：

> **思考是过程，摘要是结果。过程不计费，结果才计入上下文。**

这是经典的"链式思考草稿本"（Chain-of-Thought Scratchpad）技术——让模型先推理再总结，质量远超直接生成摘要，但推理过程本身如果保留在上下文中会浪费大量 Token。丢弃分析、保留结论，两全其美。

## 7. 断路器机制

### 7.1 设计动机

自动压缩并非总是成功。网络波动、API 错误或上下文本身的结构问题都可能导致压缩失败。如果盲目重试，系统会在每个轮次都发起注定失败的 API 调用，浪费大量资源。

**真实数据揭示的问题严重性：**

> 引入断路器前曾观察到 **1,279 个会话**出现 50 次以上的连续压缩失败（最高达 **3,272 次**），每天浪费约 **250K 次 API 调用**。

### 7.2 设计思路：经典断路器模式

Claude Code 引入了断路器（Circuit Breaker）机制：当连续失败次数达到 3 次（`MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES`）时，系统直接跳过后续的压缩尝试。

这是经典的分布式系统设计模式，通常用于防止级联失败。在 AI Agent 的上下文管理中应用这个模式，是一个很有洞察力的工程决策。

### 7.3 状态机设计

```
                    ┌────────────────────┐
                    │                    │
    系统启动 ───────▶│    CLOSED（闭合）   │◀──── 压缩成功
                    │    正常工作状态      │      （计数器重置为 0）
                    │    计数器 = 0       │
                    │                    │
                    └────────┬───────────┘
                             │
                        压缩失败
                      （计数器递增）
                             │
                             ▼
                    ┌────────────────────┐
                    │                    │
                    │   HALF_OPEN       │
                    │   半开状态         │
                    │   0 < 计数器 < 3   │
                    │                    │
                    └──┬────────────┬────┘
                       │            │
                  压缩成功     连续失败 >= 3 次
               （计数器重置 0）   （熔断）
                       │            │
                       ▼            ▼
              回到 CLOSED    ┌────────────────────┐
                            │                    │
                            │    OPEN（断开）     │──── 跳过压缩
                            │    熔断状态         │     （自循环）
                            │    不再尝试自动压缩  │
                            │                    │
                            └────────┬───────────┘
                                     │
                              新会话 / 手动压缩成功
                               （重置条件）
                                     │
                                     ▼
                              回到 CLOSED
```

### 7.4 具体工作流程

```
每次 AutoCompact 触发时：
│
├── 检查：连续失败计数 >= 3？
│   ├── 是 → 跳过压缩，直接返回
│   └── 否 → 尝试压缩
│
├── 压缩成功？
│   ├── 是 → 失败计数器重置为 0（回到 CLOSED 状态）
│   └── 否 → 失败计数器 += 1
│           ├── 如果计数器 >= 3 → 进入 OPEN 状态（熔断）
│           └── 如果计数器 < 3 → 保持 HALF_OPEN 状态
│
└── 向上层调用者传递失败计数
```

### 7.5 重置条件

断路器在以下情况下会重置：
- **新会话开始**：重新初始化所有状态
- **手动压缩成功**：用户手动触发 `/compact` 并成功完成
- **压缩成功**：在 HALF_OPEN 状态下，如果某次压缩意外成功

### 7.6 示例模拟

追踪以下事件序列中断路器状态的变化：

| 事件 | 操作 | consecutiveFailures | 断路器状态 | 是否尝试压缩 |
|------|------|---------------------|----------|-----------|
| 初始 | 系统启动 | 0 | CLOSED | - |
| 1 | 压缩成功 | 0 | CLOSED | ✅ |
| 2 | 压缩失败 | 1 | HALF_OPEN | ✅ |
| 3 | 压缩失败 | 2 | HALF_OPEN | ✅ |
| 4 | 压缩失败 | **3** | **OPEN** | ✅（这次是最后一次） |
| 5 | 下一轮 | 3 | OPEN | ❌ 跳过 |
| 6 | 下一轮 | 3 | OPEN | ❌ 跳过 |
| 7 | 用户手动 /compact 成功 | 0 | CLOSED | ✅（手动触发） |
| 8 | 正常压缩 | 0 | CLOSED | ✅ |

### 7.7 这么设计的好处

1. **防止资源浪费**：避免对注定失败的压缩操作进行无限重试
2. **防止雪崩效应**：在 API 不稳定时，不会因为大量失败重试而进一步加剧问题
3. **保留手动恢复路���**：用户仍然可以通过手动 `/compact` 尝试恢复
4. **数据驱动的阈值**：3 次的阈值来自真实数据分析，而不是拍脑袋

## 8. 压缩后恢复与预算控制

### 8.1 设计动机

AutoCompact 的风险是让模型"忘记"刚编辑的文件。如果压缩后不进行任何恢复操作，模型在下一轮可能会重复读取已经看过的文件，或者产生与之前决策矛盾的修改。

### 8.2 压缩后恢复机制

系统在压缩后自动执行 `runPostCompactCleanup()`：

```
                    压缩完成
                       │
                       ▼
            ┌──── 恢复操作 ────┐
            │                  │
     ┌──────┼──────┬───────┬──┴──────┐
     │      │      │       │         │
     ▼      ▼      ▼       ▼         ▼
  恢复最近  恢复已  重置     重新通告   恢复
  5个文件  调用技能 Collapse 延迟工具   Plan
  (每个    (<=25K          Agent列表  状态
  <=5K)    Token)          MCP指令
```

详细步骤：

| 步骤 | 操作 | 预算限制 |
|------|------|---------|
| 1 | 恢复最近 5 个文件 | 每个文件 ≤ 5,000 tokens |
| 2 | 恢复所有已激活的技能 | 总计 ≤ 25,000 tokens，每个技能 ≤ 5,000 |
| 3 | 重置 Context Collapse | 清除折叠状态 |
| 4 | 重新通告上下文增量 | 延迟工具、Agent 列表、MCP 指令 |
| 5 | 恢复 Plan 状态 | 如果当前有活跃计划 |

### 8.3 令牌预算控制

压缩完成后，系统并非简单地释放所有空间。压缩模块定义了**严格的令牌预算常量**：

| 常量 | 值 | 用途 |
|------|------|------|
| `POST_COMPACT_MAX_FILES_TO_RESTORE` | 5 | 最多恢复的文件数量 |
| `POST_COMPACT_TOKEN_BUDGET` | 50,000 | 总令牌预算上限 |
| `POST_COMPACT_MAX_TOKENS_PER_FILE` | 5,000 | 每个文件的令牌上限 |
| `POST_COMPACT_MAX_TOKENS_PER_SKILL` | 5,000 | 每个技能的令牌上限 |
| `POST_COMPACT_SKILLS_TOKEN_BUDGET` | 25,000 | 技能独立预算 |

**为什么需要这些预算限制？**

如果压缩后不加限制地恢复内容，可能导致"压缩-膨胀-再压缩"的恶性循环：

```
反模式：
  压缩：170K → 5K tokens
  恢复所有文件：5K → 160K tokens  ← 几乎回到压缩前！
  几轮对话后：160K → 170K tokens
  再次压缩...（恶性循环）

正确模式：
  压缩：170K → 5K tokens
  恢复（受预算限制）：5K → 40K tokens  ← 受控恢复
  有充足空间继续对话
```

### 8.4 真实令牌估算

`truePostCompactTokenCount` 是对压缩后上下文实际大小的估算，包括边界标记、摘要消息、附件和钩子结果的令牌总和。

如果压缩后的令牌数仍然超过自动压缩阈值，系统就知道压缩"白做了"——这种情况通常发生在对话结构极其复杂或摘要本身过长时。

## 10. 设计总结与启示

### 10.1 核心设计原则

| 原则 | 体现 |
|------|------|
| **渐进式升级** | 五级压缩从零成本裁剪到全量摘要，按需逐级升级 |
| **缓存感知** | MicroCompact 的双路径设计，根据缓存冷热选择不同策略 |
| **精度与延迟的平衡** | Token 估算的锚点策略，不调用 API 就能获得高精度估算 |
| **防御性编程** | 断路器防止级联失败，消息规范化修复各种异常 |
| **可逆性优先** | Context Collapse 不修改原始消息，Tool Result 持久化而非截断 |
| **预算控制** | 压缩后恢复有严格的令牌预算，防止恶性循环 |

### 10.2 关键设计决策及其背后的权衡

| 决策 | 选择 | 替代方案 | 权衡理由 |
|------|------|---------|---------|
| Token 估算 | 锚点 + 增量 | 每次调 API | 精度足够，零延迟 |
| 大结果处理 | 持久化到磁盘 | 简单截断 | 保留完整数据，模型可随时取回 |
| 消息清除 | 替换为标记文本 | 直接删除 | 保持消息链完整性 |
| 压缩执行 | Fork 子 Agent | 主线程调用 | 隔离副作用，限制为 1 轮无工具 |
| 摘要生成 | 双阶段输出 | 直接生成 | analysis 提升质量但不计入上下文 |
| 断路器阈值 | 3 次 | 更大/更小值 | 基于 1,279 个会话的真实数据 |
| Beta header | 粘性锁存 | 每次动态决定 | 牺牲灵活性，换取缓存稳定性 |

### 10.3 对 Agent 系统构建者的启示

1. **不要忽略上下文管理**：这不是"锦上添花"的功能，而是长对话 Agent 系统的核心工程挑战
2. **渐进式比暴力截断好得多**：先用廉价手段尝试，只在必要时动用重武器
3. **断路器是必须的**：没有断路器的系统在 API 不稳定时会陷入死循环
4. **缓存感知至关重要**：上下文管理策略必须考虑与提示缓存的交互
5. **压缩后恢复同样重要**：仅仅压缩是不够的，还需要智能地恢复关键上下文
6. **主动压缩优于被动压缩**：在工作关键节点手动触发压缩，比等待自动压缩能保留更多有价值的信息
7. **记忆系统是上下文的补充**：重要决策应保存为记忆文件，这样即使对话被压缩，关键信息也不会丢失

---

> **一句话总结：** Claude Code 的上下文管理系统将一个看似简单的"信息取舍"问题，升华为一个融合了分布式系统模式（断路器）、操作系统策略（内存预取）、编译器技术（投影式视图）和 NLP 技巧（Chain-of-Thought Scratchpad）的完整工程体系。它不仅解决了"白板写满了怎么办"的问题，还通过精细的预算控制和恢复机制，确保了 Agent 在超长对话中的工作连贯性。
