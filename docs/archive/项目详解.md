## 一、项目代码结构

```
coding agent/
├── main.py                  # 唯一入口：初始化所有模块 → 组装工具 → REPL + agent_loop
├── config.py                # 全局配置：路径常量、API 客户端、阈值参数
│
├── tools/                   # 工具层
│   ├── base.py              # 5 个基础工具函数（safe_path/bash/read/write/edit）
│   ├── definitions.py       # 23 个工具的 JSON Schema 定义（传给 LLM 的工具"菜单"）
│   └── registry.py          # 工具调度表 TOOL_HANDLERS（工具名 → 处理函数的映射）
│
├── planning/                # 规划层
│   ├── todo.py              # TodoManager：内存中的轻量待办清单
│   └── tasks.py             # TaskManager：基于文件的持久化任务系统（含依赖图）
│
├── context/                 # 上下文管理层
│   ├── compression.py       # 三层压缩策略（token 估算 / 微压缩 / 自动压缩）
│   └── skills.py            # SkillLoader：两层按需加载专业知识
│
├── agents/                  # Agent 层
│   ├── subagent.py          # 一次性子 Agent（上下文隔离，用完即弃）
│   └── team.py              # TeammateManager：持久化队友（工作-空闲-关闭生命周期）
│
├── communication/           # 通信层
│   ├── bus.py               # MessageBus：基于 JSONL 文件的消息总线
│   └── protocols.py         # 关闭协议 + 计划审批协议（request_id 握手）
│
├── background/              # 后台执行层
│   └── manager.py           # BackgroundManager：异步后台命令执行 + 通知队列
│
├── .env.example             # 环境变量模板
├── requirements.txt         # Python 依赖
└── README.md                # 项目说明
```

**依赖关系（从底层到上层）**：

```
config.py           ← 所有模块的叶子依赖，不导入任何项目内模块
    ↑
tools/base.py       ← 只依赖 config
    ↑
planning/           ← 只依赖 config
context/            ← 只依赖 config
background/         ← 只依赖 config
communication/      ← 只依赖 config
    ↑
agents/subagent.py  ← 依赖 config + tools/base
agents/team.py      ← 依赖 config + tools/base（通过构造函数注入 bus、task_mgr）
    ↑
tools/registry.py   ← 通过依赖注入接收所有单例，延迟导入 agents + communication
    ↑
main.py             ← 顶层入口，创建所有单例，组装一切
```

**为什么这样拆分？** 原始的 `s_full.py` 把 741 行代码全放在一个文件里，虽然完整但难以维护和理解。拆分后：
- 每个文件职责单一，可以独立理解
- 通过依赖注入（`registry.py` 的 `get_tool_handlers(todo, skills, task_mgr, bg, bus, team)`）避免循环导入
- 新增工具只需修改 `definitions.py` + `registry.py`，不影响其他模块

### 完整工作流程（一次用户交互的全过程）

以用户输入 `"Create a hello.py file that prints hello world"` 为例：

**Step 1：REPL 接收输入** (`main.py:164-186`)

```python
# main.py
query = input("\033[36mcoding-agent >> \033[0m")  # 用户输入
history.append({"role": "user", "content": query})  # 加入历史
agent_loop(history)  # 进入主循环
```

此时 `history` 的内容：
```python
[{"role": "user", "content": "Create a hello.py file that prints hello world"}]
```

**Step 2：agent_loop 前置管道** (`main.py:67-93`)

```python
def agent_loop(messages: list):
    rounds_without_todo = 0
    while True:
        # (1) 微压缩：清除旧的工具结果（本例是第一轮，没有旧结果，跳过）
        microcompact(messages)

        # (2) 自动压缩：检查 token 量（本例远未超阈值，跳过）
        if estimate_tokens(messages) > TOKEN_THRESHOLD:
            messages[:] = auto_compact(messages)

        # (3) 后台通知：获取已完成的后台任务（本例没有后台任务，跳过）
        notifs = BG.drain()

        # (4) 收件箱：检查 lead 的消息（本例没有消息，跳过）
        inbox = BUS.read_inbox("lead")
```

**Step 3：调用 LLM** (`main.py:96-107`)

```python
        response = client.messages.create(
            model=MODEL,           # 如 "claude-sonnet-4-6"
            system=SYSTEM,         # 系统提示词（告诉 LLM 你是 coding agent）
            messages=messages,     # 对话历史
            tools=TOOLS,           # 23 个工具的 JSON Schema 定义
            max_tokens=8000,
        )
        messages.append({"role": "assistant", "content": response.content})

        if response.stop_reason != "tool_use":
            return  # LLM 没有要调用工具 → 直接返回最终回答
```

LLM 收到的完整输入：
- **system**: `"You are a coding agent at /path/to/workdir. Use tools to solve tasks..."`
- **messages**: `[{"role": "user", "content": "Create a hello.py file..."}]`
- **tools**: 23 个工具定义（bash, read_file, write_file, ...）

LLM 的响应（`response` 对象）：
```python
response.stop_reason = "tool_use"  # LLM 决定调用工具
response.content = [
    TextBlock(type="text", text="I'll create the file for you."),
    ToolUseBlock(
        type="tool_use",
        id="toolu_abc123",
        name="write_file",
        input={"path": "hello.py", "content": "print('hello world')"}
    )
]
```

**Step 4：执行工具** (`main.py:109-134`)

```python
        results = []
        for block in response.content:
            if block.type == "tool_use":       # 找到工具调用块
                handler = TOOL_HANDLERS.get(block.name)  # 查找处理函数
                output = handler(**block.input)  # 执行: run_write("hello.py", "print('hello world')")
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,   # 必须与 tool_use 的 id 对应
                    "content": str(output),      # "Wrote 20 bytes to hello.py"
                })
        messages.append({"role": "user", "content": results})
```

工具结果以 **user 角色**追加到消息历史（原因见下文"深入理解"部分）。

**Step 5：回到 while True 循环顶部**

带着工具结果再次调用 LLM。这次 LLM 看到文件已创建，不需要再调用工具：

```python
response.stop_reason = "end_turn"  # 不是 "tool_use"
response.content = [TextBlock(type="text", text="Done! I've created hello.py.")]
```

`response.stop_reason != "tool_use"` → `return`，agent_loop 结束。

**Step 6：REPL 输出** (`main.py:187-192`)

```python
response_content = history[-1]["content"]
if isinstance(response_content, list):
    for block in response_content:
        if hasattr(block, "text"):
            print(block.text)  # 输出: "Done! I've created hello.py."
```

## 三、深入理解：LLM 交互格式与工具调用机制

> 这一节回答你关于 `block.type`、`response.stop_reason`、工具调用流程、function calling 等一系列疑问。

### 3.1 block.type 和 response.stop_reason 是哪来的？

**它们是 Anthropic Python SDK 返回的对象属性**，不是我们自己定义的。

当你调用：
```python
client = Anthropic()
response = client.messages.create(model=..., messages=..., tools=...)
```

`response` 是 SDK 返回的 `Message` 对象，它的结构是 **Anthropic API 的标准响应格式**：

```python
# response 对象的关键属性
response.id            # "msg_01XFDUDYJgAACzvnptvVoYEL"
response.model         # "claude-sonnet-4-6"
response.stop_reason   # "end_turn" 或 "tool_use" 或 "max_tokens"
response.content       # 内容块列表 [TextBlock(...), ToolUseBlock(...), ...]
response.usage         # {"input_tokens": 1234, "output_tokens": 567}
```

`response.content` 是一个列表，每个元素是以下两种类型之一：

```python
# 类型 1：文本块
TextBlock(type="text", text="I'll help you create that file.")

# 类型 2：工具调用块
ToolUseBlock(type="tool_use", id="toolu_abc123", name="write_file",
             input={"path": "hello.py", "content": "print('hello')"})
```

所以 `block.type`、`block.name`、`block.id`、`block.input` 都是 SDK 对象的属性，由 Anthropic 的 API 规范定义。

### 3.2 `stop_reason` 的三种值

| stop_reason | 含义 | agent_loop 行为 |
|-------------|------|----------------|
| `"end_turn"` | LLM 认为回答完毕，主动结束 | 退出循环，返回最终回答 |
| `"tool_use"` | LLM 想要调用工具，暂停生成 | 执行工具，把结果喂回去，继续循环 |
| `"max_tokens"` | 达到 max_tokens 限制，被迫截断 | 也会退出循环（不等于 "tool_use"） |

### 3.3 关键误解澄清：stop_reason == "tool_use" 不是 agent_loop 结束的标志，恰恰相反！

你问："为什么 `stop_reason == 'tool_use'` 是 agent loop 结束的标志？"

**实际上恰好反过来！** 请仔细看代码逻辑：

```python
# main.py:106-107
if response.stop_reason != "tool_use":  # 注意这里是 != (不等于)
    return  # 只有【不是】tool_use 时才退出
```

**翻译成白话**：
- `stop_reason == "tool_use"` → **不退出**，继续循环（执行工具 → 喂回结果 → 再调 LLM）
- `stop_reason == "end_turn"` → **退出**，LLM 已经给出最终回答

**一轮 agent_loop 的定义**：从 `while True` 到下一次 `while True`（或 `return`）就是一轮。每一轮包含：
1. 前置管道（压缩、通知、收件箱）
2. 一次 LLM 调用
3. 如果 LLM 要调用工具 → 执行工具 → 回到步骤 1
4. 如果 LLM 不要调用工具 → 退出循环

一个用户请求可能触发多轮循环。比如"创建文件并验证"：
- 第 1 轮：LLM 调用 write_file → 继续
- 第 2 轮：LLM 调用 read_file 验证 → 继续
- 第 3 轮：LLM 回答"已创建并验证" → 退出

### 3.4 工具调用的完整内部流程

你问："LLM 如何判断是否要使用工具？如何调用工具？由谁执行工具？"

**完整流程如下**：

```
┌──────────────────────────────────────────────────────────────────┐
│  Step 1: 我们发送请求给 Anthropic API                            │
│                                                                    │
│  client.messages.create(                                           │
│      model="claude-sonnet-4-6",                                    │
│      system="You are a coding agent...",                           │
│      messages=[{"role": "user", "content": "Create hello.py"}],   │
│      tools=[{name: "write_file", description: "...", schema: ...}] │ ← 告诉 LLM 有哪些工具
│  )                                                                  │
└────────────────────────────────┬─────────────────────────────────┘
                                 │
                                 ▼
┌──────────────────────────────────────────────────────────────────┐
│  Step 2: LLM 内部决策（在 Anthropic 服务器上发生，我们看不到）      │
│                                                                    │
│  LLM 看到：                                                        │
│  - system: "你是一个 coding agent"                                  │
│  - user: "Create hello.py"                                         │
│  - 可用工具: [bash, read_file, write_file, edit_file, ...]        │
│                                                                    │
│  LLM 思考：要创建文件，我应该用 write_file 工具                     │
│                                                                    │
│  LLM 生成：                                                        │
│  - TextBlock: "I'll create that file."                             │
│  - ToolUseBlock: name="write_file", input={path, content}          │
│  - stop_reason 设为 "tool_use"（表示"我需要工具结果才能继续"）       │
└────────────────────────────────┬─────────────────────────────────┘
                                 │
                                 ▼
┌──────────────────────────────────────────────────────────────────┐
│  Step 3: 我们的代码接收响应，在本地执行工具                         │
│                                                                    │
│  for block in response.content:                                    │
│      if block.type == "tool_use":                                  │
│          handler = TOOL_HANDLERS[block.name]   # 找到 run_write    │
│          output = handler(**block.input)        # 本地执行文件写入  │
│          results.append({                                          │
│              "type": "tool_result",                                │
│              "tool_use_id": block.id,           # 关联到原始请求   │
│              "content": str(output)                                │
│          })                                                        │
└────────────────────────────────┬─────────────────────────────────┘
                                 │
                                 ▼
┌──────────────────────────────────────────────────────────────────┐
│  Step 4: 把工具结果以 user 角色喂回 LLM                           │
│                                                                    │
│  messages.append({"role": "user", "content": results})             │
│                                                                    │
│  然后回到 Step 1，再次调用 client.messages.create(...)             │
│  这次 LLM 看到了工具结果，可以继续推理                              │
└──────────────────────────────────────────────────────────────────┘
```

**关键点**：

1. **LLM 自己决定是否用工具**。我们只是告诉它"你有这些工具可用"（通过 `tools` 参数），LLM 根据任务需要自主判断。它是被训练过的，知道什么场景该调什么工具。

2. **LLM 不执行工具**。LLM 只是"请求"调用工具（输出 ToolUseBlock），实际执行发生在我们的 Python 代码中（`handler(**block.input)`）。LLM 生成的是"调用意图"，不是执行。

3. **工具结果以 user 角色返回**。这是 Anthropic API 的协议要求。消息历史必须是严格交替的 user → assistant → user → assistant 结构。工具结果属于"环境反馈"，在协议中归为 user 角色。

4. **不是 system 角色产生工具调用**。system 角色只是设定 LLM 的行为规范。产生工具调用的是 **assistant 角色**（LLM 的输出）。执行工具并返回结果的是 **user 角色**（我们的代码注入的 tool_result）。

### 3.5 LLM 到底是如何学会使用工具的？（训练原理）

这是一个非常好的问题。很多人以为 LLM"天生就会"调工具，但实际上这是专门训练出来的能力。

#### 核心原理：工具使用是通过训练数据和微调学会的

LLM 学会使用工具的过程分为三个阶段：

**阶段 1：预训练中的隐式学习**

在海量文本语料（代码、文档、API 手册、技术博客）中，LLM 已经见过大量"函数定义 → 函数调用"的模式。例如训练数据中有：

```python
# 函数定义
def search(query: str, limit: int = 10) -> list:
    """Search documents by query."""
    ...

# 函数调用
results = search(query="machine learning", limit=5)
```

LLM 通过数十亿次这样的模式见识，学会了"给定一个函数签名和描述，根据需求生成正确的调用参数"这种泛化能力。这是基础。

**阶段 2：有监督微调（SFT）学习工具调用格式**

Anthropic/OpenAI 会用专门构造的训练数据，教模型输出特定格式的工具调用。训练样本大概长这样：

```
输入:
  system: "你是一个助手，可以使用以下工具：[{name: "calculator", description: "计算数学表达式", input_schema: {expression: string}}]"
  user: "13 * 47 等于多少？"

期望输出:
  assistant: [TextBlock("让我帮你计算。"), ToolUseBlock(name="calculator", input={"expression": "13 * 47"})]
  stop_reason: "tool_use"
```

通过成千上万条这样的样本，模型学会了：
- 看到 `tools` 参数 → 知道自己可以调用工具
- 分析用户请求 → 判断是否需要工具、需要哪个
- 按照 **特定格式** 输出 ToolUseBlock（name + input）
- 输出 `stop_reason: "tool_use"` 表示"我需要等工具结果"

**阶段 3：RLHF / 强化学习优化决策质量**

通过人类反馈或自动评估，优化模型在以下方面的决策：
- 什么时候该用工具，什么时候不该用（避免过度调用）
- 选择最合适的工具（有 read_file 和 bash+cat 两种方式读文件时，优先选 read_file）
- 生成正确的参数（路径、命令格式等）

#### 不同协议格式需要分别训练吗？

**是的。** Anthropic 的工具调用格式（ToolUseBlock）和 OpenAI 的格式（function_call / tool_calls）是不同的，模型需要在对应格式的数据上分别训练。这就是为什么：

- Claude 模型只能用 Anthropic 格式的工具定义
- GPT 模型只能用 OpenAI 格式的工具定义
- 如果你把 OpenAI 格式的工具定义发给 Claude，它不会正确响应

但是，GLM、Kimi、DeepSeek 等提供"Anthropic 兼容接口"的模型，是在 Anthropic 格式上做过微调或格式转换的，所以能兼容。

#### 模型是"理解"工具还是"模式匹配"？

**更接近"有泛化能力的模式匹配"。** LLM 并不真正"理解"工具在做什么——它不知道 `write_file` 实际上会在磁盘上创建文件。它学到的是："当用户要求创建文件时，输出 name='write_file' 的工具调用，并根据 description 和 input_schema 生成合理参数"。这种泛化能力非常强——即使遇到从未见过的自定义工具，只要 description 写得清楚，LLM 就能正确使用它。

这也解释了为什么 **工具的 description 极其重要**——它是 LLM 理解工具用途的唯一线索。

### 3.6 这就是 Function Calling 吗？工具定义的格式是标准协议吗？

**是的，工具调用就是 function calling**。Anthropic 的叫法是 "tool use"，OpenAI 的叫法是 "function calling"，本质是同一件事：LLM 输出结构化的函数调用请求，由外部代码执行并返回结果。

**工具定义的 JSON Schema 格式是 Anthropic API 的标准协议**，不能随意更改字段名。格式规范如下：

```python
{
    "name": "write_file",                    # 必填：工具名称（LLM 用这个名字来调用）
    "description": "Write content to file.", # 必填：功能描述（LLM 根据这个判断何时使用）
    "input_schema": {                        # 必填：输入参数的 JSON Schema
        "type": "object",                    # 固定为 "object"
        "properties": {                      # 参数定义
            "path": {
                "type": "string",            # 参数类型
                "description": "File path"   # 可选：参数描述（帮助 LLM 理解）
            },
            "content": {"type": "string"},
        },
        "required": ["path", "content"],     # 必填参数列表
    },
}
```

`name`、`description`、`input_schema` 这三个字段是 **Anthropic API 规定的**，不能改。但 `input_schema` 内部的 `properties`（参数名、参数类型、参数描述）是 **你自己定义的**——你要为工具设计什么参数，那是你的自由。

### 3.6 换模型/换 API 需要改代码吗？

**视情况而定**：

| 场景 | 需要改什么 |
|------|-----------|
| 换 Anthropic 兼容模型（如 GLM、Kimi、DeepSeek） | 只改 `.env` 文件的 `MODEL_ID` 和 `ANTHROPIC_BASE_URL`，代码完全不动 |
| 换 OpenAI API | 需要改代码。OpenAI 的工具定义格式和响应格式不同（见下文对比） |
| 换 LangChain 等框架 | 大规模重写。框架有自己的抽象层 |

**Anthropic vs OpenAI 工具定义格式对比**：

```python
# Anthropic 格式（本项目使用的）
{"name": "bash", "description": "Run command.",
 "input_schema": {"type": "object", "properties": {"command": {"type": "string"}}, "required": ["command"]}}

# OpenAI 格式
{"type": "function", "function": {"name": "bash", "description": "Run command.",
 "parameters": {"type": "object", "properties": {"command": {"type": "string"}}, "required": ["command"]}}}
```

差异：OpenAI 多一层 `{"type": "function", "function": {...}}` 包装，参数字段名叫 `parameters` 而非 `input_schema`。响应格式也不同（OpenAI 用 `tool_calls` 字段，Anthropic 用 `content` 里的 ToolUseBlock）。

本项目用的是 Anthropic SDK，而 `.env.example` 中列出的 GLM、Kimi、DeepSeek 等都提供了 **Anthropic 兼容接口**（`ANTHROPIC_BASE_URL`），所以切换这些模型不需要改代码。

## 四、核心模块详解

### 4.1 基础工具模块 (`tools/base.py`)

**设计动机**：Agent 需要与文件系统交互。但直接暴露 shell 命令太危险（`rm -rf /`），直接用 `cat` 读文件又无法控制输出大小。因此封装 5 个安全的基础工具。

**核心安全机制——路径沙箱**：

```python
# tools/base.py:18-32
def safe_path(p: str) -> Path:
    path = (WORKDIR / p).resolve()           # 将相对路径解析为绝对路径
    if not path.is_relative_to(WORKDIR):     # 检查是否还在工作目录内
        raise ValueError(f"Path escapes workspace: {p}")
    return path
```

为什么需要 `.resolve()`？因为攻击者可以用 `../../etc/passwd` 这样的路径逃逸。`resolve()` 会把 `..` 展开成真实路径，然后 `is_relative_to()` 检查是否还在 WORKDIR 内。

**数据流转示例**：LLM 调用 `write_file(path="hello.py", content="print('hi')")` →
1. `TOOL_HANDLERS["write_file"]` 触发 `run_write("hello.py", "print('hi')")`
2. `safe_path("hello.py")` → `/absolute/path/to/workdir/hello.py` ✓ 合法
3. 创建父目录 → 写入文件 → 返回 `"Wrote 11 bytes to hello.py"`
4. 这个字符串作为 `tool_result` 返回给 LLM

### 4.2 工具调度表 (`tools/registry.py`)

**设计动机**：agent_loop 需要根据工具名称找到对应的执行函数。用 if/elif 链？10 个工具就写 10 个分支，丑且难维护。用字典映射，O(1) 查找，新增工具一行搞定。

```python
# tools/registry.py:34-58
def get_tool_handlers(todo, skills, task_mgr, bg, bus, team) -> dict:
    from agents.subagent import run_subagent           # 延迟导入避免循环依赖
    from communication.protocols import handle_shutdown_request, handle_plan_review

    return {
        "bash":             lambda **kw: run_bash(kw["command"]),
        "write_file":       lambda **kw: run_write(kw["path"], kw["content"]),
        "TodoWrite":        lambda **kw: todo.update(kw["items"]),
        "task":             lambda **kw: run_subagent(kw["prompt"], ...),
        "task_create":      lambda **kw: task_mgr.create(kw["subject"], ...),
        "spawn_teammate":   lambda **kw: team.spawn(kw["name"], kw["role"], kw["prompt"]),
        # ... 共 23 个工具
    }
```

**为什么用依赖注入**：`todo`、`skills` 等是在 `main.py` 中创建的单例。如果 `registry.py` 直接 `from main import TODO`，就会形成循环导入（`main.py` 导入 `registry.py`，`registry.py` 又导入 `main.py`）。通过参数传入，彻底打断循环。

**在 agent_loop 中的使用**：

```python
# main.py:117-121
handler = TOOL_HANDLERS.get(block.name)  # 如 block.name == "write_file"
output = handler(**block.input)          # 等价于 run_write(path=..., content=...)
```

`block.input` 是一个字典（LLM 生成的参数），`**` 解包后恰好对应处理函数的参数。

### 4.3 TodoManager (`planning/todo.py`) — 轻量内存待办

**设计动机与你的理解的对比**：

你问："TodoManager 是不是 Plan-to-Solve 的实现？"

**部分正确，但有关键区别**。TodoManager 确实是"先列计划再执行"的模式，但它 **不控制执行顺序，也不自动执行任何子任务**。它只是一个 **可视化的检查清单**——像你在纸上列的 TODO 列表一样，帮助 LLM 不忘记步骤。

**执行顺序**：由 LLM 自己决定。代码里没有任何"按照 todo 列表的顺序依次执行"的逻辑。LLM 看到待办列表后，会自行推理下一步该做什么。因为 LLM 是被训练过的智能体，它能理解任务的逻辑顺序。

**串行执行**：是的，TodoManager 下所有任务都是串行的——只有一个主 agent 在执行，一次做一件事。`in_progress` 最多只能有一个就是这个约束的体现。

**前后依赖问题**：由 LLM 自行判断。比如列了 "1. 创建文件 2. 写入内容 3. 测试"，LLM 会自然地先做 1 再做 2 再做 3，不需要代码强制。这就是"模型即 Agent"的哲学——**信任模型的推理能力，而不是用代码硬编码执行顺序**。

**Nag Reminder 机制**：
```python
# main.py:137-142
rounds_without_todo = 0 if used_todo else rounds_without_todo + 1
if TODO.has_open_items() and rounds_without_todo >= 3:
    results.append({"type": "text", "text": "<reminder>Update your todos.</reminder>"})
```
如果 LLM 连续 3 轮没更新 todo，就注入提醒。这不是强制，而是"温和地提醒"。

#### 深入辨析："多步工作"和"短清单"到底怎么区分？

你的疑问完全合理："todo 不也是把任务划分为子任务吗？那不就是多步工作？"

**关键区别不在于"步数多少"，而在于以下三个维度**：

| 维度 | TodoManager（"短清单"） | TaskManager（"多步工作"） |
|------|----------------------|------------------------|
| **需要几个人做？** | 一个人（主 agent 自己） | 可能需要多个人（teammates） |
| **做完后还需要这个计划吗？** | 不需要（内存中，用完即弃） | 需要（持久化，可回溯审计） |
| **子任务之间有依赖关系吗？** | 通常没有（或由 LLM 自行判断） | 有显式的 blockedBy 约束 |
| **执行时间跨度** | 一次对话内（分钟级） | 可能跨多次对话（小时/天级） |

**用类比来理解**：
- **TodoManager** = 你在便利贴上写的购物清单："买牛奶、买鸡蛋、买面包"。你自己去超市一趟就搞定，买完把便利贴扔了。
- **TaskManager** = 公司项目管理看板（Jira）："设计数据库 → 开发后端 → 开发前端 → 集成测试"。多人协作，有明确的依赖关系，进度需要长期追踪。

**具体场景判断**：

```
用户: "帮我在这个文件里加一个函数，然后写个测试"
→ LLM 选择 TodoWrite：
  [ ] 在 main.py 添加 greet() 函数
  [ ] 在 test_main.py 添加测试
  （简单任务，自己做，不需要持久化）

用户: "重构整个认证模块，前后端都要改，还要写迁移脚本"
→ LLM 选择 task_create：
  Task #1: 重构后端认证 API（可能分配给 teammate alice）
  Task #2: 重构前端登录页（可能分配给 teammate bob）
  Task #3: 编写数据库迁移脚本 (blockedBy: [1])
  Task #4: 集成测试 (blockedBy: [1, 2, 3])
  （复杂项目，需要多人协作，有依赖关系）
```

**system prompt 那么简短，真的够用吗？**

```python
SYSTEM = "...Prefer task_create/task_update/task_list for multi-step work. Use TodoWrite for short checklists..."
```

说实话，**对于足够聪明的 LLM（如 Claude Sonnet/Opus），这确实够用了**。原因：

1. **LLM 不只看 system prompt，还看工具的 description**。`TodoWrite` 的 description 是 "Update task tracking list"，`task_create` 的 description 是 "Create a persistent file task"。"persistent" 和 "tracking list" 这两个关键词就足以帮助 LLM 区分。

2. **LLM 是在海量代码项目管理经验上训练的**。它见过 Jira、Trello、GitHub Issues，它"知道"什么场景该用轻量清单，什么场景该用正式任务管理。

3. **即使 LLM 偶尔选错，也不会造成严重后果**。用 TodoWrite 做了本该用 TaskManager 的事情？最多是清单在压缩后丢失。用 TaskManager 做了很简单的事情？最多是多创建了几个 JSON 文件。两者都是可恢复的。

4. **实际上，更长的 system prompt 不一定更好**。过于详细的决策规则会消耗 token，而且可能反而让 LLM 困惑（"规则太多记不住"）。简洁的指导 + 信任模型的判断力，是 Claude Code 的设计哲学。

### 4.4 TaskManager (`planning/tasks.py`) — 持久化任务系统

**设计动机：和 TodoManager 有什么区别？**

这是你提出的核心问题之一。让我用一张对比表彻底说清：

| 维度 | TodoManager | TaskManager |
|------|------------|-------------|
| **存储** | 内存中的 Python 列表 | 磁盘上的 JSON 文件（`.tasks/task_*.json`） |
| **生命周期** | 上下文压缩后就丢失 | 永久存在，跨会话存活 |
| **依赖关系** | 无 | 有 `blockedBy` 字段 |
| **所有者** | 无（只有主 agent） | 有 `owner` 字段（可分配给 teammate） |
| **谁来执行** | 主 agent 自己串行执行 | 主 agent 或 teammate 均可认领 |
| **复杂度** | 适合 3-10 步的简单任务 | 适合需要多人协作的复杂项目 |
| **自动执行** | 无自动执行 | teammate 可自动巡检认领 |

**关键误解澄清**：TaskManager **不会** 自动为每个 task 分配 subagent。它只是一个"任务看板"——就像 Jira 或 Trello。任务创建后，需要有人（主 agent、teammate、或手动）去认领（`claim`）。

**依赖关系如何解决你担心的"执行顺序"问题**：

```python
# planning/tasks.py:92-97
if status == "completed":
    for f in TASKS_DIR.glob("task_*.json"):
        t = json.loads(f.read_text())
        if tid in t.get("blockedBy", []):
            t["blockedBy"].remove(tid)  # 自动解除下游依赖
            self._save(t)
```

如果 task_2 的 `blockedBy: [1]`，那么 task_1 完成前，task_2 会被标记为"被阻塞"。Teammate 的自动认领逻辑只认领 `status=="pending" and not blockedBy` 的任务，所以被阻塞的任务不会被提前认领。

**LLM 如何知道用 TodoManager 还是 TaskManager？** 通过 **system prompt**：

```python
# main.py:48-53
SYSTEM = (
    f"You are a coding agent at {WORKDIR}. Use tools to solve tasks.\n"
    f"Prefer task_create/task_update/task_list for multi-step work. "
    f"Use TodoWrite for short checklists.\n"  # ← 这句指导 LLM 选择
    ...
)
```

我们在 system prompt 中明确告诉 LLM：多步工作用 TaskManager，短清单用 TodoWrite。LLM 会根据任务复杂度自行判断。

#### TaskManager 的 JSON 文件详解

**文件路径**：`.tasks/task_{id}.json`

**完整字段**：

```json
{
  "id": 1,                          // 唯一 ID，自增
  "subject": "Implement auth module", // 任务主题
  "description": "Create login and signup endpoints", // 详细描述
  "status": "pending",              // 状态：pending / in_progress / completed / deleted
  "owner": null,                    // 认领者：null（未认领）或 "alice"（队友名）
  "blockedBy": [2, 3]              // 前置依赖：需要 task_2 和 task_3 先完成
}
```

**CRUD 操作时机**：

| 操作 | 触发时机 | 对应方法 |
|------|---------|---------|
| Create | LLM 调用 `task_create` 工具 | `TaskManager.create()` |
| Read | LLM 调用 `task_get` 或 `task_list` | `TaskManager.get()` / `list_all()` |
| Update | LLM 调用 `task_update` 改状态/依赖 | `TaskManager.update()` |
| Delete | LLM 设 `status="deleted"` | `update()` 内 `unlink()` 删文件 |
| Claim | Teammate 自动认领或 LLM 调用 `claim_task` | `TaskManager.claim()` |

**完整流程示例**（多步任务拆分）：

```
用户: "重构认证模块，分前端和后端两部分"

LLM 调用: task_create(subject="重构后端认证", description="...")
  → 创建 .tasks/task_1.json  {id:1, status:"pending", blockedBy:[]}

LLM 调用: task_create(subject="重构前端登录页", description="...")
  → 创建 .tasks/task_2.json  {id:2, status:"pending", blockedBy:[]}

LLM 调用: task_create(subject="集成测试", description="...")
  → 创建 .tasks/task_3.json  {id:3, status:"pending", blockedBy:[1, 2]}
  //（集成测试被 task_1 和 task_2 阻塞，必须它们都完成才能开始）

LLM 调用: spawn_teammate(name="alice", role="backend", prompt="Work on task #1")
  → Alice 认领 task_1，开始工作

LLM 调用: spawn_teammate(name="bob", role="frontend", prompt="Work on task #2")
  → Bob 认领 task_2，开始工作

// Alice 完成 task_1 → task_update(1, status="completed")
//   → 自动从 task_3 的 blockedBy 中移除 1 → blockedBy 变为 [2]

// Bob 完成 task_2 → task_update(2, status="completed")
//   → 自动从 task_3 的 blockedBy 中移除 2 → blockedBy 变为 []
//   → task_3 现在可以被认领了

// 空闲的 teammate 或主 agent 认领 task_3 开始集成测试
```

### 4.5 子 Agent (`agents/subagent.py`) — 一次性上下文隔离

**核心问题：Subagent、TaskManager、TeammateManager 都涉及"多 agent"，它们的区别和联系是什么？**

这是你最核心的问题之一。三者是完全不同的机制，解决不同层次的问题：

| 维度 | Subagent (s04) | TaskManager (s07) | TeammateManager (s09/s11) |
|------|---------------|-------------------|--------------------------|
| **本质** | 一次性函数调用 | 任务看板（数据结构） | 持久化线程 Agent |
| **生命周期** | 调用 → 执行 → 返回 → 消亡 | 无生命周期（只是 JSON 文件） | spawn → work → idle → shutdown |
| **有没有自己的 agent loop** | 有（独立的 while 循环） | 没有（它不是 agent） | 有（独立线程中的 while 循环） |
| **上下文** | 全新的 messages=[] | 不适用 | 全新的 messages=[] |
| **可用工具** | bash + read（Explore 模式）或 + write/edit | 不适用 | bash + read + write + edit + send_message + idle + claim_task |
| **能否通信** | 不能（没有 MessageBus） | 不适用 | 能（通过 MessageBus 收发消息） |
| **能否认领任务** | 不能 | 不适用 | 能（空闲时自动扫描认领） |
| **适用场景** | "帮我查个东西" | "这个项目要做 5 件事" | "分给团队成员去做" |

**为什么 Subagent 没有 MessageBus？**

因为 Subagent 是 **一次性的**——调用、执行、返回摘要、消亡。它不需要和其他 agent 交流，它的唯一任务就是"帮父 agent 做一件独立的事情，然后把结果汇报回来"。就像你让实习生去查一个资料，他查完告诉你结果，然后就走了——不需要给他安装企业微信。

**为什么 TaskManager 没有 MessageBus？**

因为 TaskManager **不是 agent**！它只是一个数据结构（任务看板）。就像 Jira 不是一个员工——Jira 是一个记事板，员工（agent/teammate）才是干活的。

**你的理解"涉及多 agent 不一定需要协作"是正确的**：
- Subagent：多个独立工人，各干各的，不需要交流（`独立并行`）
- Teammate：多个团队成员，可以通过 MessageBus 交流协作（`协作并行`）

**TeammateManager 实现的协作方式是什么？**

**星型拓扑（Hub-Spoke）的异步消息传递模式**：

```
         ┌─────────┐
    ┌───→│  Lead   │←──┐
    │    │ (主agent)│    │
    │    └─────────┘    │
    │         ↕          │
    ↕    MessageBus     ↕
┌──────┐  (JSONL)  ┌──────┐
│Alice │           │ Bob  │
│(队友)│           │(队友) │
└──────┘           └──────┘
```

**优点**：
- 简单可靠：文件系统作为消息队列，不需要额外的 MQ 中间件
- 持久化：消息写在磁盘上，不会因进程崩溃丢失
- 可观测：直接看 `.team/inbox/*.jsonl` 文件就能审计所有通信

**缺点**：
- 延迟高：基于文件轮询，最快也是 5 秒一次
- 无直接 P2P：Alice 不能直接给 Bob 发消息（实际上可以，通过 `send_message` 工具，但设计上 Lead 是协调中心）
- 并发安全：JSONL 追加写在极端并发下可能交错（但实际 daemon 线程的并发量很低）

**Subagent 的工具为什么受限？**

```python
# agents/subagent.py:29-48
sub_tools = [bash, read_file]        # Explore 模式：只读
if agent_type != "Explore":
    sub_tools += [write_file, edit_file]  # general-purpose 模式：可写
```

注意 subagent **不能**调用：task、TodoWrite、spawn_teammate、load_skill、compress、background_run 等。原因：
1. **没有 `task` 工具**：防止递归嵌套（subagent 再生 subagent 再生 subagent...无限套娃）
2. **没有团队工具**：subagent 是临时工，不参与团队协作
3. **没有压缩工具**：subagent 最多 30 轮就结束，不需要长期上下文管理
4. **没有后台工具**：subagent 本身就是"后台执行"的，给它后台工具会增加复杂度且无意义

**Teammate 的工具为什么不同于 subagent？**

Teammate 有 `send_message`（通信）、`idle`（进入空闲）、`claim_task`（认领任务），但没有 `task`（不能创建 subagent）、没有 `spawn_teammate`（不能创建新队友——只有 Lead 能）。这是 **最小权限原则**：每个角色只拥有它需要的能力。

#### 深入辨析：Subagent 到底有什么意义？它不是阻塞主 agent 吗？

你问得很对。让我们看看 subagent 的调用过程：

```python
# tools/registry.py:40
"task": lambda **kw: run_subagent(kw["prompt"], kw.get("agent_type", "Explore")),

# agents/subagent.py:12-117
def run_subagent(prompt, agent_type="Explore"):
    sub_msgs = [{"role": "user", "content": prompt}]
    for _ in range(30):                    # ← 这是一个同步的 for 循环
        resp = client.messages.create(...) # ← 阻塞调用 LLM API
        ...
    return summary                         # ← 返回后主 agent 才能继续
```

**是的，subagent 确实会阻塞主 agent。** 它不是异步的。那它的意义是什么？

**Subagent 的价值不在于并行，而在于上下文隔离**。用一个具体场景说明：

```
场景：用户说 "这个项目用的什么测试框架？然后帮我写个新功能"

如果不用 subagent（主 agent 自己做）：
  第 1 轮：read_file("package.json")      → 200 行内容进入上下文
  第 2 轮：read_file("jest.config.js")    → 50 行内容进入上下文
  第 3 轮：bash("ls tests/")              → 30 行内容进入上下文
  第 4 轮：read_file("tests/example.test.js") → 100 行内容进入上下文
  第 5 轮：LLM 回答 "用的是 Jest"
  // 此时主 agent 的上下文已经被 380 行探索内容污染了
  // 接下来写新功能时，这些无关内容占着 token，降低 LLM 的注意力质量
  第 6-10 轮：写新功能（但上下文已经很脏了）

如果用 subagent：
  第 1 轮：主 agent 调用 task(prompt="查一下项目用的什么测试框架")
    → subagent 在独立上下文中做了同样的 4 轮探索
    → subagent 返回摘要: "Jest, 配置在 jest.config.js"
    → 主 agent 的上下文中只多了一行摘要文本
  第 2-6 轮：写新功能（上下文干净清爽）
```

**类比**：你是老板（主 agent），要做一个决策需要一些调研数据。你可以自己花 2 小时去翻资料（上下文污染），也可以让助理去查然后给你一份一页纸的摘要（上下文隔离）。两种方式都不是并行的——你等着助理查完才能决策——但第二种方式让你的"工作台"保持整洁。

**总结**：Subagent 的核心价值是 **信息压缩**，不是并行加速。30 轮工具调用的细节被压缩成一段摘要返回，主 agent 的上下文窗口被保护了。

#### 深入辨析：什么情况下主 agent 会调用 subagent？可以预测吗？

你问的很好："1+1等于几这么简单的问题也会交给 subagent 吗？"

**答案：不会。** LLM 调用 subagent 的决策逻辑是：

1. **简单问题（1+1=?）**：LLM 直接回答，不调用任何工具，更不用 subagent
2. **需要单步操作的问题（"读一下 config.py"）**：LLM 直接调用 `read_file`，主 agent 自己做
3. **需要多步操作但不会污染上下文的问题（"写个 hello.py 并测试"）**：LLM 用 TodoWrite 列清单，主 agent 自己依次执行
4. **需要大量探索且结果可以压缩的问题（"这个项目用了什么技术栈？"）**：LLM **可能**调用 `task` 工具，让 subagent 去翻遍整个项目，返回一句话摘要

**关键词是"可能"**——这不是确定性的规则，而是 LLM 的概率决策。

**是否可预测？** 大致可预测，但不是100%确定的。同一个问题在不同上下文下可能有不同选择：

```
场景 A：上下文很干净（刚开始对话）
用户: "这个项目的架构是什么？"
→ LLM 可能选择自己做：read_file("README.md") + read_file("package.json") + ...
  （因为上下文有空间，不需要隔离）

场景 B：上下文已经很满（已经做了很多事）
用户: "顺便帮我看看那个子项目用了什么框架？"
→ LLM 更可能选择 subagent
  （因为上下文已经快满了，不想再往里塞探索结果）
```

**"所有事都丢给 subagent"的想法为什么不好？**

理论上可以，但有三个问题：
1. **延迟**：每次 subagent 调用都是一次新的 API 请求链，"1+1" 本来 0.5 秒回答，走 subagent 要 3-5 秒
2. **成本**：subagent 有自己的 system prompt + 工具定义开销，哪怕只问一句话也要消耗这些 token
3. **信息丢失**：subagent 只返回摘要。如果任务需要主 agent 看到完整细节（比如审查代码），subagent 的摘要可能不够

**实际的最佳实践**：
- 日常操作（读写文件、跑命令、简单问答）→ 主 agent 自己做
- 探索性任务（调研、搜索、分析大量文件）→ subagent，因为探索过程产生大量噪声
- 独立子任务（"在另一个模块加个功能"）→ subagent(general-purpose)，因为任务范围清晰且独立
- 复杂项目（多人协作、有依赖关系）→ TaskManager + Teammate

### 4.7 上下文压缩 (`context/compression.py`)

```python
def microcompact(messages):

    return [{"role": "user", "content": f"[Compressed. Transcript: {path}]\n{summary}"}]

# Layer 3 — 手动压缩（LLM 调用 compress 工具）
# 同 auto_compact，但由 LLM 主动判断"我需要清理一下上下文了"
```

#### transcript JSONL 文件详解

**路径**：`.transcripts/transcript_{timestamp}.jsonl`

**格式**：每行一个 JSON 对象，对应一条消息

```jsonl

{"role": "assistant", "content": [{"type": "text", "text": "I'll create that file."}, {"type": "tool_use", "id": "toolu_abc", "name": "write_file", "input": {"path": "hello.py", "content": "print('hello')"}}]}
```

**读写时机**：只在 `auto_compact()` 触发时写入（保存完整对话历史），之后不再读取（仅作为灾难恢复备份）。

### 4.8 BackgroundManager (`background/manager.py`)

**设计动机**：有些命令要跑几分钟（`npm install`、`pytest`、`docker build`）。阻塞式执行下，agent 只能干等。BackgroundManager 让 agent 可以"启动任务后继续做别的事"。

**应用场景**：
- `npm install`（安装依赖，可能要 2 分钟）
- `pytest`（跑测试套件，可能要 5 分钟）
- 任何 agent 不需要等结果就能继续工作的长命令

**Subagent 能用吗？** 不能。看 subagent 的工具列表（`agents/subagent.py:29-48`），只有 bash/read/write/edit，没有 `background_run`。

**为什么这么设计？** Subagent 本身就是一个"后台执行单元"——主 agent 把任务委派给 subagent，subagent 同步执行完后返回结果。如果 subagent 内部再搞后台，就变成了"后台中的后台"，增加了不必要的复杂度。而且 subagent 最多 30 轮就结束，不需要异步。

**agent 如何知道要用 BackgroundManager？**

你的担忧很合理："description 只是 'Run command in background thread.'，LLM 会不会把 `ls` 也后台执行？"

**实际上不会，原因如下**：

1. **LLM 同时看到了 `bash` 和 `background_run` 两个工具**。`bash` 的 description 是 "Run a shell command."，`background_run` 是 "Run command in background thread."。LLM 被训练过在多个候选工具中选择最合适的。对于 `ls` 这种毫秒级命令，LLM 没有理由选择后台执行——因为 `bash` 更简单直接。

2. **LLM 有关于命令执行时间的世界知识**。它在训练数据中见过无数次 "npm install takes a while"、"pytest running for 5 minutes" 这样的讨论。它知道哪些命令是耗时的，哪些是瞬时的。

3. **上下文引导**。当用户说"安装依赖，顺便帮我创建配置文件"时，"顺便"这个词暗示了并行需求。如果用户只说"列出文件"，LLM 不会产生并行的需求。

4. **即使偶尔误判也不严重**。把 `ls` 后台执行？结果依然会通过通知队列返回，只是多了几秒延迟。不会导致错误。

5. **更好的做法（改进方向）**：可以将 description 改为更明确的 `"Run a long-running command (>10s) in background thread, e.g. npm install, pytest, docker build."`，通过举例进一步引导 LLM。

**通知队列的工作机制**：

```python
# 主线程发起后台任务
BG.run("npm install")  # → 启动 daemon 线程，立即返回 task_id

# daemon 线程中执行
def _exec(self, tid, command, timeout):
    r = subprocess.run(command, ...)     # 阻塞等待完成
    self.notifications.put({...})        # 完成后放入通知队列

# 下一轮 agent_loop 开始时
notifs = BG.drain()                      # 取出所有已完成的通知
if notifs:
    messages.append({"role": "user",     # 以 user 消息注入
        "content": f"<background-results>\n{notif_text}\n</background-results>"})
```

通知是在 **下一轮 LLM 调用前**注入的，所以 agent 会在继续推理时看到后台结果。

### 4.9 MessageBus (`communication/bus.py`)

**设计动机**：Teammate 之间需要通信。方案有很多（共享内存、socket、数据库），但文件系统最简单：每个 agent 一个 `.jsonl` 文件作为收件箱，追加写入 + 读后清空。

#### inbox JSONL 文件详解

**路径**：`.team/inbox/{name}.jsonl`（如 `.team/inbox/alice.jsonl`）

**每行格式**：

```json
{
  "type": "message",                    // 消息类型：message / broadcast / shutdown_request / ...
  "from": "lead",                       // 发送者
  "content": "Please work on auth",     // 消息内容
  "timestamp": 1711900000.123           // 时间戳
}
```

**特殊消息类型示例**：

```json
// 关闭请求
{"type": "shutdown_request", "from": "lead", "content": "Please shut down.",
 "request_id": "abc12345", "timestamp": 1711900000.0}

// 计划审批响应
{"type": "plan_approval_response", "from": "lead", "content": "Looks good!",
 "request_id": "xyz67890", "approve": true, "feedback": "Go ahead", "timestamp": 1711900000.0}
```

**读写时机**：
- **写入**：`bus.send()` 时追加一行到目标收件箱文件
- **读取**：`bus.read_inbox()` 时读取全部内容并 **清空文件**（drain 语义）
- Lead 在每轮 agent_loop 开始时自动 `read_inbox("lead")`
- Teammate 在工作阶段和空闲阶段都会 `read_inbox(name)`

### 4.10 TeammateManager (`agents/team.py`)

**Teammate 的完整生命周期**：

```python
# agents/team.py:94-322 (_loop 方法)
def _loop(self, name, role, prompt):
    while True:
        # ===== 工作阶段（最多 50 轮工具调用）=====
        for _ in range(50):
            inbox = self.bus.read_inbox(name)  # 每轮检查收件箱
            for msg in inbox:
                if msg.get("type") == "shutdown_request":
                    return  # 收到关闭请求，立即退出

            response = client.messages.create(...)  # 调用 LLM
            if response.stop_reason != "tool_use":
                break  # LLM 认为当前任务完成

            # 执行工具（含 idle 工具检测）
            if idle_requested:
                break  # LLM 主动请求进入空闲

        # ===== 空闲阶段（轮询 60 秒）=====
        self._set_status(name, "idle")
        for _ in range(12):  # 60s / 5s = 12 次轮询
            time.sleep(5)

            # 检查收件箱
            inbox = self.bus.read_inbox(name)
            if inbox: resume = True; break

            # 扫描未认领任务
            unclaimed = [t for t in tasks if t.status=="pending" and not t.owner and not t.blockedBy]
            if unclaimed:
                self.task_mgr.claim(unclaimed[0]["id"], name)
                # 身份重注入（压缩后可能丢失）
                if len(messages) <= 3:
                    messages.insert(0, {"role": "user", "content": "<identity>You are 'alice'...</identity>"})
                resume = True; break

        if not resume:
            self._set_status(name, "shutdown")  # 超时退出
            return
```

| `.team/config.json` | JSON | 团队名册（队友名、角色、状态） | spawn/set_status 时写，list_all 时读 |

| `.transcripts/transcript_{ts}.jsonl` | JSONL | 压缩前的对话备份 | auto_compact 时写，通常不读（灾难恢复用） |
| `skills/*/SKILL.md` | Markdown | 专业知识文件（YAML frontmatter） | 启动时读，运行中 load_skill 时读 |

## 六、核心亮点总结

1. **Agent Loop 核心范式**：整个系统的灵魂就是 `while stop_reason == "tool_use"` 的反馈循环——模型自主决策何时使用工具、使用哪个工具，代码不强加任何工作流
2. **三层上下文压缩**：微压缩（每轮）+ 自动压缩（阈值触发）+ 手动压缩（按需），使 Agent 可运行无限时长会话
3. **工具调度表 (Dispatch Dict)**：O(1) 查找，新增工具只需一行代码，完美遵循开闭原则
4. **子 Agent 上下文隔离**：独立 messages 列表防止上下文污染，只返回摘要给父 Agent
5. **多 Agent 团队协作**：基于 JSONL 的文件消息总线 + 工作/空闲/关闭状态机 + 自主任务认领
6. **两层 Skill 加载**：system prompt 放摘要（低成本），tool_result 放全文（按需），避免 token 浪费
7. **安全沙箱**：路径逃逸检测 + 危险命令过滤 + 输出截断，防止 Agent 做出破坏性操作

## 七、优化改进建议

### A. 在项目当前功能实现上进行优化改进

#### A1. 消息总线并发安全

**问题**：多个 teammate 线程同时写同一个 `.jsonl` 文件，追加操作可能交错导致 JSON 行损坏。

**方案**：
```python
# communication/bus.py — 使用线程锁保护写入
import threading
_write_lock = threading.Lock()

def send(self, sender, to, content, ...):
    msg = {"type": msg_type, "from": sender, "content": content, "timestamp": time.time()}
    with _write_lock:  # 排他锁，保证一次只有一个线程写文件
        with open(INBOX_DIR / f"{to}.jsonl", "a") as f:
            f.write(json.dumps(msg) + "\n")
```

#### A2. Teammate 缺少上下文压缩

**问题**：`agents/team.py` 的 `_loop` 方法没有调用 `microcompact` 或 `auto_compact`。Teammate 执行长任务时 messages 列表无限增长，最终导致 API 调用因 token 超限而失败。

**方案**：在 Teammate 工作循环的 LLM 调用前加入压缩管道：
```python
# agents/team.py — _loop 方法中，在 client.messages.create() 前添加
from context.compression import microcompact, estimate_tokens, auto_compact

microcompact(messages)
if estimate_tokens(messages) > 80000:  # Teammate 用更低阈值，因为工具集更小
    messages[:] = auto_compact(messages)
    # 身份重注入（压缩后 Teammate 可能忘记自己是谁）
    messages.insert(0, {"role": "user", "content": f"<identity>You are '{name}', role: {role}</identity>"})
    messages.insert(1, {"role": "assistant", "content": f"I am {name}. Continuing."})
```

#### A3. 任务认领的并发竞争

**问题**：两个 teammate 同时扫描到同一个未认领任务，都调用 `claim()`，可能导致重复认领。

**方案**：
```python
# planning/tasks.py — 原子认领
import threading
_claim_lock = threading.Lock()

def claim(self, tid: int, owner: str) -> str:
    with _claim_lock:
        task = self._load(tid)
        if task.get("owner"):
            return f"Task #{tid} already claimed by {task['owner']}"
        task["owner"] = owner
        task["status"] = "in_progress"
        self._save(task)
        return f"Claimed task #{tid} for {owner}"
```

#### A4. 工具编辑操作缺少 Linter 验证

**问题**：`run_edit` 和 `run_write` 不检查写入的代码是否有语法错误。LLM 可能写入无效代码，然后花很多轮调试。SWE-agent 的 NeurIPS 2024 论文证明 Linter 阻断能显著提高代码质量。

**方案**：
```python
# tools/base.py — 写入后自动 lint
import subprocess

def _lint_check(filepath: Path) -> str | None:
    """对 Python 文件运行语法检查，返回错误信息或 None"""
    if filepath.suffix != ".py":
        return None
    try:
        r = subprocess.run(
            ["python", "-m", "py_compile", str(filepath)],
            capture_output=True, text=True, timeout=10
        )
        if r.returncode != 0:
            return r.stderr.strip()
    except Exception:
        pass
    return None

def run_write(path: str, content: str) -> str:
    try:
        fp = safe_path(path)
        fp.parent.mkdir(parents=True, exist_ok=True)
        fp.write_text(content)
        # 写入后自动 lint
        lint_error = _lint_check(fp)
        if lint_error:
            return f"Wrote {len(content)} bytes to {path}\n⚠️ Syntax warning:\n{lint_error}"
        return f"Wrote {len(content)} bytes to {path}"
    except Exception as e:
        return f"Error: {e}"
```

#### A5. Token 估算精度

**问题**：`len(json.dumps(messages)) // 4` 对中文非常不准确（中文一个字约 2-3 token，但 JSON 转义后一个中文字约 6-18 字节）。可能导致压缩过早或过晚触发。

**方案**：使用 Anthropic SDK 的 `count_tokens` 方法，或基于启发式的分段估算：
```python
# context/compression.py
def estimate_tokens(messages: list) -> int:
    text = json.dumps(messages, default=str, ensure_ascii=False)  # 不转义中文
    # 中文字符约 2 token/字，英文约 0.25 token/字符
    chinese_chars = sum(1 for c in text if '\u4e00' <= c <= '\u9fff')
    ascii_chars = len(text) - chinese_chars
    return chinese_chars * 2 + ascii_chars // 4
```

#### A6. 结构化错误处理

**问题**：工具错误返回 `f"Error: {e}"` 字符串，LLM 无法区分"文件不存在"和"权限被拒"等不同类型的错误，可能导致错误的重试策略。

**方案**：返回结构化错误，同时保持向后兼容：
```python
def run_read(path: str, limit: int = None) -> str:
    try:
        lines = safe_path(path).read_text().splitlines()
        ...
    except FileNotFoundError:
        return "Error [FILE_NOT_FOUND]: File does not exist: {path}. Check the path and try again."
    except PermissionError:
        return "Error [PERMISSION_DENIED]: Cannot read {path}. File is not accessible."
    except Exception as e:
        return f"Error [UNKNOWN]: {e}"
```

#### B2. 评测体系：量化 Agent 表现

**现状**：没有任何评测机制，无法知道 agent 做得好不好。

**方案**：创建 `evaluation/` 模块：

```python
# evaluation/metrics.py
class AgentMetrics:
    def __init__(self):
        self.total_rounds = 0          # LLM 调用轮次
        self.total_tool_calls = 0      # 工具调用次数
        self.tool_errors = 0           # 工具调用错误次数
        self.total_tokens_in = 0       # 输入 token 总量
        self.total_tokens_out = 0      # 输出 token 总量
        self.task_completion_rate = 0  # 任务完成率
        self.avg_rounds_per_task = 0   # 平均每任务轮次
        self.compression_triggers = 0  # 压缩触发次数

    def record_round(self, response):
        self.total_rounds += 1
        self.total_tokens_in += response.usage.input_tokens
        self.total_tokens_out += response.usage.output_tokens

    def record_tool_call(self, tool_name, success: bool):
        self.total_tool_calls += 1
        if not success:
            self.tool_errors += 1

    def report(self) -> str:
        error_rate = self.tool_errors / max(self.total_tool_calls, 1) * 100
        return (
            f"Rounds: {self.total_rounds} | Tool calls: {self.total_tool_calls} "
            f"| Error rate: {error_rate:.1f}% | Tokens: {self.total_tokens_in}+{self.total_tokens_out}"
        )
```

在 `main.py` 的 `agent_loop` 中集成：
```python
METRICS = AgentMetrics()
# 在 LLM 调用后
METRICS.record_round(response)
# 在工具执行后
METRICS.record_tool_call(block.name, "Error" not in str(output))
# REPL 中添加 /metrics 命令
if query.strip() == "/metrics": print(METRICS.report()); continue
```

#### B5. MCP (Model Context Protocol) 支持

**现状**：工具集是硬编码的，不支持外部工具服务器。Codex CLI 和 Gemini CLI 都支持 MCP。

**方案**：创建 `mcp/` 模块作为 MCP 客户端：

```python
# mcp/client.py
import json, subprocess

class MCPClient:
    """连接外部 MCP 服务器，动态加载工具"""
    def __init__(self, server_command: list):
        self.process = subprocess.Popen(
            server_command, stdin=subprocess.PIPE,
            stdout=subprocess.PIPE, text=True
        )

    def list_tools(self) -> list:
        """获取 MCP 服务器提供的工具列表"""
        self._send({"method": "tools/list"})
        response = self._recv()
        return response.get("tools", [])

    def call_tool(self, name: str, arguments: dict) -> str:
        """调用 MCP 服务器的工具"""
        self._send({"method": "tools/call", "params": {"name": name, "arguments": arguments}})
        response = self._recv()
        return response.get("content", [{}])[0].get("text", "")
```

这样可以动态接入数据库查询、Slack 通知、Jira 操作等外部能力，无需修改 agent 核心代码。

#### B8. RAG（检索增强生成）

**现状**：Skill 系统只有 4 个预定义知识文件。对于大型项目文档、API 手册等海量知识，无法全部预加载。

**方案**：集成向量检索，按需检索相关知识片段：

```python
# context/rag.py
class SimpleRAG:
    """基于 TF-IDF 的轻量 RAG（无需 GPU）"""
    def __init__(self, docs_dir: Path):
        self.chunks = self._load_and_chunk(docs_dir)
        self._build_index()

    def _load_and_chunk(self, docs_dir):
        """将文档切分为 500 字符的块"""
        chunks = []
        for f in docs_dir.rglob("*.md"):
            text = f.read_text()
            for i in range(0, len(text), 500):
                chunks.append({"source": str(f), "text": text[i:i+500]})
        return chunks

    def query(self, question: str, top_k: int = 3) -> str:
        """检索与问题最相关的 top_k 个文档片段"""
        scores = [(self._similarity(question, c["text"]), c) for c in self.chunks]
        scores.sort(reverse=True)
        return "\n---\n".join(
            f"[{c['source']}]\n{c['text']}" for _, c in scores[:top_k]
        )
```

注册为工具：
```python
"search_docs": lambda **kw: RAG.query(kw["question"]),
```

这使得 agent 可以在需要时检索项目文档、API 手册等海量知识。
