# 多 Agent 架构调研与模式辨析（2026-09-02）

> 本文整理自围绕本项目三种多 agent 模式（普通 SubAgent / Coordinator / MetaGPT-lite SOP）的系列讨论与外部调研。调研依据：Anthropic《Building Effective Agents》（2024-12）、《How We Built Our Multi-Agent Research System》（2025-06）两篇原始文献，Claude Code 源码调研（本地 `cc源码调研/06-cc-子agent及多agent编排-v2.md`），以及 CodeBuddy 产品第一手架构信息。

---

## 一、核心结论（先看这个）

1. **产品化多 agent 的主体形态 = 单主 agent + LLM 自主委托**（即本项目的"普通模式"）。业界没有任何产品把"协调者模式"做成用户可切换的开关。
2. **"协调者"是架构角色，不是产品功能**。几乎每个多 agent 系统都有协调者，区别只在于：由 LLM 动态扮演（主流），还是被硬编码成用户模式（本项目的模式 B，业界孤例）。
3. 多 agent 设计模式（协调者、团队、消息总线等）**不是炒作，但常被误读**：它们是真实的架构词汇，主要活在**框架圈**（LangGraph/CrewAI/AutoGen）和**学术圈**（MetaGPT），而非产品交互层。类比：后端天天讲微服务，但没有产品有"微服务模式"按钮。
4. Anthropic 生产系统的多 agent（Research 功能）**内部就是 orchestrator-worker**（LeadResearcher + 3-5 个并行子 agent，性能提升 90.2%），但用户界面上无任何模式选择——**模式选择发生在产品设计层，不是用户交互层**。
5. 多 agent 有明确适用边界（Anthropic 原文）：适合**广度优先、可高度并行、信息量超出单上下文**的任务（研究类）；**多数编程任务的真正可并行部分较少**。多 agent 系统的 token 消耗约是普通对话的 15 倍。

## 二、概念框架：两个正交维度

来自《Building Effective Agents》的核心定义，是理解一切"模式"混乱的钥匙：

- **Workflow（工作流）**：LLM 和工具通过**预定义代码路径**编排
- **Agent（智能体）**：LLM **动态主导自身流程**、自主决定工具使用

注意：这是**编排方式**的划分，不是 agent 数量的划分。与"实体数量"维度正交组合：

| | 编排预定义（workflow） | 编排动态（agent） |
|---|---|---|
| **多 agent** | **模式 C 在此**：角色管线预定义（YAML），角色内执行是 agent | Coordinator：主 agent 动态拆解派 worker |
| **单主 agent（+临时子 agent）** | 固定管线单执行者（prompt chaining） | **普通模式在此**：动态决策，按需派生 |

由此澄清几个常混的问题：

- **模式 C（MetaGPT-lite）既是 agentic workflow 也是多 agent**——预定义编排 × 多 agent 执行者。术语上这就是 "agentic workflow" 的准确含义：workflow 的骨架 + agent 的血肉。
- 三个模式不是互斥的"三选一"，而是同一二维空间的三个点。
- `run_workflow` 工具化（2026-09-02 已实现）本质是**动态编排的 agent 按需进入预定义编排的子流程**——两个维度的嵌套组合，与 Anthropic LeadResearcher 的做法同构。

## 三、业界形态盘点

| 形态 | 代表 | 状态 | 对应本项目 |
|---|---|---|---|
| ① LLM 自主委托 | Claude Code 日常（Fork 模式）、CodeBuddy 子代理、Cursor | 绝对主流 | 普通模式 ✅ 同构 |
| ② 对等团队 + 消息总线（Swarm） | CC Agent Teams（feature gate `AGENT_SWARMS`，未公开）、CodeBuddy 团队模式 | 真实存在的进阶特性 | **无对应** |
| ③ 预定义管线 | Devin、MetaGPT | 产品级 | 模式 C（已工具化为 run_workflow） |
| ④ 协调者用户模式 | 无（CC 有未公开的实验实现） | 无人产品化 | 模式 B（业界孤例，已降级为预设） |

### Claude Code 的模式递进（源码调研结论）

```
SubAgent 模式 → Fork 模式（缓存前缀共享，成本 -60%）→ Coordinator 模式（feature gate 未公开）→ Swarm 团队模式（feature gate 未公开）
```

关键事实：**CC 用户日常看到的多 agent 并行是 Fork 模式，不是 Coordinator**。CC 的杀手锏是 Fork 的 prompt cache 字节级前缀继承（多个并行子 agent 共享请求前缀，token 成本降 60% 以上）——本项目没有对应实现，是潜在优化方向。

### CodeBuddy 的两套机制（第一手信息）

1. **子代理**：code-explorer（只读探索），派发决策由主 agent 自己做，结果同步返回——与本项目普通模式**完全同构**（对应 explore agent）
2. **团队模式**：异步命名成员 + 消息总线，是本项目没有的形态：

| 维度 | 本项目普通模式异步 | CodeBuddy 团队模式 |
|---|---|---|
| 拓扑 | 星型：子 agent 只跟主 agent 通信 | 网状：成员间可互发消息 |
| 生命周期 | 一次性：完成即消失 | 持久：有名字、有保存的历史、可 respawn |
| 协调 | 主 agent 汇聚 | 可无中心（自组织）或主 agent 协调 |
| 协作协议 | 完成/失败通知 | 消息、广播、关闭请求、计划审批 |

### Anthropic 生产系统的架构（博文要点）

- LeadResearcher 先把计划写入持久 Memory（防上下文截断丢失），再并行创建 3-5 个子 agent
- CitationAgent 后置处理引用归属
- 8 条提示词工程原则，前两条：**像你的 agent 一样思考**（Console 模拟）、**教主 agent 如何委派**（子任务要明确目标/输出格式/工具指引/边界，模糊指令导致重复劳动）
- **工作量随查询复杂度缩放**：简单查证 1 个 agent；直接对比 2-4 个；复杂研究 10+
- **子 agent 产出写文件系统只传引用**（防"传话游戏"信息损失）——本项目的 workflow 产物机制已这么做，普通模式委托还没有
- 涌现行为：主 agent 的小改动会不可预测地改变子 agent 行为；最佳提示词不是严格指令而是**协作框架**

## 四、本项目的经验与教训

### 4.1 为什么会有模式 B（教学史实）

本项目照着 CC 源码调研复刻架构，忠实抄了 feature gate 后面的实验代码——连"应该藏在 gate 后面"的产品判断也一起抄了。模式 B 因此成为一个**活的架构教学样本**：亲手实现一个模式再发现其冗余，比读十篇博文更能建立"模式 vs 功能"的判断力。

### 4.2 已落地的修复（2026-09-02）

围绕"普通模式不触发子 agent"和"模式 C 不稳定"的诊断与修复：

1. **base.md Delegation 章节**：五类应委托场景 + 执行机制说明（同步=依赖安全顺序执行 / 后台=真并行，**依赖判定交给 LLM，不强制并行**）
2. **run_workflow 工具**：LLM 自主选择 SOP 管线，无需预选模式（`SOP_MODE`/`/workflow` 保留为显式入口）
3. **Coordinator 降级为预设**：默认关闭、配置驱动（`coordinator.enabled`），不再是主要模式
4. 模式 C 稳定性四项修复（详见 `git log 4566972`）：中性提示词覆盖（消解双重指令冲突）、JSON 解析失败重试（不再误判为测试失败）、角色崩溃兜底、fix_round 产物分版本

### 4.3 讨论中推翻过的错误设计（存档以防重犯）

- ❌ "把 Coordinator 的等待逻辑统一到普通模式"——这等于消灭普通模式的战术性，把所有委托逼成"派完全部等全部"。正确做法：机制说明交给 prompt，同步/异步选择由 LLM 按任务性质判断
- ❌ "引导里写 in parallel within a single response"——暗示"批处理=并行"。事实：一个响应里多个同步 tool_use 是**顺序执行**的（依赖安全），真并行必须 `run_in_background: true`
- ❌ "技能安装约定写进记忆"——产品固定约定属于 prompt（记忆是易失的、按项目隔离的、可被 LLM 整理掉的）

## 五、未来方向（待 trace 数据验证后决策）

按优先级：

1. **团队模式（Swarm 形态）**：星型 → 网状 + 成员持久化 + 协作协议。触发条件：普通模式的星型委托被充分使用（trace 里 agent_spawn 稳定出现）且出现"子任务间需要互相沟通"的真实需求。参考 CC 的 JSONL 消息总线 + 工作-空闲-关闭状态机 + CodeBuddy 团队模式
2. **Fork 式缓存共享**：并行子 agent 共享 prompt cache 前缀降成本（CC 的核心创新，本项目暂无）——依赖 Anthropic 原生 API，DeepSeek 兼容模式下可能不可行，需先验证
3. **工作量梯度引导**：委托指导中加入"简单 1 个 / 中等 2-4 个 / 复杂 10+"的量化缩放意识（Anthropic 原则 3）
4. **子 agent 产出走文件引用**：普通模式委托让子 agent 写产物文件、只回传引用（防传话游戏）
5. **REPL 空闲唤醒**：后台任务全部完成而主循环已退出时自动触发一轮处理结果（不改模式边界的等待缺口解法）
