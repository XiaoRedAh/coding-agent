# Claude Code 记忆系统深度调研报告

---

## 一、AI Agent 中 Memory 的含义、动机与必要性

### 1.1 什么是 Agent Memory？

在 AI Agent 领域，**Memory（记忆）** 指的是 Agent 跨越单次对话边界、持久化保存和召回信息的能力。它让 Agent 从一个"无状态的问答工具"进化为一个"有上下文感知的协作伙伴"。

这一概念源自认知科学对人类记忆的分层模型：

| 人类记忆类型 | 时间尺度 | 对应 AI Agent 概念 |
|---|---|---|
| 感觉记忆 | 毫秒级 | 单次 API 调用的输入 |
| 工作记忆 | 秒~分钟 | 上下文窗口（Context Window） |
| 长期记忆 | 天~年 | 持久化的 Memory 系统 |

### 1.2 为什么 Agent 需要记忆？

LLM 天生是**"金鱼记忆"**——每次对话都从零开始。这带来三个核心痛点：

1. **用户偏好丢失**：用户告诉 Agent "我喜欢用 bun 而不是 npm"，下次对话它就忘了。
2. **行为纠正失效**：用户纠正了 Agent 三次"不要 mock 数据库"，第四次它可能又 mock 了。
3. **上下文重建成本高**：每次对话都要重新了解项目背景、架构决策、团队约定。

> **没有记忆的 Agent 永远是新手**：每次都要重新了解用户偏好、重新踩同样的坑、重新探索同样的代码库。

### 1.3 记忆系统的核心约束原则

Claude Code 的记忆系统有一个根本性的设计约束：

> **只记忆不可从当前项目状态推导的信息。**

这个约束不是为了省存储空间，而是为了**防止记忆与现实漂移**。代码模式、架构、文件结构和 Git 历史都是自描述的——从代码本身读取永远比从记忆中回忆更准确。

**信息获取成本对比：**

```
人类开发者:
  记住文件结构 → 几小时的阅读和理解
  下次需要时回忆 → 几秒钟（如果有记忆）
  → 记忆的价值 = 节省的重新阅读时间

Agent:
  实时读取文件结构 → 几毫秒的工具调用
  每次重新获取的成本 → 几百个 token
  → 记忆的价值 ≈ 0（因为实时获取成本极低）
```

因此，记忆系统应该专注于保存**"实时获取不到"的信息**——人的偏好、决策的背景、外部的链接。

## 二、Claude Code 记忆系统的设计亮点与创新点

### 2.1 五层多粒度记忆架构

Claude Code 没有采用单一的记忆存储，而是构建了一个**五层记忆架构**，每层解决不同时间尺度和不同粒度的需求：

```
┌─────────────────────────────────────────────────────┐
│  Layer 5: Relevant Memories — 按需智能召回           │
├─────────────────────────────────────────────────────┤
│  Layer 4: Agent Memory — 子Agent专属记忆             │
├─────────────────────────────────────────────────────┤
│  Layer 3: Session Memory — 当前会话结构化笔记         │
├─────────────────────────────────────────────────────┤
│  Layer 2: Auto Memory (memdir) — AI自主学习知识库     │
├─────────────────────────────────────────────────────┤
│  Layer 1: CLAUDE.md — 静态指令与规则                  │
└─────────────────────────────────────────────────────┘
```

### 2.2 核心创新点总结

| 创新点 | 描述 |
|---|---|
| **闭合四类型分类法** | 不让 AI 自由存储——`user/feedback/project/reference` 四种类型，每种有明确的写入条件和排除规则 |
| **索引-内容分离 + 语义召回** | MEMORY.md 作为轻量索引常驻上下文，详细内容按需用 Sonnet 模型做 side query 选择注入 |
| **后台提取 + 主 Agent 互斥** | fire-and-forget 的后台 Agent 自动提取记忆，与主 Agent 写入互斥避免重复 |
| **Prompt 与代码协同设计** | 代码保证前置条件（如目录存在），Prompt 告知 AI 前置条件已满足，省去不必要的验证步骤 |
| **缓存感知架构** | 后台 Agent 与主 Agent 共享完全相同的工具列表和 System Prompt，最大化 Prompt Cache 命中率 |
| **"什么不该保存"同样重要** | 明确排除可推导信息，即使用户明确要求也引导到更有价值的方向 |
| **记忆是线索而非结论** | 记忆被当作"时间点快照"，使用前必须验证当前状态 |
| **Auto Dream 记忆巩固** | 类似人类睡眠时的记忆巩固过程，定期自动整理和优化记忆 |

## 三、分模块深入详解

### 模块 1：CLAUDE.md —— 静态指令的层级发现

#### 设计动机

CLAUDE.md 是 Claude Code 最早也最基础的"记忆"形式。它本质上不是 AI 自主写入的记忆，而是**人类预写的指令文件**。其核心动机是：让团队或个人能够以声明式方式定义 Agent 的行为规范，无需每次对话重复说明。

#### 设计思路：四种类型与层级加载

CLAUDE.md 定义了四种来源，按优先级从低到高排列：

```typescript
// utils/claudemd.ts:1-9
// Files are loaded in the following order:
// 1. Managed memory (eg. /etc/claude-code/CLAUDE.md) - Global instructions for all users
// 2. User memory (~/.claude/CLAUDE.md) - Private global instructions for all projects
// 3. Project memory (CLAUDE.md, .claude/CLAUDE.md, .claude/rules/*.md) - Instructions checked into the codebase
// 4. Local memory (CLAUDE.local.md) - Private project-specific instructions
//
// Files are loaded in reverse order of priority, i.e. the latest files are highest priority
```

| 类型 | 位置 | 版本控制 | 作用范围 |
|---|---|---|---|
| Managed | `/etc/claude-code/CLAUDE.md` | 否 | 组织级全局 |
| User | `~/.claude/CLAUDE.md` | 否 | 个人全局 |
| Project | `CLAUDE.md`, `.claude/CLAUDE.md`, `.claude/rules/*.md` | 是 | 项目级团队共享 |
| Local | `CLAUDE.local.md` | 否 | 个人项目级 |

**精妙的设计：加载顺序与优先级相反。** Managed 最先加载但优先级最低，Local 最后加载但优先级最高。这是因为 LLM 对消息中**靠后的内容关注度更高**（recency bias），所以高优先级内容排在后面。

#### 目录遍历机制

`getMemoryFiles()` 的核心逻辑是从当前工作目录逐级向上遍历到文件系统根目录：

```typescript
// utils/claudemd.ts:850-934
const dirs: string[] = []
let currentDir = originalCwd
while (currentDir !== parse(currentDir).root) {
  dirs.push(currentDir)
  currentDir = dirname(currentDir)
}
// Process from root downward to CWD
for (const dir of dirs.reverse()) {
  // CLAUDE.md (Project)
  // .claude/CLAUDE.md (Project)
  // .claude/rules/*.md (Project)
  // CLAUDE.local.md (Local)
}
```

`dirs.reverse()` 确保从根目录向 CWD 方向遍历，离 CWD 越近的文件优先级越高。

#### @include 指令与安全约束

CLAUDE.md 支持 `@path` 语法引用外部文件：

```
@./coding-standards.md
@~/global-rules.md
```

安全约束包括：只支持 70+ 种文本文件扩展名（`TEXT_FILE_EXTENSIONS`），防止二进制文件注入；循环引用检测和深度限制。

#### 注入到 System Prompt 的双路径

```typescript
// context.ts:155-188
export const getUserContext = memoize(async () => {
  const claudeMd = shouldDisableClaudeMd
    ? null
    : getClaudeMds(filterInjectedMemoryFiles(await getMemoryFiles()))
  return {
    ...(claudeMd && { claudeMd }),
    currentDate: `Today's date is ${getLocalISODate()}.`,
  }
})
```

当 feature gate `tengu_moth_copse` 开启时，MEMORY.md 索引不再通过此路径注入，改为完全依赖 Relevant Memories 的异步预取机制。

#### 与其他模块/产品的差异

| 对比维度 | CLAUDE.md | 其他产品（如 Cursor Rules） |
|---|---|---|
| **层级** | 四级层级（Managed/User/Project/Local） | 通常只有项目级 |
| **遍历机制** | 逐级向上遍历到根目录 | 通常只读当前目录 |
| **优先级方向** | 利用 LLM recency bias，后加载=高优先级 | 通常靠覆盖合并 |
| **模块化** | 支持 @include 递归引用 | 通常不支持 |

#### 示例模拟

假设项目结构如下：
```
/home/user/
├── .claude/CLAUDE.md          # User: "我偏好简洁回复"
└── projects/
    └── my-app/
        ├── CLAUDE.md           # Project: "使用 TypeScript strict mode"
        ├── .claude/
        │   └── rules/
        │       └── testing.md  # Project: "使用 Vitest 不要用 Jest"
        └── CLAUDE.local.md     # Local: "API key 在 .env.local"
```

加载顺序（注入 System Prompt 的顺序）：
1. User: `~/.claude/CLAUDE.md` → "我偏好简洁回复"
2. Project: `/home/user/projects/my-app/CLAUDE.md` → "使用 TypeScript strict mode"
3. Project: `.claude/rules/testing.md` → "使用 Vitest 不要用 Jest"
4. Local: `CLAUDE.local.md` → "API key 在 .env.local" ← **最高优先级（最后加载）**

### 模块 2：Auto Memory (memdir) —— AI 的持久化知识库

#### 设计动机

Auto Memory 是 Claude Code 记忆系统的**核心**。与 CLAUDE.md 由人类编写不同，memdir 中的内容**完全由 AI 生成和维护**。它解决的核心问题是：让 AI 能够跨会话学习和记住用户偏好、项目背景和行为反馈。

#### 目录结构与路径解析

```
~/.claude/projects/<sanitized-git-root>/memory/
├── MEMORY.md              # 索引文件（≤200行）
├── user_role.md            # 用户角色记忆
├── feedback_testing.md     # 反馈记忆：测试偏好
├── project_auth_rewrite.md # 项目记忆：认证重构背景
├── reference_linear.md     # 参考记忆：外部系统指针
├── team/                   # 团队共享记忆
│   ├── MEMORY.md
│   └── ...
└── logs/                   # Assistant 模式日志
    └── 2026/03/2026-03-15.md
```

路径解析有三级优先级：

```typescript
// memdir/paths.ts:223-235
export const getAutoMemPath = memoize(
  (): string => {
    const override = getAutoMemPathOverride() ?? getAutoMemPathSetting()
    if (override) return override
    const projectsDir = join(getMemoryBaseDir(), 'projects')
    return (
      join(projectsDir, sanitizePath(getAutoMemBase()), AUTO_MEM_DIRNAME) + sep
    ).normalize('NFC')
  },
  () => getProjectRoot(),
)
```

1. **环境变量覆盖**：`CLAUDE_COWORK_MEMORY_PATH_OVERRIDE`
2. **Settings 覆盖**：`autoMemoryDirectory`（排除 projectSettings——防止恶意仓库将路径指向 `~/.ssh`）
3. **默认路径**：基于 Git 根目录的 sanitized 路径

**安全设计亮点**：`findCanonicalGitRoot()` 确保所有 Git worktree 共享同一个记忆目录，避免同一仓库的不同 worktree 各自维护一份记忆。

#### 四类记忆的闭合分类法

```typescript
// memdir/memoryTypes.ts:14-19
export const MEMORY_TYPES = ['user', 'feedback', 'project', 'reference'] as const
```

| 类型 | 含义 | 写入时机 | 不应保存的内容 | 结构要求 |
|---|---|---|---|---|
| `user` | 用户角色、偏好、知识水平 | 了解到用户信息时 | 负面评价 | 自由格式 |
| `feedback` | 行为纠正 + 正向确认 | 用户纠正或确认做法时 | 仅保存纠正而忽视确认 | Rule + Why + How to apply |
| `project` | 项目背景、决策、截止日期 | 了解到不可从代码推导的信息时 | 可从 git log 推导的内容 | 事实 + Why + How to apply |
| `reference` | 外部系统指针 | 了解到外部资源位置时 | 系统的具体内容（只存指针） | 自由格式 |

**为什么是闭合系统？** 开放类型系统会导致：(1) 类型爆炸；(2) 分类模糊；(3) 索引膨胀。闭合四类型的设计是"**约束即自由**"的哲学。

**"What NOT to save" 同样重要：**

```
这些排除规则即使用户明确要求保存也生效。如果用户说"记住这个 PR 列表"，
Agent 应该反问"其中什么是令人惊讶或不显而易见的"——那才是值得保存的部分。
```

**为什么 feedback 同时记录成功和失败？** 源码注释解释：

> 如果你只保存纠正，你会避免过去的错误，但会偏离用户已经验证过的好方法，并可能变得过于谨慎。

#### 存储格式

每条记忆是独立的 Markdown 文件，带 YAML frontmatter：

```markdown
---
name: pre-commit-lint-requirement
description: Must run npm run lint before every commit; CI failed for a full day due to unlinted code
type: feedback
---

**Rule**: Run `npm run lint` before every code commit.

**Why:** A previous commit with unlinted code caused CI to fail for an entire day, blocking the team.

**How to apply:** Before using git commit, always run `npm run lint` first and fix any errors.
```

`description` 字段是**召回系统的核心依据**——Sonnet 模型主要依赖它判断相关性，因此必须足够具体。

#### MEMORY.md 索引与截断保护

```typescript
// memdir/memdir.ts:34-38
export const ENTRYPOINT_NAME = 'MEMORY.md'
export const MAX_ENTRYPOINT_LINES = 200
export const MAX_ENTRYPOINT_BYTES = 25_000
```

`truncateEntrypointContent()` 实现**双重保护**：

1. **行截断（200 行）**：保护 Agent 的理解效率——即使每行很短，200 行以上的索引也需要 Agent 花费更多 token 理解
2. **字节截断（25KB）**：保护上下文预算——捕捉行数在 200 以内但单行极长的异常（实际观察到 197KB 在 200 行内）

截断顺序也有讲究——先按行截断再按字节截断，两种情况都有对应保护。

#### DIR_EXISTS_GUIDANCE —— Prompt 与代码协同设计

```typescript
// memdir/memdir.ts:116-118
export const DIR_EXISTS_GUIDANCE =
  'This directory already exists — write to it directly with the Write tool (do not run mkdir or check for its existence).'
```

源码注释：*Shipped because Claude was burning turns on ls/mkdir -p before writing.* 解决方案不是改代码逻辑，而是在 Prompt 中告诉 AI "目录已经存在，直接写"。同时，代码层面通过 `ensureMemoryDirExists()` 保证这个承诺成立。

> **这是典型的 Prompt 与代码协同设计模式：代码保证前置条件，Prompt 告知 AI 前置条件已满足，从而省去不必要的验证步骤。**

#### System Prompt 中的记忆指令注入

`loadMemoryPrompt()` 根据启用状态做三路分发：

```
loadMemoryPrompt()
    ├── KAIROS && active? → buildAssistantDailyLogPrompt() [日志追加模式]
    ├── TEAMMEM && enabled? → buildCombinedMemoryPrompt() [私有+团队双目录]
    ├── AutoMem enabled? → buildMemoryLines() [单目录模式]
    └── disabled → return null
```

通过 `systemPromptSection('memory', ...)` 注册为 System Prompt 的**缓存段**——只要 MEMORY.md 内容不变，Prompt Cache 命中率不受影响。

#### 示例模拟

**场景**：用户在第3次对话中说"我不喜欢你在每次响应末尾加总结"

**写入过程**：
1. 主 Agent 识别到这是一条 `feedback` 类型记忆
2. 写入文件 `~/.claude/projects/-Users-alice-my-app/memory/feedback_terse.md`
3. 更新 `MEMORY.md` 索引添加一行：`- [简洁回复偏好](feedback_terse.md) — 不要尾部总结`

**第4次对话时**：
1. 会话启动，`MEMORY.md` 被加载到 System Prompt
2. 用户提交查询，`startRelevantMemoryPrefetch()` 异步扫描记忆文件
3. Sonnet 模型判断 `feedback_terse.md` 与当前查询相关
4. 该记忆内容作为 Attachment 注入上下文
5. Claude 在响应中自动遵循"不加尾部总结"的偏好

### 模块 3：Background Extract Memories —— 从对话中自动提取记忆

#### 设计动机

Auto Memory 的内容从哪来？除了 AI 在对话中主动写入（用户说"记住这个"），Claude Code 还有一个**后台提取系统**，在每次对话回合结束时自动运行，从对话中萃取值得记住的信息。核心动机：**不要让记忆的保存依赖于用户的显式请求。**

#### 触发机制：stopHooks 中的 fire-and-forget

```typescript
// services/extractMemories/extractMemories.ts:598-603
export async function executeExtractMemories(
  context: REPLHookContext,
  appendSystemMessage?: AppendSystemMessageFn,
): Promise<void> {
  await extractor?.(context, appendSystemMessage)
}
```

在 `handleStopHooks`（对话循环结束时）被 fire-and-forget 调用。

#### 互斥控制（核心设计）

```typescript
// services/extractMemories/extractMemories.ts:556-564
if (inProgress) {
  logForDebugging('[extractMemories] extraction in progress — stashing for trailing run')
  pendingContext = { context, appendSystemMessage }
  return
}
```

**闭包作用域管理的三个核心状态：**
- `lastMemoryMessageUuid`：游标，标记上次处理到哪条消息
- `inProgress`：互斥锁，防止并行执行
- `pendingContext`：暂存最新上下文等当前提取完成后执行 trailing run

这是一个**优雅的合并模式**：不排队所有请求，只保留最新的一个。

#### 主 Agent 与提取 Agent 的互斥

```typescript
// services/extractMemories/extractMemories.ts:348-360
if (hasMemoryWritesSince(messages, lastMemoryMessageUuid)) {
  logForDebugging('[extractMemories] skipping — conversation already wrote to memory files')
  const lastMessage = messages.at(-1)
  if (lastMessage?.uuid) {
    lastMemoryMessageUuid = lastMessage.uuid
  }
  return
}
```

`hasMemoryWritesSince()` 扫描助手消息中的 `tool_use` 块，检查是否有 Edit/Write 操作目标路径在记忆目录范围内。**避免了主 Agent 和后台 Agent 同时写同一个记忆文件的竞态。**

#### Forked Agent 的权限沙箱

```
提取 Agent 权限白名单：
✅ 允许：FileRead、Grep、Glob（任意路径，只读）
✅ 允许：Bash（仅只读命令：ls, find, grep, cat, stat...）
✅ 允许：FileEdit/FileWrite（仅限 memoryDir 内的路径）
❌ 拒绝：MCP、Agent、写入型 Bash、其他所有工具
```

**最小权限原则的���美体现**——即使后台 Agent 的 Prompt 被注入攻击，它也无法对记忆目录之外的文件系统造成影响。

#### 提取策略：两步并行

提取 Prompt 指导 Agent 采用两步并行策略：

> *turn 1 — issue all FileRead calls in parallel for every file you might update; turn 2 — issue all FileWrite/FileEdit calls in parallel.*

限制 `maxTurns: 5`，防止 Agent 进入验证兔子洞（rabbit-hole）。

#### 缓存感知的关键设计

提取 Agent 通过 `runForkedAgent()` 创建，与主对话共享完全相同的 System Prompt 和工具列表。关键约束：

> **工具列表是 API 缓存 key 的一部分。** 如果 forked Agent 使用与主 Agent 不同的工具集，缓存就无法命中。这就是为什么工具权限过滤使用 `canUseTool` 回调而非不同的工具列表——**接口一致，行为可变。**

```
无缓存共享时：提取 Agent 重新发送 80,000 tokens → $0.24
有缓存共享时：提取 Agent 复用缓存 → $0.008（仅缓存读取费用）
节省：96.7%
```

#### 工作流程时序图

```
对话结束 → 检查主Agent是否已主动写入记忆？
  ├─ 是 → 跳过提取，推进游标（互斥机制）
  └─ 否 → 检查节流计数器是否达到阈值？
       ├─ 否 → 等待下一次
       └─ 是 → Fork 后台 Agent
            → 共享 System Prompt + 工具列表（缓存感知）
            → Turn 1: 并行读取所有已有记忆文件
            → Turn 2: 并行写入新记忆 + 更新索引
            → 是否有暂存的尾随上下文？
                 ├─ 是 → 尾随提取（跳过节流计数器）
                 └─ 否 → 完成
```

### 模块 4：Session Memory —— 当前会话的结构化笔记

#### 设计动机

Session Memory 解决的是一个不同的问题：当对话变得很长，需要 auto-compact（上下文压缩）时，如何保留关键的会话上下文？它本质上是一个**会话级的实时笔记本**。

#### 与 Auto Memory 的核心差异

| 维度 | Auto Memory | Session Memory |
|---|---|---|
| 生命周期 | 跨会话永久 | 单次会话 |
| 内容来源 | AI 自主判断值得跨会话保留的知识 | 当前会话的工作状态快照 |
| 核心价值 | 长期学习和记忆 | 服务于 compact（上下文压缩） |
| 触发方式 | 对话结束时后台提取 | 双阈值定期触发 |

#### 结构化模板

Session Memory 使用固定的 10 段 Markdown 模板：

```typescript
// services/SessionMemory/prompts.ts:11-41

_A short and distinctive 5-10 word descriptive title..._

# Current State
_What is actively being worked on right now?..._

# Task specification
_What did the user ask to build?..._

# Files and Functions
_What are the important files?..._

# Workflow
_What bash commands are usually run?..._

# Errors & Corrections
_Errors encountered and how they were fixed..._

# Codebase and System Documentation
_What are the important system components?..._

# Learnings
_What has worked well? What has not?..._

# Key results
_If the user asked a specific output..._

# Worklog
_Step by step, what was attempted, done?..._
`
```

设计亮点：**模板不可变 + 内容可变**——每个 section 有固定标题和斜体描述行，AI 只能修改描述行之后的内容。这确保了结构的稳定性。

#### 双阈值触发机制

```typescript
// services/SessionMemory/sessionMemory.ts:134-181
export function shouldExtractMemory(messages: Message[]): boolean {
  const currentTokenCount = tokenCountWithEstimation(messages)
  
  // 1. 初始化阈值：上下文 token 数达到 10000
  if (!isSessionMemoryInitialized()) {
    if (!hasMetInitializationThreshold(currentTokenCount)) return false
    markSessionMemoryInitialized()
  }
  
  // 2. Token 增长阈值：自上次提取后增长 5000 tokens
  const hasMetTokenThreshold = hasMetUpdateThreshold(currentTokenCount)
  
  // 3. Tool call 计数阈值：3 次
  const hasMetToolCallThreshold = toolCallsSinceLastUpdate >= getToolCallsBetweenUpdates()
  
  // 触发条件：token 阈值 AND (tool call 阈值 OR 无 tool call 的自然暂停)
  return (hasMetTokenThreshold && hasMetToolCallThreshold) ||
         (hasMetTokenThreshold && !hasToolCallsInLastTurn)
}
```

**关键约束：Token 阈值是必要条件。** 即使 tool call 阈值满足，token 没增长就不触发——防止过度提取。

#### 与 Compact 的协同

Session Memory 的核心价值在 compact 时体现。当 auto-compact 触发时，可以**直接复用后台已经提取好的 Session Memory 作为 compact 后的总结**，免去额外的 compact 总结 API 调用。

大小控制：
```typescript

```

### 模块 5：Agent Memory —— 每个 Agent 的专属记忆

#### 设计动机

除了主对话的记忆，Claude Code 还为**自定义子 Agent**（通过 Agent 工具创建的）提供了独立的记忆空间。一个 "explorer" Agent 学到的代码导航技巧、一个 "test-runner" Agent 学到的测试模式——这些是 Agent 类型特有的操作知识，与用户偏好和项目决策没有关系。分离存储避免了主记忆被 Agent 操作细节污染。

#### 三种作用域

```typescript
// tools/AgentTool/agentMemory.ts:12-13
export type AgentMemoryScope = 'user' | 'project' | 'local'
```

| Scope | 默认路径 | 版本控制 | 适用场景 |
|---|---|---|---|
| `user` | `<memoryBase>/agent-memory/<type>/` | 否 | 跨项目通用知识 |
| `project` | `<cwd>/.claude/agent-memory/<type>/` | 是 | 项目特定知识，团队共享 |
| `local` | `<cwd>/.claude/agent-memory-local/<type>/` | 否 | 本地特定知识，不分享 |

每种 scope 的行为指引不同：

```typescript
case 'user':
  scopeNote = '- Since this memory is user-scope, keep learnings general since they apply across all projects'
case 'project':
  scopeNote = '- Since this memory is project-scope and shared via version control, tailor your memories to this project'
case 'local':
  scopeNote = '- Since this memory is local-scope (not checked into version control), tailor to this project and machine'
```

#### Fire-and-forget 目录创建

`loadAgentMemoryPrompt()` 在 React render 的同步路径中被调用，不能是 async。解决方案：

```typescript
// tools/AgentTool/agentMemory.ts:164-165
// Fire-and-forget: this runs at agent-spawn time inside a sync
// getSystemPrompt() callback. The spawned agent won't try to Write
// until after a full API round-trip, by which time mkdir will have completed.

```

Agent 从 spawn 到实际写文件，中间至少要经过一个完整的 API 往返（几百毫秒到几秒），而 mkdir 只需要微秒级别，因此 fire-and-forget 是安全的。

### 模块 6：Relevant Memories —— 按需召回的智能记忆注入

#### 设计动机

前面的模块都是关于"如何存储记忆"。Relevant Memories 解决的是"**何时以及如何召回记忆**"——不是把所有记忆都塞进上下文，而是只注入与当前查询相关的记忆。

#### 双阶段召回：Scan → Select

**阶段一：扫描（scanMemoryFiles）**

```typescript
// memdir/memoryScan.ts:35-77
export async function scanMemoryFiles(
  memoryDir: string, signal: AbortSignal,
): Promise<MemoryHeader[]> {
  const entries = await readdir(memoryDir, { recursive: true })
  const mdFiles = entries.filter(f => f.endsWith('.md') && basename(f) !== 'MEMORY.md')
  
  // 并行读取每个文件的前 30 行 frontmatter
  const headerResults = await Promise.allSettled(
    mdFiles.map(async (relativePath) => {
      const { content, mtimeMs } = await readFileInRange(filePath, 0, FRONTMATTER_MAX_LINES)
      const { frontmatter } = parseFrontmatter(content, filePath)
      return { filename, filePath, mtimeMs, description, type }
    }),
  )
  
  // 按修改时间降序排序，最多 200 个
  return results.sort((a, b) => b.mtimeMs - a.mtimeMs).slice(0, MAX_MEMORY_FILES)
}
```

**单遍扫描设计**：`readFileInRange` 内部 `stat` 获取 `mtimeMs`，所以读取和排序不需要两轮 syscall。对于常见情况（N ≤ 200），syscall 数量减半。

**阶段二：选择（selectRelevantMemories）**

```typescript
// memdir/findRelevantMemories.ts:77-141
const result = await sideQuery({
  model: getDefaultSonnetModel(),
  system: SELECT_MEMORIES_SYSTEM_PROMPT,
  messages: [{ role: 'user', content: `Query: ${query}\n\nAvailable memories:\n${manifest}${toolsSection}` }],
  max_tokens: 256,
  output_format: { type: 'json_schema', schema: { /* selected_memories: string[] */ } },
})
```

用 **Sonnet 模型做一个轻量 side query**，传入用户查询和记忆清单（文件名 + 描述），选择最多 5 个相关文件。

**为什么用 Sonnet 而非关键词匹配？** 语义相关性评估更准确。例如用户问"部署流程"时，关键词匹配可能错过标题为"CI/CD 注意事项"的记忆���但 Sonnet 能理解语义关联。

**反直觉的 recentTools 设计**：如果最近使用了某些工具，这些工具的**参考文档不应被召回**（AI 已经在使用它了），但相关的**已知问题/注意事项仍应被召回**——正在使用时恰恰是这些警告最重要的时候。

#### Prefetch + Attachment 注入

```
用户提交查询 → startRelevantMemoryPrefetch() → [并行执行 sideQuery]
                                                         ↓
query() 组装消息 ← await prefetch result ← 选中的记忆
                                                         ↓
                                               注入为 'relevant_memories' Attachment
```

注入时的记忆内容带有**预计算的新鲜度标记**：

```typescript
// memdir/memoryAge.ts:15-20
export function memoryAge(mtimeMs: number): string {
  const d = memoryAgeDays(mtimeMs)
  if (d === 0) return 'today'
  if (d === 1) return 'yesterday'
  return `${d} days ago`
}
```

**为什么预计算？** 如果在每次 API 调用时重新计算 `memoryAge()`，"saved 3 days ago" 可能变成 "saved 4 days ago"——不同的字节会导致 **Prompt Cache 失效**。预计算保证了跨 turn 的字节稳定性。

#### Session-level 去重与总量控制

```typescript
// utils/attachments.ts:2251-2266
export function collectSurfacedMemories(messages: ReadonlyArray<Message>) {
  const paths = new Set<string>()
  let totalBytes = 0
  for (const m of messages) {
    if (m.type === 'attachment' && m.attachment.type === 'relevant_memories') {
      for (const mem of m.attachment.memories) {
        paths.add(mem.path)
        totalBytes += mem.content.length
      }
    }
  }
  return { paths, totalBytes }
}
```

**精巧的 compact 自动重置**：扫描 messages 而非追踪状态。当 compact 发生时，旧的 attachment 消息被删除，`surfacedPaths` 自然被重置——那些记忆可以被合理地重新注入到压缩后的上下文中。

### 模块 7：Auto Dream —— 记忆的后台巩固

#### 设计动机

Auto Dream 类似于人类睡眠时的记忆巩固过程。当积累了足够多的会话后，系统会自动运行 `/dream` 技能来整理和优化记忆——合并冗余、删除过时、提炼关键信息。

#### 三重门控

```typescript
// services/autoDream/autoDream.ts:95-100
function isGateOpen(): boolean {
  if (getKairosActive()) return false  // KAIROS 模式用自己的 dream
  if (getIsRemoteMode()) return false
  if (!isAutoMemoryEnabled()) return false
  return isAutoDreamEnabled()
}
```

通过后还有：
1. **时间门控**：距上次巩固 ≥ 24 小时
2. **会话门控**：此期间至少有 5 个新会话
3. **锁门控**：无其他进程正在巩固（文件锁）

#### 锁与回滚

```typescript
// services/autoDream/autoDream.ts:261-270
} catch (e: unknown) {
  if (abortController.signal.aborted) {
    logForDebugging('[autoDream] aborted by user')
    return
  }
  failDreamTask(taskId, setAppState)
  // Rewind mtime so time-gate passes again
  await rollbackConsolidationLock(priorMtime)
}
```

如果巩固失败，**回滚锁的 mtime** 让时间门控重新通过，下次会话会再次尝试。防止"梦被永久打断"。

## 四、不同记忆层的区别、适用场景与触发时机

### 4.1 全面对比表

| 维度 | CLAUDE.md | Auto Memory | Session Memory | Agent Memory | Relevant Memories |
|---|---|---|---|---|---|
| **生命周期** | 永久 | 跨会话 | 单次会话 | 跨会话 | 每用户 turn |
| **内容来源** | 人类手动编写 | AI 自主生成/维护 | AI 后台提取 | 子 Agent 生成 | 从已有记忆中选择 |
| **存储位置** | 项目目录/用户目录 | `~/.claude/projects/.../memory/` | `~/.claude/projects/.../<sessionId>/session-memory/` | `agent-memory/` 三种 scope | 内存（Attachment） |
| **核心职责** | 静态指令与规则 | 自动提取的持久化知识 | 当前会话的结构化笔记 | 特定 Agent 的专属记忆 | 按需召回的相关记忆 |
| **注入方式** | System Prompt (getUserContext) | 索引→System Prompt；内容→Attachment | compact 时作为总结 | Agent 的 System Prompt | user message (isMeta) |
| **版本控制** | Project 类型可以 | 否 | 否 | project scope 可以 | 不涉及 |
| **大小限制** | 无硬限制 | 索引 200 行/25KB | 12000 tokens | 与 Auto Memory 类似 | 每次最多 5 个文件 |

### 4.2 触发时机详解

```
会话启动时：
  → CLAUDE.md 加载（memoize 缓存，session 只加载一次）
  → MEMORY.md 索引注入 System Prompt
  
用户每次提交查询时：
  → startRelevantMemoryPrefetch() 异步预取相关记忆
  → 选中的记忆作为 Attachment 注入
  
每个对话回合结束时（主 Agent 停止时）：
  → 检查是否需要触发后台记忆提取（节流 + 互斥）
  → 检查 Session Memory 是否需要更新（双阈值）
  
auto-compact 触发时：
  → Session Memory 提供 compact 后的总结（免额外 API 调用）
  
足够多会话积累后（≥5 个新会话，≥24 小时）：
  → Auto Dream 自动巩固和整理记忆
  
用户显式说"记住这个"时：
  → 主 Agent 直接写入 memdir
  
用户显式说"忘记这个"时：
  → 主 Agent 查找并删除对应记忆文件
```

### 4.3 典型场景匹配

| 场景 | 最适合的记忆层 | 原因 |
|---|---|---|
| "我们团队统一用 ESLint + Prettier" | CLAUDE.md (Project) | 团队共享的静态规范，适合签入 Git |
| "我喜欢简洁回复，不要总结" | Auto Memory (feedback) | 个人偏好，跨会话有效 |
| "认证模块选 JWT 因为要支持移动端" | Auto Memory (project) | 决策背景，不可从代码推导 |
| "当前正在重构 UserService 的第 3 步" | Session Memory | 当前会话的临时工作状态 |
| "测试 Agent 在这个项目应该用 Vitest" | Agent Memory (project) | 子 Agent 的项目特定知识 |
| 用户问"部署流程"→自动注入相关的 CI/CD 记忆 | Relevant Memories | 按需语义匹配 |

## 六、可迁移的设计模式

### 模式 1：分类法驱动的记忆质量
不要让 AI 自由存储任何东西——定义一个闭合的分类法，每种类型有明确的写入条件和排除规则。特别重要的是定义"什么不应该存储"。

### 模式 2：索引-内容分离 + 智能召回
将记忆分为轻量索引（≤200 行）和按需召回的详细内容。用轻量模型做 side query 选择最多 5 个相关文件注入。

### 模式 3：后台提取 + 主 Agent 互斥
不要在主对话流中做记忆提取（会增加延迟），而是用 fire-and-forget 的后台 Agent。通过互斥机制避免重复写入。

### 模式 4：Prompt 与代码协同
如果模型反复犯某个错误（如检查目录是否存在），优先考虑改变环境（预创建目录）而非改变提示词。然后在 Prompt 中告知 AI 前置条件已满足。

### 模式 5：缓存感知的接口设计
保持工具列表等缓存相关参数不变，将差异化逻辑放在运行时的行为控制中（`canUseTool` 回调）。
